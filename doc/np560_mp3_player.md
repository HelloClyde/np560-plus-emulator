# 原厂 MP3 播放器：功能键纠正与实际 ROM 阻断点

## 2026-09-23：Web 音频关闭失败的隔离

`AudioOutput.stop()` 原先直接丢弃 `AudioContext.close()` 返回的Promise，
关闭失败会形成未处理拒绝。以可控浏览器接口替身先复现
`stop leaked a close rejection`，再修复生产清理路径：停止监听并清空当前引用，
捕获同步抛错和异步关闭失败，向当前已停止会话显示释放失败提示。
延迟错误按会话serial隔离，不能覆盖重新启用后的状态。

`test_np560_audio_output.js` 验证失败被处理、停止状态完整、可重新启用、
旧会话错误不污染新会话，以及同步抛错分支；原有PCM/中断/实际UI接线检查
全部通过，32项Web前端检查也通过。没有修改guest状态、PCM或解码器，
没有重启用户实例。此处是受控错误路径复现，不声称真实设备曾发生同样故障，
也不能据此认定移动端听感或NPE缺失音效已经完成。

### 同一录音的关闭区间拆分

v2 `audio-analysis.json` 的真实零值段可对齐完整控制事件：关闭前 50.5ms、
关闭 93.023375ms、重开后 220.583333ms。以 sequence=14 / PC=08:478E 首次关闭
为零点，sequence=17 在 50.03ms 又由同一 PC 写关闭值；19/20 在约 50.04ms
由 08:3306/330A 清两路 DAC。21 在 88.17ms 由 08:38F4 改音频 PLL，
随后约 88.21ms 才进入 HLE release，93.023375ms 由 08:4718 重开。
因此当前正常短曲也保留第二次停止等待；约 38ms 区间位于第二次清 DAC 与改 PLL
之间，而非 HLE 解码或重新创建会话耗掉整个 93ms。控制事件只给边界，不能精确归属
中间所有函数时间；`cause_verified=false` 继续保留。

进一步读取未修改 PRG 的停止回调后继（runtime / source 段相差 0x1D）：
`31:CF22→33:662E→32:8394`，后者仅在 `F010 & FFF0 == 8040` 时才调用
`08:3262`，不同于前一停止入口要求的 8010。不能看到另一个 CALL 就算第三次等待。
后续 `33:6EE2`、`33:6F30` 在 PRG source `50:6EE2/6F30` 本身均是
LINK/UNLINK/RETS 三条指令，不是此处模拟器遗漏实现的服务，也不是长等待。
`31:CF3E..CF4E` 在 `52:5468` 对象非空时调用 `32:A9D2`，之后清空该指针；
这段对象处理及其返回后的重开路径仍是下一轮动态定位范围。静态分支不能代替本次
实际执行证据，尚未修改任何原厂等待或按地址绕过调用。

后继细化：source `4F:A9D2..AA24` 是指针间接关闭包装器，不是画图或固定延时：
读取传入地址中的双 word 对象指针，调用 `24:EAEC`，保存返回码，无条件清空传入
指针，再返回该错误码。`24:EAEC` 的 source `41:EAEC..EF04` 则是带设备表与
条件提交的关闭路径：空对象报 FFEE，设备回调不存在报 FFFE；对象 +0x15 的 bit7
置位才走 `24:EC22..EDE2` 提交分支（包括 `30:6D9E`、`1C:E37E` 等调用）。
末尾通过设备表 +0x14 的远指针执行可选回调，再调用 `32:5592` 清理。
不能仅因关闭函数包含提交代码就认定只读 MP3 每次重播都写 NAND；须记录实际对象
标志、分支和回调目标。已有旧 PC 点采样仍混有 LCD 合成、内存管理和校验路径，
不能把全部约 38ms 指派给 `32:A9D2`。下一步动态边界应覆盖整个回调返回→重新改 PLL，
而不是只测 HLE release 或只测这个条件关闭包装器。

## 2026-09-23：超长单帧请求在解码前拒绝

延续声道错误修复，发现另一条先提交历史再报错的路径：guest LENGTH/BODY 一致，
但长度比 MP3 头声明的帧长多一字节，codec 原先成功消费第一帧并提交状态，
HLE 随后因 consumed != length 返回 status=7/detail=0x806。修正长度直接重试，
PCM 与未插入错误请求的对照不同。不是只改 LENGTH 导致的早期长度一致性错误。

单帧 codec API 现在在调用解码器前拒绝 surplus bytes：普通请求返回 DECODE_ERROR，
保留 HLE 原有 status/detail；final 请求仍按原规则返回 BAD_HEADER。输出清零、
历史不变。调用者负责分帧，不让该 API 跳过或偷偷消费拼接数据。合法完整帧、
缺少历史时 NO_PCM 的消耗语义及 terminal 短帧策略均未改动。

## 2026-09-23：重载调用者不是多缓冲循环

重新按指令边界核对 PRG 源 `2F:2BF2..2D40`（文件偏移 `2C2BF2..2C2D40`）：
这是动态记录中的同步搜索调用者，不要再按 resident 的其它段别名盲加 1D。
静态控制流如下，尚未增加完整文件服务执行夹具：

- 2C12 比较目标位置与 25B0/25B2；相等直接返回 0。
- 2C26/2C2A 清零 284A/284C 的历史字节，然后调用 1B:C5EC 定位。
- 2C54..2C62 读取 284E/2850 并与 0600 比较；两条分支均只调用一次
  1C:CCD4，读取到内部缓冲 00:1000，返回长度保存在 FP-4/FP-2。
- 返回长度零时在 2CE8 返回 FFFE；否则先调用 31:EB24（可选逐字节 XOR，
  并非字节交换），然后 2D2A 以方向 0 调用 16:E2B4。
- 2D30..2D40 直接保留搜索返回值并退出，没有 FFFA 后重读下一块的回边。

因此当前已知 Info 反例不是这条函数的连续缓冲拼接失效。前一节六种拼接测试
仅证明搜索函数的能力，不表示这个调用者会使用跨块能力。
原厂的单窗口策略及严格头字段匹配均暂不修改；可选固件兼容补丁是另一层行为变更，
不是 01/02 缺失服务 HLE，需要明确选择并与原厂模式分开。目前未实现此补丁。

### 定位推进：重新装载发生在 HLE 复位之前

H 前后 HLE calls 的 reset 项保持3，decode从297到301后停止，release仍0；
即没有进入一次新的HLE codec reset/release。最后ROM调用由播放期01:49BE
变为02:6200（NAND读），之后保持不变。该观察不能证明所有guest代码停止：
主循环PC仍变化，按键S仍被消费。

静态核对原PRG：`0D:3B62..3B80` 读取播放器+0806的32位目标时间并加0x1388
（5000），随后与+0802上限比较。`0D:3C6E` 或 `3CEE` 分别进入30:9978/
32:B974；前者经 `30:9A5A → 22:9C28`，后者经 `32:B9B8 → 25:0000`。
这些不是仅绘制时间的函数；上面的动态记录已确认本次选择30:9978分支。

路径才在22:A0E2调用1D:33CE重建解码配置，再由08:31AC启输出。

监视点。早退原因现已缩小到同步匹配失败，不先改DAC或补发松键事件，未实施修复。

此前“F1 打不开文件”首先是 Web 功能键映射错误，不是文件窗口缺少 ROM。

## 追加：MP3 输入、输出与缺失服务的边界

本节为原始 PRG 静态核对及原厂输入函数的隔离执行结果。
**没有修改 QEMU、重建 ROM 或歌曲，没有越过 `01:4804` 运行完整播放器，也没有新增播放能力。**
地址均为 VMA03；用 `dump_np560_range.py` 查看时 source 地址需加 `1D:0000`。

### 压缩输入搬运已在 PRG 中，不应再做成新 ROM 服务

原厂调用链为 `16:EC34` 文件续填 → 两块暂存区 → `16:EA42` → `16:E844`：

- `16:EC34..EDB0` 使用文件读取 `1C:CCD4`，目的区为 `50:D948` 或 `50:E948`，
  单次上限 `1000` bytes。成功路径再调用 `31:EB24`，把读到的 byte 数除以 2，
  存为 `51:2854/2856` 的 word 数；最后一块及错误路径修改 BIT89.14/.11。
  这里记录 31:EB24 的调用，不仅凭名称推定其完整转换语义。
- `16:EA42` 先调用缺失的 `01:49BE`，将 R0 与当前剩余 word 数 `51:2852` 比较，
  按较小数量调用写入函数；必要时切换暂存区。当前源 far pointer 在 `51:2858/285A`。
- **`16:E844..E896` 是完整的 84-byte 原厂写入函数**，参数为源 far pointer 和 word 数。
  它保存 DS0、DS1、R8、XM0，选择 DS0=0、XM0=`0600`，从内部 `00:3340` 取写指针，
  用 `REP; MOV [R8++],[R1++]` 搬运后写回指针，并以 R0:R1 返回推进后的源 far pointer。
  它没有调用缺失 ROM，也没有像另一条 PCM 写入函数那样更新 `4B02` 计数。
  零 word 时不搬运、不更新写指针，但仍会执行清状态位等其它指令。

因此 `01:49BE` 的返回值在这里被用作可追加的 **word 数**；不能把它伪造为固定可用空间。
`16:E906..E91A` 还将 `02FE - 返回值` 与消费位置变化比较，说明必须与解码推进共享状态。
该常量不足以单独确定读指针地址、满/空判别及所有边界规则。

### 输出及回调的已知契约

| 缺失入口 | 原厂消费者给出的约束 | 仍缺什么 |
| --- | --- | --- |
| `01:4804` | 三个已核对调用者 `1D:300A/375C`、`27:95F4` 都传六个 far pointer 与 `0300`，清栈 `001A` bytes | 六参数各自的完整含义、内部字段绑定及全部初始化副作用 |
| `01:485A` | 初始化后调用；处理错误累计后也再调用，并由 caller 返回错误 | 解码器复位、状态清理和错误恢复的实际规则 |
| `01:46F2` | 传入 `2F:A452` 或 `2F:A6BA` 的原厂函数地址 | 回调保存位置、调用时机、参数与寄存器约定 |
| `01:46D4` | 三条初始化路径均传 `16:EDB2` | 同上，不能任选一块 RAM 保存指针冒充恢复 |
| `01:4954` | 接收两个 far 输出参数，每个结果占两个 word；结果随后被当作 PCM 缓冲 far pointer 交给 `24:9B9C/9BB8` | 两通道/缓冲选择、切换条件与所有指针状态 |
| `01:49BE` | 返回输入可追加 word 数，被 PRG 续填器及消费位置判断共同使用 | 与 `3340` 写指针对应的读游标、保留量及满/空语义 |
| `01:49F8` | 在续填后调用，R0 bit0 被状态路径使用；随后读取 `3346` 错误与 `3350/3352` 消费位置，并取输出缓冲 | 实际 MP3 处理算法、状态推进、错误值和输出时序 |

`3350/3352` 是高/低 word 顺序的消费位置，caller 左移一位后写入
`51:25B8/25BA` 的 byte 位置；不要把两者按普通小端 32-bit 字段直接拼接。
`4A7A/7C`、`4A7E/80` 等输出 far pointer 也须按原厂加载顺序解释。
`16:E89C` 与 `1D:38xx` 清 `3346` 再调用处理函数；不能据此认为 3346 始终为零。

一个需要保留的原厂细节：**`16:EDB2` 本身确实只有原始 `C620 / RETS`**；
其后 `16:EDB4` 才是读取 `4A64`、渐变音量并更新 `333E` 的函数。
这不是我们添加的成功桩，不能因它是空函数就把传参目标擅改为 EDB4。

`2F:A6BA` 不只是文件续填回调：它调用 `08:2F22`，注册
`16:EA42`、`16:EC34` 及 `16:E9B2` 或 `32:97AA` 等流回调；
随后设置 `0240` 处理长度，调用 `08:385C` 并置 BIT8A.10。
模式与输出回调的选择依赖 BIT8C.7。`01:46F2` 的真实调度必须与这一状态链闭合。

### MP3 也有 ACD8/AD92 依赖

`1D:33CE..3700` 根据 `51:25CC/25CE` 和 BIT8C.7 选择分支，其中多条调用 `02:ACD8`。
`1D:3958..3A06` 的 BIT8C.7 分支先经 `08:372A` 处理缓冲，随后向 `02:AD92`
传两个 far pointer 与 `0240` word 数。这与已有 NPE 输出路径有共同服务依赖。
当前 44.1 kHz MP3 现场只证明先停在 4804，不能外推为其它输入都不会先遇到 ACD8，
也不能将 AD92 简化为 DAC 写入或普通 memcpy。
