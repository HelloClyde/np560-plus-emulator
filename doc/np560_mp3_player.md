# 原厂 MP3 播放器：功能键纠正与实际 ROM 阻断点

日期：2026-09-06。地址按 VMA03 链接地址；对应 PRG 文件偏移为地址减 `0x030000`。

## 本次结论与实现变化

此前“F1 打不开文件”首先是 Web 功能键映射错误，不是文件窗口缺少 ROM。
纠正物理矩阵映射后，原厂文件浏览器实际出现，能进入目录并选择已导入的 MP3。
选中文件后的真实阻断点是 `1D:375C → 01:4804` 缺失服务；仍不能播放音乐。
这与 NPE 当前首先触发的 `02:ACD8` 是不同入口，不能把两条路径直接视为同一实现。
后续静态核对也发现 MP3 的条件分支调用 `ACD8/AD92`；“首个缺口不同”不等于两条声音链完全独立。
同日再次实测，空列表提示、确认后的画面恢复、原厂搜索、添加及非空列表显示均通过，
见末节；添加后退出再打开播放器仍触发 4804，不能称重开和播放已完成。

修改仅在 [Web 按键映射](../scripts/web/app.js) 和
[前端回归](../scripts/tests/test_np560_web_frontend.py)，没有修改 CPU、ROM、PRG、LCD 数据或
原厂事件处理器。没有按应用切换映射，没有向 guest 队列直接写事件。

## 功能键依据

原厂播放器皮肤明确标有 `F1打开 / F2曲目 / F3设置 / F4最小化`。
原始程序 `0D:39A8` 调用 `2F:C216` 取事件，随后经过播放器分支和 `0E:992E`。

| 面板键 | 旧矩阵 / 事件 | 修正矩阵 | 正常 / 小写模式事件 | 原厂处理依据 |
| --- | --- | --- | --- | --- |
| F1 | M23 / `8B` | M60 | `E2` | `0E:A348..A7BC` 区分 E1/E2/EA；E2 分支在 A858 或 A894 调用文件选择器 `0C:0000` |
| F2 | M26 / `8C` | M52 | `E1` | `0E:A3F6` 区分曲目分支，先检查列表是否为空 |
| F3 | M15 / `8D` | M44 | `EA` | `0E:A37E` 分支把对象模式设为 2，进入选项设置 |
| F4 | M4 / `8E` | M4，保持不变 | `8E` | `0D:555A/5592`；主播放器模式 5 时退出，子页按自身模式返回 |

原始键表 `32:29B2/2A32/2AB2` 并非给这些位置分配完全相同的含义：
大写模式下，M60/M52/M44 分别是 `DD/DC/DF`，另外两表才是 `E2/E1/EA`。
前端始终发送同一物理开关，由原厂软件决定活动模式，不能在宿主强制改为 E2/E1/EA。

旧代码只凭“四个连续键值 8B..8E”推定 F1..F4，旧测试也只是重复了这一假设。
已知 [M26/8C 的原厂状态键语义](NP560_keyboard_completion_worker.md) 本就与 F2 不符。
新测试分别核对矩阵表、原厂应用分支，以及执行实际 JavaScript 配置后生成的矩阵电平。
保留原有保持、去抖、失焦释放及租约逻辑。

## 追加：MP3 输入、输出与缺失服务的边界

本节为原始 PRG 静态核对及原厂输入函数的隔离执行结果。
**没有修改 QEMU、重建 ROM 或歌曲，没有越过 `01:4804` 运行完整播放器，也没有新增播放能力。**
地址均为 VMA03；用 `dump_np560_range.py` 查看时 source 地址需加 `1D:0000`。

### 压缩输入搬运已在 PRG 中，不应再做成新 ROM 服务

原厂调用链为 `16:EC34` 文件续填 → 两块暂存区 → `16:EA42` → `16:E844`：

- `16:EC34..EDB0` 使用文件读取 `1C:CCD4`，目的区为 `50:D948` 或 `50:E948`，
  单次上限 `1000` bytes。成功路径再调用 `31:EB24`，把读到的 byte 数除以 2，
  存为 `51:2854/2856` 的 word 数；最后一块及错误路径修改 BIT89.14/.11。
  这里记录 31:EB24 的调用，不仅凭名称推定其完整转换语义。
- `16:EA42` 先调用缺失的 `01:49BE`，将 R0 与当前剩余 word 数 `51:2852` 比较，
  按较小数量调用写入函数；必要时切换暂存区。当前源 far pointer 在 `51:2858/285A`。
- **`16:E844..E896` 是完整的 84-byte 原厂写入函数**，参数为源 far pointer 和 word 数。
  它保存 DS0、DS1、R8、XM0，选择 DS0=0、XM0=`0600`，从内部 `00:3340` 取写指针，
  用 `REP; MOV [R8++],[R1++]` 搬运后写回指针，并以 R0:R1 返回推进后的源 far pointer。
  它没有调用缺失 ROM，也没有像另一条 PCM 写入函数那样更新 `4B02` 计数。
  零 word 时不搬运、不更新写指针，但仍会执行清状态位等其它指令。

因此 `01:49BE` 的返回值在这里被用作可追加的 **word 数**；不能把它伪造为固定可用空间。
`16:E906..E91A` 还将 `02FE - 返回值` 与消费位置变化比较，说明必须与解码推进共享状态。
该常量不足以单独确定读指针地址、满/空判别及所有边界规则。

### 输出及回调的已知契约

| 缺失入口 | 原厂消费者给出的约束 | 仍缺什么 |
| --- | --- | --- |
| `01:4804` | 三个已核对调用者 `1D:300A/375C`、`27:95F4` 都传六个 far pointer 与 `0300`，清栈 `001A` bytes | 六参数各自的完整含义、内部字段绑定及全部初始化副作用 |
| `01:485A` | 初始化后调用；处理错误累计后也再调用，并由 caller 返回错误 | 解码器复位、状态清理和错误恢复的实际规则 |
| `01:46F2` | 传入 `2F:A452` 或 `2F:A6BA` 的原厂函数地址 | 回调保存位置、调用时机、参数与寄存器约定 |
| `01:46D4` | 三条初始化路径均传 `16:EDB2` | 同上，不能任选一块 RAM 保存指针冒充恢复 |
| `01:4954` | 接收两个 far 输出参数，每个结果占两个 word；结果随后被当作 PCM 缓冲 far pointer 交给 `24:9B9C/9BB8` | 两通道/缓冲选择、切换条件与所有指针状态 |
| `01:49BE` | 返回输入可追加 word 数，被 PRG 续填器及消费位置判断共同使用 | 与 `3340` 写指针对应的读游标、保留量及满/空语义 |
| `01:49F8` | 在续填后调用，R0 bit0 被状态路径使用；随后读取 `3346` 错误与 `3350/3352` 消费位置，并取输出缓冲 | 实际 MP3 处理算法、状态推进、错误值和输出时序 |

`3350/3352` 是高/低 word 顺序的消费位置，caller 左移一位后写入
`51:25B8/25BA` 的 byte 位置；不要把两者按普通小端 32-bit 字段直接拼接。
`4A7A/7C`、`4A7E/80` 等输出 far pointer 也须按原厂加载顺序解释。
`16:E89C` 与 `1D:38xx` 清 `3346` 再调用处理函数；不能据此认为 3346 始终为零。

一个需要保留的原厂细节：**`16:EDB2` 本身确实只有原始 `C620 / RETS`**；
其后 `16:EDB4` 才是读取 `4A64`、渐变音量并更新 `333E` 的函数。
这不是我们添加的成功桩，不能因它是空函数就把传参目标擅改为 EDB4。

`2F:A6BA` 不只是文件续填回调：它调用 `08:2F22`，注册
`16:EA42`、`16:EC34` 及 `16:E9B2` 或 `32:97AA` 等流回调；
随后设置 `0240` 处理长度，调用 `08:385C` 并置 BIT8A.10。
模式与输出回调的选择依赖 BIT8C.7。`01:46F2` 的真实调度必须与这一状态链闭合。

### MP3 也有 ACD8/AD92 依赖

`1D:33CE..3700` 根据 `51:25CC/25CE` 和 BIT8C.7 选择分支，其中多条调用 `02:ACD8`。
`1D:3958..3A06` 的 BIT8C.7 分支先经 `08:372A` 处理缓冲，随后向 `02:AD92`
传两个 far pointer 与 `0240` word 数。这与已有 NPE 输出路径有共同服务依赖。
当前 44.1 kHz MP3 现场只证明先停在 4804，不能外推为其它输入都不会先遇到 ACD8，
也不能将 AD92 简化为 DAC 写入或普通 memcpy。

### 诊断中的无效操作与边界

- 最初 `route-player` 执行时的 `00-before` 已为应用 FF，不是先前截图的每日一句。
  沿固定“dismiss → Start → Enter → Enter”序列实际进入过应用 17，又回桌面，
  随后的 `route-f2` 不是播放器 F2 验证。保留原记录，不按文件标签改称成功。
- 第二次进入播放器时，应用状态先变为 4E，但 LCD 仍是娱乐菜单；再运行后才出现皮肤。
  状态/ACK 与页面就绪不是同一件事。搜索页同样先显示进行中，随后才显示结果。
- 最初截图目录未建立导致采集失败；创建目录后采集同一实例，没有因此重启。
  搜索等待命令尚在运行时一次图像读取也过早；随后等同一命令正常完成再检查其真实结果。
- 本轮没有复现休眠。既有 [阿诺关屏记录](np560_npe_arno_compatibility.md) 已证明某场景下
  M61/上键可唤醒，不能仅由 Enter 或 Start 无响应推定整个唤醒路径缺失；
  真机电源接线、CPU 低功耗及完整现场恢复仍未完成。

下一步仍需恢复媒体初始化/解码，并在同一版本中验证添加后的重开、原生持久化和实际播放。
