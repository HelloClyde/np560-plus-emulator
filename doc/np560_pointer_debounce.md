# Web 点按漏键：原厂去抖门槛与传输时序

日期：2026-09-06。属于 M1 输入可用性，不是 NPE ROM 恢复，也不关闭全部菜单故障。

## 已复现的现象

同一开发核心、严格 ROM 和原厂文件 API 导入 NAND，冷启动后只施加物理矩阵电平。
右键 M29/81、左键 M45/80；每次按下后等待 120 ms，再释放，不在按住期间抓取完整诊断。

`tmp/np560-native-short-press-20260906-v2/report.json` 中，前 16 次操作均只有一次映射、
一次前台消费，顶栏与对应原包资源一致。第 17 次右键实际保持约 122.66 ms：

- candidate、map、foreground acknowledgement 增量全部为 0；
- 最后一次活动 F160 读取来自 `27:E53E` 的预扫描，drive=3F00、input=00F7；
- 完整矩阵 scanner 累计仍为 16，未进入第 17 次解码；
- 无 ROM_MISSING、UNSUPPORTED、INVALID_CONTROL，画面仍是完整的“学习”页。

这次失败是一次物理点按未通过 guest 去抖，不是图形损坏或生成了错误菜单资源。
它与旧菜单记录中的“长电平期间多消费一次”不同，不能互相冒充首因。

首轮 `v1` 误用了旧注释中的 M20/85，将逗号当作右键；该结果不作为菜单缺陷证据。
修正后的脚本同时核对当前原厂键表中 M29=81、M45=80，保留原始失败记录，不改 guest 使其通过。

## 原厂字节支持的时序

1. 原厂配置 TBC=8009：64 Hz，见 [时基](np560_timebase.md)。
2. `08:40EC` 增加 near 0490；`08:4112..4118` 检查至少累计 4 tick。
   回调 guard 允许时，`08:41BA..41E0` 保存累计值、清零并转入 `27:E528`。
   因此空闲时键盘任务标称 16 Hz，即 62.5 ms 一次；忙碌或 guard 占用可能推迟。
3. `27:E546..E55A` 在无键时设置 51:2A94=1、清字节 51:2A8C。
   有键时 `27:E592` 调用 `31:BE70`，只有返回非零才进入 `2E:5F28`。
4. `31:BE70` 每次增加 2A8C；首次按下走 `31:BEDC..BF08`，要求计数至少为 2 才返回 1。
   从任意相位按下，要等两次回调，标称等待范围约 62.5..125 ms。

所以 120 ms 并非一个能够覆盖原厂去抖相位的鼠标点按时长。这个推导来自原厂指令，
不是为了让截图通过而调整 TBC、去抖计数或 ROM 返回值。

原始 PRG 按 VMA03（文件偏移=地址减 030000）核对：

| 片段，末地址不含 | 字节数 | SHA-256 |
| --- | ---: | --- |
| 08:40D0..427A | 426 | a89fcc6e16931f4b0540596187743f7f02cbbba5e1a6f2c0547436fc5fea4e4f |
| 27:E528..E600 | 216 | 745b15677693f257c9bfe91535b0a53cd0a3c2627ec2a82d1907caeffbc65a21 |
| 31:BE70..BF0E | 158 | 1da1bfb0ad3a21f2b5e1d9857b7c2ee4a954b8150143636ef6a60a40275c0422 |

严格 ROM 中 08:40D0 的这 426 字节与 PRG 完全一致；后两段位于 PRG 地址范围。

## 修复范围

`scripts/web/app.js` 将鼠标/触屏点按的最短物理闭合时间从 120 改为 150 ms。
150 是前端点按策略，包含对标称 125 ms 的余量，不是声称真机使用了 150 ms 常量。
不改 PC 键盘的真实按下/释放，不限制长按，不伪造事件；连发仍由原厂代码产生。

同时修正计时起点：以前从 pointerdown 开始倒计时，若按下请求在 HTTP/QMP 队列中延迟，
真正施加到 QEMU 的电平可能远短于标称时长。现在等待该按下请求完成，再开始最短接触计时。
松开事件可提前到达，但不能排队成“按下刚到 QEMU，随即释放”。

- 快速重按取消旧释放，并用独立 promise 身份防止旧异步回调释放新按下。
- 失焦、隐藏、页面退出或连接失败的全释放绕过最短时间，不让延迟确认重新恢复按住状态。
- 已经超过最短时间的正常长按在松开时立即释放，不额外增加 150 ms。

这里没有按游戏或 ROM 地址特判，也没有强制“一次点按必须映射一次”来绕过真实扫描。
忙碌 guest、暂停、其它页面持有输入租约等情形仍可能影响响应，不能据此宣称全部输入已完成。
