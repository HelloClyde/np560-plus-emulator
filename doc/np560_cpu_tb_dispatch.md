# CPU 翻译块连接与音频调度

日期：2026-09-08。当前功能主线仍是 M2 音频；未完成整机或正常音乐播放验收。

## 已修改的执行路径

旧 DMCU helper 只返回“可以继续当前 TB / 退出”。普通跳转、重复回跳与确实需要重新
仲裁中断的状态改变共用退出路径；顺序执行到 TB 尾部也总是退出到宿主 `cpu_exec`。

当前区分三个**宿主执行结果**，不是新增 guest 寄存器或改变 CPU 指令：

- `DMCU_EXEC_EXIT`：数据映射改变、CRIT 保护结束、IRQ 状态改变、旧 native-tick 等仍返回
  `cpu_exec`；没有跳过软件中断、DTU 或中断重新仲裁。
- `DMCU_EXEC_NEXT`：可继续当前 TB；到尾部可在同页使用 QEMU 标准 `goto_tb`。
- `DMCU_EXEC_LOOKUP`：普通跳转/调用/返回或重复回跳，通过标准 `lookup_and_goto_ptr`
  查询实际 guest PC 对应的新 TB，不继续执行旧 TB 内的顺序指令。

MMIO 和可执行内存写仍在当前 TB 最后一条，代码失效仍走 QEMU 通用机制；
后继 TB 的入口保留异步退出请求和 icount 检查。GDB 单步的 `CF_NO_GOTO_*` 限制由标准
接口处理。宽指令从 `CS:FFFE` 取扩展字时，线性 TB 长度不含回绕的扩展字，
因此必须按 helper 已提交的实际 PC 查找，不使用线性长度推断目标。

没有改变 PLL、音频请求频率、IRQ 优先级、原厂 PCM 缓冲/ready 位，也未新增 HLE 入口。
此变更与上一轮默认关闭的精简观察开关独立，后者默认值保持不变。

## 下一层：虚拟时间与宿主调度

当前 DMCU 普通运行采用 QEMU 的非 icount TCG 路径，虚拟时间与实际宿主执行耗时相关。
本地 `accel/tcg/tcg-accel-ops-rr.c` 可见，启用 icount 时 CPU 根据下一个设备期限分配
指令预算，并在 vCPU 循环处理到期定时器；普通模式由 I/O 线程产生定时事件。
此前原厂续填函数普通模式约数十微秒、固定 icount=5 为 608 ns 的差异须在此区分。
它不是查到 NP560 实际每条指令周期数的证据。

已有本地专利文本 d205 区分内部/外部取指的 A/B 管线化周期，操作码表也含
1、1或2、4/5、2～3 等值；不是完全没有周期资料。但流水线冲突、总线等待状态、
当前 SoC 的内外存映射与 PLL 分频尚未形成统一 CPU 周期实现，不能把每指令固定
32 ns 或宿主自适应比例直接称作依据表格实现的真机周期。

实验播放器探针现在接受 `--icount-shift auto`，使用 QEMU 自身的自适应指令调度，
不修改设备采样率或 PCM。这只是分离宿主调度影响的对照，不是精确 CPU/PLL 周期模型；
QEMU 会随宿主负载改变指令到时间的比例，不能将其宣布为真机时序。
普通 Web 的启动参数未变。完整播放器须分别复核实际音高、空请求、双声道和曲目交接，
不能以固定短缓冲通过替代整机结果。

## 整机结果：块连接未修好音频，auto 不采用

两轮均使用最终 `d1416613…`、同一原厂 PRG/UPD/tone NAND、HLE v4 ROM
`7d9dc59e…`、精简观察、物理选曲、12 次观察和 60 秒墙钟录音上限，串行执行。
没有 GDB、运行时 RAM 注入或 NAND 保存；两轮进程均已退出 0，用户 Web 未替换。

- 实际 DAC 1369221 帧 / 28.525438 秒，PCM SHA256

### 自适应指令时钟（只作对照，拒绝作为当前播放方案）

`tmp/np560-mp3-tb-linked-auto-20260908-v1/report.json` 和 `delivery-analysis-v2.json`：

- HLE 第一次观察起至第 12 次始终为 19 帧 / 38 granule，输入空间查询继续到 107541 次。
  没有解码/查询/复制失败、缺失 ROM、unsupported 或坏控制转移，但这并不代表正常工作。
- 实际 DAC 918935 帧 / 19.144479 秒；从第 2.181625 秒起的 `(448,448)` 保持
  16.962854 秒直到录音末尾，没有持续输出新 PCM。PCM SHA256
  `aa7fb663bdec0ca5cc04d31290a5cf090bda1dfd382ddc138dd5bdc03585c431`。
- 第 10 秒窗口仍约 44086.06 Hz 请求，但双路写入均为 0，各有 44312 次空请求。
- 第 8 次 CPU 快照有 303470 次中断进入；不能仅凭有限观察断言永久死锁，
  但**本轮连续播放明确失败**。
- 仅余开始阶段的 64 个 refill 事件，左路总时差中位数 47.104 µs；不是长时间稳态。
  不能把这个较小中位数或仅 43 个左右不同帧数算作改进，大部分录音已经是单值。
- 报告 `passed=true` 表示探针完成选曲、收集和关闭，不表示播放通过；
  两轮的 `playback_verified` 均仍为 false。

分析器原先把恒定 DAC 的全零交流频谱 `argmax` 误报为第一个 FFT bin（约 1 Hz）。
现将这类 `peak_hz` 明确置为 null，并增加 `ac_rms=0`；原始录音与第一次分析保留不动。
在上述录音的 15 个完整单值窗口、双声道逐项核对：RMS=448、AC RMS=0、无新写入、
无虚构频率；结果另存 `delivery-analysis-v2.json`，不是重采样或改声音数据。

结论：普通宿主时钟的续填延迟不能仅靠小幅提速解决；自适应指令比例也不能取代
硬件执行时间模型。下一步基于已有 A/B 周期表、PLL/CLKCON 和外部等待状态资料，
建立可追溯的 CPU/设备相对时间；先区分行为正确与宿主实时速度，再针对实际热点加速。
尚不采用 auto 为 Web 默认，也不扩大 HLE 去强制原厂 ready/EN、提前中断或补齐 PCM。

后续发现本节旧 icount 执行路径有中途退出多计未执行尾部的问题，已改为 icount
单指令块；普通模式的连接不变。精确反例与同构建 auto/fixed 播放器重试见
[指令计数修复](np560_icount_accounting.md)。旧实验记录保留为历史观测，
不能把其固定指令时间换算直接当作正确的指令数，更不能当成真机周期。
