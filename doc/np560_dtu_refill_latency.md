# 音频缓冲完成中断与续填延迟

记录：2026-09-08。当前音频仍未验收；本项没有替换用户 Web。

## 已取得的证据

MP3 HLE 输出 PCM 已通过数值对照，但原厂播放器的实际 DAC 主峰仍低于约 440 Hz。
本次不改采样率、不补 ready/EOF/EN、不改变 IRQ 优先级，直接记录：

1. DTU 搬完最后一个样本、COUNT 变零的虚拟时间。
2. CPU 实际接受对应 ICR 中断的虚拟时间。
3. guest 将该 DTUC 从零改为非零的时间、写入 PC 和 COUNT。

原厂 source 16 的向量跳到 `08:39B4`（RETI）；source 17 跳到 `08:3B48`，
经过 `24:98FC` 装填两路。实际 576 样本续填写入点是 `24:99BC/99C0`。
所以第二段“接受→重装”是时间差，**不能一概称作同一个 ISR 的纯执行耗时**；
右路可先接受无操作 ISR，再由左路处理程序一起重装。

## 默认关闭的记录

`dtu-refill-trace` QOM bool 显式开启；`dtu-refill-state` 返回只读 JSON。
每通道保留未重装的完成时点，最近 64 个完成→重装事件，以及每 source 的 CPU 进入数。
记录完成时 IE/PSR/CRIT/IGNDS、完成/受理/重装 PC，重装时 COUNT 及期间中断进入数。
数据是诊断信息，不是新增硬件 latch，不参与请求仲裁、DTU 搬运或缓冲选择。

默认关闭；原有设备复位清空 env 中记录。脚本在自有暂停实例上显式开启，
`probe_np560_mp3_player_heap.py --observe-dtu-refill` 每次既有 codec 快照额外读一次，
不用 GDB/写入 guest 内存，也不逐样本轮询。短记录会覆盖旧数据，不是完整无损追踪。
分析器按 seq 去重，分别列全观察数量和统计筛选：accepted、COUNT=576、总时差<20 ms。
此筛选排除较长曲目交接，但不能证明所有留下的事件都是稳态；保留原始事件供核对。

## 已实施的通用开销修正

DS0/DS1 和 IGNDS 只影响数据地址映射；此前三处均 `tlb_flush()`，同时失效指令映射。
现改成 `tlb_flush_by_mmuidx(..., 1 << MMU_DATA_IDX)`：数据映射仍及时失效，
指令映射不因数据 bank 切换被清空。翻译块结束边界保留；代码写入、覆盖装载、
真实的全局缓存失效仍走原逻辑，不能把本修改推广为取消所有 TLB/TB 失效。
QEMU 的 partial TLB flush 仍清跳转缓存，本次没有修改 QEMU 通用缓存实现。

新构建 `d9f4992beb62e355c0fd65e3221aa265e6789bcd9daec102526352e115341aea`。
IGNDS/中断 10 项、AGU 16 项、代码一致性及原厂重定位中断 18 项通过，
分别在 `tmp/np560-data-tlb-ignds-20260908-v1`、`-agu-...`、`-coherence-...`。
保持真实的数据/指令语义是本项边界，不能仅凭该优化宣称音频已修复。
