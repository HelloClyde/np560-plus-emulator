# NP560+ 右下角时钟残影的最小边界

## 2026-09-01 v838 二十次变化最终验收

正式长跑已在隔离 v838 实例完成 20/20 次真实分钟变化，连续文本为
`00:16..00:35`，总观察时间 1216.985 秒，相邻变化间隔 61.485..62.984 秒；覆盖了
`00:19→00:20` 和 `00:29→00:30` 两个多位数字边界。没有 transient trigger，20/20
触发帧都与同步 pause 后的 coherent capture 完全相同。

每次变化均在完整 45×20 时钟矩形端点同时观察到旧像素清除和新像素绘制；两个多位边界
也不例外。`00:19→00:20` 的最终 LCD 时钟区域清除 8 个旧像素、绘制 14 个新像素，
`00:29→00:30` 同样取得非零清除/绘制。20/20 的 guest back↔front 全屏 mismatch 为 0，
归一化 ST7529 GRAM↔最终 LCD 全屏 mismatch 也为 0，证明可直接比较的各层没有分叉，
Web 没有清除或修补画面。

四阶段 `CLOCK_RASTER_PIPELINE` 中，19/20 次被严格分类为
`uniform_background_observed_before_text_draw`：`s2` 文字调用前前景像素为 0 且只含
背景灰阶 `0008`，`s3` 保留背景并加入前景 `8008`。首条 `00:16` 因基线附近采样区含
多个非前景灰阶而按收紧规则保持 `inconclusive`，但其完整矩形端点仍有 6 个旧像素清除、
9 个新像素绘制，back/front 与 GRAM/LCD 均为 0 mismatch；没有任何一条被分类为
`foreground_survived_background_phase_before_transparent_draw`。两个多位边界都属于上述
19 条严格通过样本。

因此，用户在旧 v656 截图中报告的右下角叠字在当前 v838 权威基线上已经关闭：原厂 guest
路径会在透明文字调用前恢复背景，随后正常绘制新时间，最终 LCD 连续 20 次及两个十位边界
均无旧字形残留。不需要也禁止新增 ROM 清除服务、Web 擦除或 LCD 后处理。

证据目录为 `tmp/v838-clock-20-v2`，共 274 个文件、12,047,851 bytes；manifest
SHA-256 为 `F16E57E96B363653CA8E3BD660D4508B9635640785BB71E25FC95448CD053781`，最终
`20-lcd.png` SHA-256 为
`91B264394EE7BD55A295218B8AAE979EA6E57915F81C0439C382AE40756BA538`。当前时钟监控
定向测试 21/21 及 `py_compile` 均通过。

## 2026-08-30 v751 长跑权威结论

隔离端口 8795 的只读长跑已经越过 30 对门槛：`RESOURCE_PAIR_RELEASE` 最终为
`CALLS=65 ACTIVE=0`。固定 64 项 trace 中完整保留 `#2/#3` 至 `#62/#63` 共 31 对相邻
footer/clock 调用，31/31 均满足以下原厂生命周期契约：

- caller 顺序为 `27:58E4 → 31:590E`，共同释放入口为 `2E:0AF6`；
- `PRE8/CALL8/ENTRY8/RET8/CALL3/ENTRY3/RET3/EXIT` 八阶段完整，全阶段 `irq0`；
- 同一对正常复用 handle `0003`，`mask1=1`；
- node 从 `w8003` 去 pin 为 `w0003`，随后移除为 `none/m0`；
- bitmap 从 `f000` 变为 `e000`，`0x1000` 位被清除；
- 每个完整周期最终都回到 `ACTIVE=0`。首个 clock-only `#1/h0002` 也完整释放。

因此，重复的 `h0003` 是释放后的 handle 复用，不是节点残留、pin 泄漏或 bitmap 未清。
`CLOCK_RASTER_PIPELINE COUNT=33`，保留的序号 26..33 共 8/8 有效，格式化文本连续为
`00:26..00:33`。这排除了“当前 v751 因 footer/clock 临时资源逐次泄漏而产生叠字”的候选，
但还没有完成像素层验收：下一步必须连续捕获至少 20 次真实时间变化，并覆盖一次多位数字
边界，同时比较 guest back buffer、ST7529 GRAM 和最终 gray5 的时间矩形；只有这样才能
确定用户截图中的旧字形究竟首次出现在哪一层。

证据：`tmp/np560-v751-resource-pair-release-8795-summary.json`，大小 5390 bytes，SHA-256
`0361C7783962DCFE6126BF23D337C20E5022945F4F734C3368EB645CB2C5994A`。定向源码契约测试
5/5 通过；8795 已停止，用户的 8778 未被触碰。

同一轮还在 v752/8796 上启动了三层像素监测。90 秒窗口只取得一次真实变化
`00:08 → 00:09`，没有达到请求的 20 次，所以只能作为局部证据：时间矩形内恰有 3 个像素
变化，LCD 和 GRAM 的变化数均为 3；guest front buffer 也为 3。最终 LCD 同时包含 1 个
旧像素清除和 2 个新像素绘制，字形从 8 干净变为 9，没有观察到直接叠加。证据在
`tmp/np560-v752-clock-20-changes-8796/manifest.json`，SHA-256
`48DB2B0C00288D37C1AC374F343733DE503A99FB09166FEDCCC4E13571CB2DDE`。监控脚本随后已经
把同一次 pause 下的 guest back `50:0000`、front `50:3840`、240×160 raw GRAM 和
240×120 LCD 统一采集：native 逻辑行使用 physical `119-y`，COM=1 GRAM 使用
`139-y`，post-INV 的 draw/clear 极性也已纠正。back↔front 与 GRAM↔LCD 是已验证比较；
native gray4 到 LCD post-INV gray5 的横向/灰阶映射仍显式标为 unavailable，不作猜测。
当时的定向测试为 14/14；下述判据收紧后当前为 21/21。v752 离线样本归一后
GRAM↔LCD 全屏 mismatch 为 0。

90 秒不是“20 次变化测试失败”，而是采样预算从一开始就不足：当前可见时间约每 60 秒
变化一次，90 秒最多只应期待 1–2 次。若要取得 20 次变化，按最佳起始相位也至少需要
1140 秒；覆盖一个完整相位的预算是 1200 秒。因此下一次正式长跑按约 20 分钟安排，不能再
用 90 秒超时结果评价 20 次门槛。

四阶段只读 trace 已给出更直接的 guest 写序证据。v752 保留的 8 个完整周期中，`s2`
（文字调用前）的 native back-buffer 40×8 样区均为 hash `3f9f5a05`、前景像素 0、
`levels=0008`，即只含灰阶 3；`s3`（透明文字调用后）则为前景像素大于 0、
`levels=8008`，即保留灰阶 3 并新增灰阶 15。这支持“该样区先恢复统一背景，再透明绘字”，
也说明当前 v752 样本不支持在同一位置补一个新的清除 ROM 服务。它仍只覆盖 40×8 样区，
不能替代完整 45×20 时间矩形、三层同步、20 次变化和多位边界验收。

监控器的判据也已收紧：`s2` 仅“前景像素为 0”不再算清除证据；还必须只有一个非前景
灰阶，并且 `s3` 必须保留该背景灰阶、同时新增精确前景灰阶。新增的反例测试固定了
“前景计数为 0、但存在多个灰阶”必须判为 inconclusive。当前定向测试为 21/21，
`py_compile` 和 `diff --check` 通过。

由于真实时间采样仍只有一次，不能据此将用户报告的残影标记为已修复；后续长跑必须补齐
20 次和多位边界。验收同时要求时间矩形外不变化，并区分“背景恢复后重新绘制”与“透明
字形直接叠加”，Web 不得参与清除。

## v750 初始边界与历史结论

v750 已推翻“根时钟调用自身的释放 worker 缺 ROM 或未执行”这一旧判断。最新隔离实例中，
`31:590E -> 2E:0AF6` 已进入 `2D:CAA6 -> 18:66EE` 完成 44×15 背景恢复；随后才由
`31:596E -> 28:1F08 -> 28:FD38 -> 18:6454` 以 `MODE=1` 透明模式绘制新时间。
三次被完整跟踪的时钟资源调用均执行以下闭环：

- `30:8B26` 清除 pin；
- `30:3A56` 调用 `31:8ABC`，且 `mask1=1`；
- registry 节点从 pinned 到 unpinned，再被移除；
- bitmap 对应位被清除，最后 `ACTIVE=0`。

v656 与 v750 在 `2E:0AF6`、`30:8B26`、`30:3A56`、`31:8ABC`、`25:77DA`
五个命名函数上的 live bytes 和 manifest 映射相同且均为 exact。因此目前没有证据支持在
这些函数上补 ROM、HLE、CPU 指令或 Web 擦除逻辑。

旧 v656 的确定异常仍然有效，但范围要改写：资源句柄不是由时钟单独泄漏，而是从第 4 次起
严格成对出现——`27:58E4 -> 2E:0AF6` 的 240×17 资源先取得 handle，紧随其后的
`31:590E -> 2E:0AF6` 时钟资源取得同一个 handle；两者一直递增到 `h0019` 后一起失败。
所以当前首个未证明边界是这对调用者的共同对象生命周期，尤其是前置 `27:58E4`，而不是
时钟 release worker 本身。

只读 `RESOURCE_PAIR_RELEASE` 观察器已经实现：它同时记录两个 caller 的 handle、
`30:8B26` 前后 node word、`30:3A56 -> 31:8ABC` mask 与 bitmap，容量为 64 条。
v750 隔离冷启动的首次相邻 pair 为 `#2 27:58E4 h0003` 和 `#3 31:590E h0003`；两者均由
`node w8003` 变为 `w0003` 后移除，`mask1=1`，bitmap 从 `f000` 清为 `e000`，最终
`ACTIVE=0`。这证明同号 handle 是前一调用释放后的正常重用，不是遗留 pinned handle。

该初始样本后来增长到 5 次调用且仍为 `ACTIVE=0`。上方 v751 长跑已完成 31 对门槛并全部
回到基线，所以共同资源生命周期审计已经关闭；剩余工作是连续至少 20 次真实时间变化及
多位数字边界的三层像素验收。

## v656 历史失败证据

旧 v656 实例中，临时资源对象分配器 `25:77DA` 最终返回零，代码在 `2E:0C0A` 转向退出，
没有进入背景位图写入；时钟文字仍以 `MODE=1` 透明模式绘制，因此旧像素累积为实心块。
以下证据用于说明该旧症状，不得直接外推为 v750 当前状态。

## 历史证据明细

### 1. v656 资源路径先失败

8778 旧实例的只读 `ROOT_RESOURCE_TRACE` 保留了冷启动后前 64 次资源调用。

- 前 49 次调用走完 `st4ff`。`st4ff` 包含分配成功、对象解析、资源拷贝、
  `18:66EE` 返回和函数退出等所有阶段。
- 时钟调用的临时 handle 从 `h0002` 逐步到 `h0019`，对象地址从
  `51:4A92` 逐步到 `52:2F22`。
- 第 50 次资源调用开始返回 `h0000/obj0000:0000/st60f`。
  第 51 次正是 `31:590E` 的时钟背景，也是同样的失败。
- `st60f` 包含 `2E:0C0A` 的 allocation-zero 分支 (`0x200`)，但不包含
  `2E:0C0E` (`0x10`)、`2E:0C22` (`0x20`)、`2E:0C46` (`0x40`) 和
  `2E:0C62` (`0x80`)。因此失败时没有对象、没有位图拷贝，也没有进入最终光栅器。

关键样本：

```text
#49/31:590e/.../h0019/obj0052:2f22/st4ff
#50/27:58e4/.../h0000/obj0000:0000/st60f
#51/31:590e/.../h0000/obj0000:0000/st60f
```

这只证明 v656 的“临时资源对象生命周期/分配状态最终不能再提供对象”。后续 v750
`CLOCK_RESOURCE_RELEASE` 已证明时钟调用自己的 release worker 完整闭环；旧现象应改由
`27:58E4` 与 `31:590E` 的成对生命周期解释和复验。

### 2. 时间文本和字形路径正常

- `CLOCK_FORMAT_RETURN_TRACE` 在出现残影后仍给出正确 ASCII，例如
  `20 30 37 3A 34 32 00`，即 `" 07:42\0"`。
- `FONT_COPY_TRACE` 显示字形源 `3B:81xx` 被拷贝到内部字形缓存 `00:4844`；
  源和缓存字节均为有效的 8 行字形。
- `FONT_BLIT_TRACE` 显示字符、位置和步进正确：`x=188,196,204,212,220,228`，
  `y=107`，字符是空格、数字和冒号。
- `NATIVE_FONT_BLIT` 明确记录 `PTR=00500000` 和 `MODE=1`。
- `18:6454` 的精确代码在 `18:64DC..651A` 表明，当字形位为零且
  `4BB0 == 1` 时跳过背景写入；实际像素存储点是 `18:6558`。

### 3. 损坏在 Web/LCD 之前已经存在

对 8778 的只读抓帧显示，残影在原始 `50:0000` 后缓冲中已经存在。
`NATIVE_REFRESH` 同时显示 `50:0000 -> 50:3840` 复制前后的非零计数和 FNV 一致，
没有 mismatch。ST7529 和最终 LCD 帧只是忠实显示已损坏的前缓冲。

## 新增的只读边界诊断

QEMU 诊断中新增了有界的 `CLOCK_RASTER_PIPELINE` 行，最多保留 8 个时钟周期：

- `s0`: `31:590E` 调用背景资源之前。
- `s1`: `31:5912` 背景资源返回之后。
- `s2`: `31:596E` 文本渲染之前。
- `s3`: `31:5972` 文本渲染返回之后。

每个阶段只读取样 `50:0000` 和 `50:3840` 的
`x=196..235, y=107..114`，记录 FNV hash、完全前景像素数、灰度级位图、
活动 framebuffer 指针、字形模式和掩码。`s2` 还记录 8 个文本字节。
实现不写 guest 寄存器、内存、LCD 状态或 Web 帧。

后续 v750 隔离实例已经进入桌面并取得有效阶段记录。第二次时钟调用的 back-buffer hash
依次为 `3f9f5a05 → f01b4d80 → 25cc0ce4`：背景资源确实先改变区域，文字随后再次改变区域；
同时 release observer 为 0 active。第 1/3 次出现 `s0 == s1` 只表示该次背景像素与区域
原内容相同，不能在 `stage=4ff` 且释放闭合时解释成跳过背景。旧 8778 使用旧二进制和
旧 v656 ROM，只保留作历史症状对照，不能再代表 v750 当前行为。
