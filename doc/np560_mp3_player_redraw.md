原厂尺寸函数 source `50:1E7A` / runtime `33:1E7A` 计算
`(((width+3)>>2)<<1)*height+10`。它申请的对象不是简单的 2-bit 裸屏缓冲：
240×120 需要 **14410** 字节，大于当前最大空闲 **6702** 字节。
`scripts/tests/test_np560_bitmap_allocation_size.py` 执行原始 44 字节叶函数，
验证 240×120→14410、5×6→34、4×1→12、1×1→12，四项通过。
诊断将无绝对引用的叶函数原样放在 20:0100，避免生产代码别名；第一次直接用
33:1E7A 的极简 fixture 未正确提供别名来源，超时跑入零区，不作为尺寸证据。

v4 曾仍得到 COUNT=0：观察器只处理 SCALL，但播放器经 `32:13E8` 的 SJMP
进入资源入口。v5 增加默认关闭的 `resource-trace-all` 跳转入口观察，按既有
远返回地址取栈上四参数；普通调用、跳转、关闭/复位三项隔离测试通过。
这没有更改客机调用语义。完整观察模式下结果不作为实时速度证据。

资源请求尺寸或分配失败的证明。须捕获原厂 `2E:0AF6` 资源路径的尺寸、申请返回
和阶段，再决定是否调整 HLE 专用工作区。不能用扩大虚构 SRAM 或强制清屏代替。

一个候选方案是 HLE 专用 lease 不再预留不被使用的原生 synthesis history，
