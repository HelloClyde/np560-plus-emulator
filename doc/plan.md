## 1. 目标与原则

**以 QEMU 忠实实现 NP560+ 整机，通过 Web 操作原厂系统，完整使用原厂应用和游玩 NPE 游戏。**

交付的是同一套可安装、可重建、可长期使用的虚拟设备，不是菜单演示、单款游戏补丁或自动化测试平台。
NPE 是优先打通的核心用途，但不是整机实现的范围上限。

“完美实现”需要同时满足：

- **硬件正确：** CPU 指令、寻址、DSP、内存、异常/中断、时钟与外设行为完整；不只覆盖已经运行过的代码。
- **系统完整：** 原厂系统正常启动，菜单、窗口、输入、显示、声音、文件及应用服务实际工作。
- **游戏完整：** 从“开始 → 娱乐 → 游戏世界”进入真实 NPE，正常游玩、发声、保存、退出，重启后继续。
- **资料可靠：** 原生文件与存档持久保存，内容可交换，升级、关机、恢复不会破坏资料。
- **独立可用：** 普通使用不需要调试器、运行中 RAM 注入、离线修 NAND 或切换实验专用构建。

没有真机和完整原厂 mask-ROM 转储，当前不能证明逐字节、逐周期等同真机。
目标不因此缩小：能恢复的继续恢复，无法核对的明确标为未知；不能把行为兼容宣布为真机完全一致。

## 2. 架构不能偏离

| 层 | 应实现什么 | 不采用的替代方式 |
| --- | --- | --- |
| QEMU CPU / SoC | 指令、总线、内存、SFR、DSP、异常、中断、时钟、传输 | 按游戏名或程序地址强改执行结果 |
| resident ROM | 有原厂字节的继续执行；01/02 缺失服务允许按 ABI 实现 HLE，包含状态与副作用 | 未知入口一律成功、假 ready、把 HLE 宣称为原厂 ROM |
| 外设 | LCD、物理键盘、音频、NAND/ECC、RTC、电源及本机实际接口 | 固定 ready、忽略状态变化、按某张截图修数据 |
| Web | 显示实际 LCD，传递物理输入，播放设备音频，管理虚拟设备 | 补画菜单、擦除残影、修改选中项或游戏状态 |

ROM 的原厂字节、依据调用契约重建的 guest 代码、HLE 服务、临时桩和未知入口必须区分。
PRG 中有可复用代码，不等于升级包包含完整 mask ROM；重建镜像也不是取得了原厂 ROM 转储。
HLE 是被允许的软件服务实现层，不用于掩盖通用 CPU、总线或外设错误。
仅对已登记的 01/02 缺失服务生效；不能顺手启用旧诊断菜单、逻辑键注入或改写其它程序执行结果。

### 当前开工顺序

1. **可复现的使用故障优先。** 当前崩溃、花屏、输入失效或资料损坏，先定位所属层并修复通用实现。
   已修好的旧故障不反复重做；没有现场证据时不预设又是 ROM 缺失。
2. **下一功能主攻是 M2 原厂声音。** 复用已有原始内容、调用记录和输出链，补缺失的声音服务，
   不再把建设外围诊断平台当作音频进展。
   MP3 已区分“Web 功能键错误”和“选入歌曲后的 ROM 初始化缺口”；前者已修正，
   接下来沿实际媒体调用链恢复服务，不将所有无声问题笼统归为 NPE codec。
   原厂 MP3 输入搬运器已单独验证；剩余重点是解码状态、处理算法及共享输出服务，
   不重复实现 PRG 已有搬运代码，也不以缓冲测试通过代替音乐播放完成。
   **2026-09-07 最新路线：MP3 与 NPE 专有编码分开推进，01/02 缺失服务允许 HLE。**
   MP3 不再继续投入逐指令移植和优化标准算法，优先将成熟宿主解码库接到缺失 ROM 服务，
   适配原厂播放器的调用与状态契约；已有原生解码实现保留作对照和可选路径。
   HLE 明确标注来源和范围，不称作找回原厂字节，也不宣称逐周期等同真机。
   NPE 格式 13 与 ESAC-4 的来源线索独立保留，不能直接用 MP3 解码替代。
3. **当前保持 M2 优先，不自行转去装备或菜单检查。** 2026-09-07 用户再次明确音频优先；
   暂停与声音无直接依赖的 M3 实验。只有直接阻断音频的 CPU、ROM 或外设问题插入处理。
   实验原生 ROM 已接入原厂帧处理接口，并在完整播放器内实际产出 PCM，仍不计为可播放。
   启动音频传输时的定时器并发缺陷已修复并越过原崩溃窗口；当前以已接入的 HLE 排查连续双声道请求/缓冲交接和停止/退出释放；
   不再重复已完成的头解析、缓冲常量检查或单独 PCM 核心建设。
   对升级目录的 MPEG 解码表数值筛查没有找到可直接恢复的实现；具体覆盖和未覆盖表示
   已记入 MP3 契约文档，不把阴性扫描推成“整个包绝无算法”，也不反复跑同一筛查。
   NPE 的下一来源方向已收窄到历史 ESAC-4 实现：官方十档码率与固件 9..18 完整匹配，
   但取得的演示 WAV 是 PCM，没有取得解码器；仍以原始 NPE 实际解码发声为交付条件。
   随后从 CYBIT 历史试用包取得旧版 CyberVoice 播放器机器码，但其解码路径是固定 5 kbps，
   并非已取得 ESAC-4 实现；不把该播放器另做宿主播放或错误接入 guest 充当完成。
   已取得并验证 NoahMediaMaker 压缩包，其主程序含 NP560+ 机型标识和音频库；
   AudioCtl、Compile 已静态解包，NP560+ 分组 2 的声音写入阶段绕过 Sonix/Sitronix 编码器，
   目前核对到的是输入资源拼接，并非 ESAC 实现；不把解包计为解码恢复，
   不继续拆其他机型库冒充进展。调用地址与边界见 [音频路径记录](np560_noahmedia_audio_path.md)。
   原包、哈希与已知边界见 [来源记录](sources/noahmediamaker-2007-20260907/README.md)。
   M3 的技能、装备、完整战斗、后续剧情及保存仍全部保留，声音之后继续，不缩小整机目标。
4. **扩展 M4、M5。** 逐项完成原厂应用和设备功能；若它们是当前声音或游戏的依赖，提前实现。
5. **交付便利功能随后补齐。** 整机快照、管理界面等保留在范围内，但除非解决当前故障，
   不优先于声音、原生存档和核心设备功能。快照不替代原厂游戏存档。

### M2 的具体执行路线：先推进 MP3，保留完整声音目标

执行方向：成熟 MP3 解码器可以作为 **01/02 缺失 ROM 服务的宿主 HLE 后端**。
逆向集中在原厂调用契约、工作区、缓冲、返回值、回调和设备连接，不再要求算法本身由 DMCU 执行。
当前主线保持音频，不自行切回菜单修饰或通用工具建设。
本机播放 MP3 需要解码，不需要重新发明编码器。公开实现提供算法依据，
原厂 ABI 和硬件时序仍要适配；“成熟 MP3 算法”与“已经能在整机中实时播放”分别验收。

**HLE 接入时的记录（历史，最新进展见下）：** minimp3 后端已加入 QEMU，独立开关 `rom-mp3-hle-base` 只接受
严格 skeleton 中已登记、带版本标记的 01/02 服务门，不启用旧 `rom-hle`/`hle-ui`。
三组 MPEG1/2/2.5 文件共 136 帧独立对照 FFmpeg 最大差异 1 个 PCM16 单位；
QEMU 内七入口 ABI 的 176 项检查及三帧实际 guest PCM 对照通过，释放与设备复位清理已验证。
完整原厂播放器亦已调用 HLE，但正常时钟试验仍在第 19 帧/37 个 granule 停顿；
ICR 修复后的 v1 DTU 两路传输 20160/20159 次、完成 35/34 次，随后设备 PCM 保持单值，没有解码或缺 ROM 报错。
**下一项是核对重复音频中断与缓冲续填的关系，恢复连续输出；不再优化原生 IMDCT。**
2026-09-08 已定位并修复一个宿主竞争：原厂执行了 ICR61 的 OR 1 开启指令，
却被音频请求线程基于旧值的写入覆盖。ICR/DTUC 的共享访问现已同步；直接 SFR ALU/位操作
保护完整读改写，内存操作数保持 QEMU MMIO 边界，避免重复加锁。
最新整机不再停在原先“ICR61 丢失 EN”的现场，两路能反复关闭/恢复；完整播放仍未修好。
实际 DAC 连续采集 9.968 秒，其中末尾 7.317 秒保持 (-435,-435)，不能把非零输出当作正常音乐。
捕获的两块文件暂存区已耗尽、环内还剩 251 字节，HLE 有待交付的第二个 granule；
session BUSY 为 0，单例锁也会释放，不是已证实的 HLE 死锁。
新增 opt-in version-2 HLE 输入空间查询（01:49BE），与重建 query 的 186 项控制/PCM 对照通过，
默认 version-1 镜像保持不变。整机仍停在 19 帧，说明查询封装开销不是全部原因。
新的 SRAM 栈证据：前台保存 `playlist.lst` 时反复经过 `32:1614` 文件相关循环；
BIT8D.0 占用位使 `08:3ED6` 跳过续读，回调本身已注册。
更长的 60 次同实例观察仍停在第 19 帧：实际 DAC 142.064 秒中末尾 139.408 秒保持单值。
文件局部计数会重新开始，末尾栈位置已复用，NAND 计数后来也继续增长；不能宣布永久死锁，
更不能把一个循环能结束误报成保存或播放完成。
新的稀疏边界记录已证实 `32:1614` 正常返回 129 后重入，原厂保存位置推进至
512/1024/1536 字节；本轮尚未捕获整个保存返回及后续续读，不能称作永久死循环。
现场循环字节与原始 PRG 一致，可选文件回调为零也符合原厂初始化，不再猜测漏装回调。
下一项使用固定指令时钟核对前台与音频请求的相对进展，再核对保存结束、占用释放与
`16:EC34` 续读；指令时钟试验不等于普通 Web 已经实时可播放。
对照启动曾停留在原厂“每日一句”，已用真实画面确认；探针增加精确画面门控的物理确认键，
不跳改启动 PC 或计时器，也不把没有进入播放器的等待计为音频结论。
不跳过保存、不强清占用位，也不靠强开通道、改优先级或伪造 ready 结案。
修复与失败回归边界见 [ICR 并发缺陷](np560_icr_control_race.md)。
宿主后端很快不等于整机可实时播放，不能以减少中断或固定 ready 掩盖未知硬件语义。
用户现有 Web 实例未替换，M2 尚未完成。边界、证据和具体接入顺序见
[ROM 01/02 音频 HLE](np560_rom_hle_audio.md)。

   40704-byte 核心，并将非零 PCM 输出到原厂 X0 缓冲。不是宿主申请对象或代解码。
   原厂预填等待的 `F006.bit15` 现仅在真实 PCM 完成后发布，复位/真实失败时清除；
   这是依据消费契约重建的软件状态，不是恢复的原厂生产者函数，也不代替其它未知状态位。
   该改动让初始化进一步运行，但隔离进程随后触发 `ptimer_transaction_begin` 断言退出。
   已用只读断点确认旧 QEMU 的直接 SFR 读写没有持有设备锁，而 MMIO 路径持锁；
   修复此并发边界后，原厂定时器/DTU/DAC 回归通过。同一 v3 ROM 的完整应用观察
   `np560-mp3-player-priming-lockfix-20260907-v1` 完成选歌后的 12 次、每次间隔 5 秒观察，
   正常退出 0，无缺 ROM/非法控制/不支持指令；DAC 实际启用并接收原始 MP3 生成的 PCM。
   未移除断言、跳过定时器更新或写固定 ready。**仍未达到听歌要求：** 末次 0.2 秒的
   设备输出全为 `(-470,-470)` 保持值，两个 DTU 传输计数也不一致；不能把“有非零输出”称为音乐正常。
   证据、失败现场和 ROM 身份见 [原厂 MP3 ABI 集成](np560_mp3_factory_abi.md)。
4. **当前：解码提速与真实播放状态衔接。** 共享全宽乘法和基于 libmad 的快速
   DCT32 已移植为 guest 原生代码；新 DCT 保留全宽输入及明确舍入，复用空闲工作区，
   没有扩大堆或 ROM。全宽算术、完整合成、分页表和三类真实 MP3 前缀已验证；
   同条件原厂七入口三帧测试从 22.48→16.49→11.87 秒，最新 PCM 对照最大差异 1。
   这些有限前缀和单次耗时不是整机加速比例、完整格式覆盖或实时达标。
   新 ROM 的完整原厂选歌后实际输出到 DAC，D/F/D/G 均已送达，G 能进入停止状态
   并关闭 DAC；但 F 后未观察到稳定暂停，设备音频仍长时间保持单一样本对。
   只读写观察进一步确认：原厂结束回调先把状态 1 改成 3，主循环随后重新打开
   曲目并调用 codec 初始化，释放旧 session 后重新解码；本窗口没有观察到状态 2。
   后续只读观察捕获到帧头拒绝返回与原厂四次错误结束阈值，实际坏头为 AAAA，
   不是本次已经证明的 short/busy 或文件自然 EOF；该次有观察开销导致的按键超时，
   不算控制验证通过。这些是定位证据，尚未修复暂停或实现连续音乐。
   进一步确认第二块 4096-byte 文件缓冲在消费前被下一块覆写。原因是新解码器
   将自身首帧误当成设备格式改变，再次运行原厂初始化、重置续填标志。
   已修正重建封装的首帧通知条件；旧版针对性失败、新版双缓冲标志和 PCM 回归通过，
   未预配置设备或采样率不同的必要回调仍有效。完整应用已能稳定切换暂停/恢复/停止
   状态及 DAC 开关，但输入停在前两帧，DTU 传输计数为零，尚未越过旧坏头边界。
   说明软件完成位/Hz 匹配还不能证明初始硬件配置齐全；实验 ROM 不替换用户版本。
   随后已定位实际区别：原厂首次传采样率编号 6，而旧独立测试传 44100 Hz。
   编号路径选择 REG60/61 专用音频请求，不走 Timer1/2；旧 QEMU 没有该请求发生器，
   并且音频 PLL 的直接/内存视图未接齐。已实现固件约束下的专用时钟与映射，
   精确 PLL 时序仍属未知；实现和证据边界见 [专用音频请求](np560_audio_requests.md)。
   首次整机已实际越过 4096-byte 坏头边界并推进到 10866 bytes，双路 DTU 都有搬运；
   但真实 PLL 值暴露通用 CPU 缺陷：`MOV R7,[R7++]` 最后把读出值覆盖成指针，
   导致错误音频时钟。已修正后增量装载的写回顺序，原厂表加载及新整机组合已验证：
   实际 PLL=89C6、请求频率 44084 Hz，消费推进至 6687 bytes，双路各搬运 16704 次，
   均无 ROM/指令/控制流/DTU 故障。但设备样本仍长时间单值，实际供给远低于时钟需求；
   新组合尚未再做 D/F/D/G，不把前版控制结果拼成新版完成。
   前一错误时钟组合的 G 超时仍保留为未结案问题，不能算控制全部通过。
   **HLE 授权前的最后一项：快速长块 IMDCT 原生移植。现已暂停继续集成优化。**
   三帧只读 PC 粗采样显示混合滤波、合成及共享乘法是主要执行区域；采样不是精确周期统计，
   也不以带采样开销的耗时评价提速。libmad 快速长块 IMDCT 已通过 186 组有效全宽向量、
   3 组非法类型及 icount 子集的原生/独立 C 对照；未接入整机，不声称已改善音乐播放。
   修正的是移植代码未关闭乘法饱和模式；另一次失败是测试地址碰到已有可执行覆盖区。
   **目前仍不能正常听歌。新的下一项是 HLE 解码后端及其原厂服务连接，随后核对连续供给、
   双声道交接和播放控制。** 原生方案留存，不再为标准 MP3 继续手写 CPU 优化。
   不能为避免结束而返回虚假的成功。与此同时保留 hybrid/窗口的性能缺口，
   不把剩余故障全部归为吞吐，不反复跑已通过的算术测试代替状态实现。
   随后完成真实播放/暂停/继续、跳转、曲目切换、EOF 与退出释放；G 的单次停止
   证据不等于生命周期完成。允许 HLE 宿主解码，但不能修改采样率、绕过缓冲或跳过等待制造播放效果。
   具体版本、失败和数值见 [原生解码性能](np560_mp3_performance.md)，
   实际状态与剩余调用缺口见 [播放状态与物理控制](np560_mp3_play_controls.md)。

仍不能在原厂播放器中播放 MP3；IS 的末带策略仍须在完整 PCM
对照中核验，组件可调用不等于标准符合性或原厂声音兼容已经证明。
滤波链的统一动态范围/缩放和最终溢出策略也要完成，不能靠丢弃合法的大幅度帧掩盖范围不足。
帧 CRC 计算/拒绝和内部输入环已有实现；完整 CRC 错误恢复、跨帧 main_data 使用范围
冲突校验，以及原厂公共接口的复位/双缓冲/EOF 适配仍未完成。
详见 [MP3 guest 核心](np560_mp3_guest_decoder.md)。

## 5. 各层必须补齐的工作

### CPU / SoC 与硬件时序

- 补齐合法指令及操作数形式、标志、DSP/累加器、舍入/饱和、循环与寻址。
- 完成代码/数据视图、片选、字节通道、SFR 别名、栈、可写代码一致性。
- 完成异常、优先级/屏蔽/嵌套/返回、循环中断组合与软件可见状态。
- 按依据实现 Timer、DTU 和设备完成事件；明确尚未知的时序，不以固定成功绕过等待。

### resident ROM 与真实声音

- 查清 PRG、升级包、装载器、重定位/覆盖模块与 resident 入口的关系。
- 恢复启动、调度、内存/对象、绘图、文件、输入和媒体服务，包含共享状态、释放与错误处理。
- 当前声音重点是流初始化、处理、续填、停止及表模式服务，不仅补出一个可返回的入口。
- 查明实际格式、帧结构、算法、系数和输出规则；候选算法名字或相似码率不是匹配依据。
- 恢复“原始内容 → 原厂应用/ROM 服务（允许 01/02 HLE）→ guest PCM 缓冲 → 音频设备 → Web”整条链；
  HLE 解码不等于宿主播放器，不能直接播放原文件冒充完整模拟成功。
- 同时清退已知临时桩；依据不足的部分保留明确缺口，不盲填算法或推测常量。

### LCD、键盘与音频设备

- 补全本机 LCD 命令、GRAM、寻址/扫描、灰度、局部刷新、滚动、显示/休眠与背光。
- 完成键盘接线、电平保持/释放、组合键、去抖和原厂连发；Web 失焦或断开须释放输入。

- 显示错误沿原资源、内存对象、绘图、总线、LCD、Web 逐层查，不在前端补像素。

### NPE 与全部原厂应用

## 6. 避免再次把工具当目标

画面比较用于确认显示错误；自动导航用于复现操作；压力测试用于已发现或合理怀疑的累积状态问题。
它们有用途，但都是验证手段，不是模拟器的功能，也不是独立交付阶段。

- 不设自动导航平台、截图平台、千次压力测试或脚本数量目标。
- 优先复用现有工具；只有当前缺陷无法观察时才补最小诊断，取得证据后回到实现。
- 每项修改做与风险相称的验证，确认原厂实际用途；不以 ACK、无报错、退出码或测试音替代结果。
- 汇报固定为：**缺失行为 → 原因/依据 → 实现变化 → 新增能力 → 剩余缺口**。
- 新的逆向结论是进展，但与功能完成分开记录。没有新证据时，不反复检索已排除来源或重跑已通过流程。
- 若当前缺口确实缺资料，写清需要什么证据、影响什么功能，先做音频内其它能约束该缺口的检查。
  如必须转向其它功能，先明确告知用户卡点及拟切换事项，不将暂时缺证据自动当作换方向的理由；不能用绕过结案。
- 保护用户正在运行的实例和存档。验证使用隔离设备，不因连接失败擅自重启用户实例。
