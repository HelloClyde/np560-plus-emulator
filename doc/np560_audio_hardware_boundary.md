# NP560+ 音频硬件边界

更新时间：2026-09-05

## 2026-09-05 新设备上的进展

当前进展：guest DAC→PCM→Web 数字输出链已接通，非零诊断采样进入真实浏览器
AudioBuffer；原厂渐变函数、静音/暂停、活动中复位和原厂冷启动已验证。另修复了设备先
复位、CPU 后清零导致的旧采样/时钟缓存残留。精确范围和构建见
[DAC 与 Web 输出](np560_dac_web_output.md)。原厂 ROM 解码/流服务仍缺，音乐和 NPE
声音尚未贯通；不能将诊断采样播放当作原厂游戏音频。下面各段保留阶段性历史结论。

前一阶段：三路周期 Timer 已实现；原厂 DAC 传输的高位 BIT 路由原先错误地与 F01C
分离，现已修为 DPRAM 寻址。原厂双路配置/续填/启停代码已能把采样送到 F1E0/F1E2，
六种不同定时器配对均通过，原厂冷启动仍正常。见 [三路 Timer 与 DPRAM](np560_periodic_timers_and_dpram.md)。
当时只到数据传输与寄存器边界；后续数字输出进展见上面的新记录。

最新实现：Timer2 已实际计时、产生硬件请求，并使原厂声音启停等待正常返回。
本轮又接入 DTU 的逐请求数据传输及计数归零 IRQ；原厂 `24:98FC` 已能由真实 Timer2
请求驱动，按 1023+1 两块续填并完成 1024 次传输。两者均不是宿主调用原厂函数或改写
等待变量。依据和验证边界见 [Timer2 设备](np560_timer2_device.md) 与 [DTU](np560_dtu.md)。

当时尚无输出设备：`02:ACD8/AD92`、格式后端和实际输出设备均未完成。新增的参数分档、
输入/输出缓冲调用关系见 [ROM 流后端](np560_resident_stream_backend.md)。以下按时间
保留较早的寄存器、中断及旧镜像记录；其中“Timer2 未计数”“DTU 未实现”不再是最新状态。

较早阶段：基础 ICR 和 RAM 向量已接入，原厂 Timer2 ISR 经 guest 软件 RQ 已能执行、
倒计时归零并返回；详见 [ICR 派发](np560_icr_vector_dispatch.md)。尚未由 Timer2 时钟
产生请求，也尚无声音输出；下文各阶段的“向量未实现”按其构建时间理解。

原厂烧录和文件 API 导入生成的新设备，配置 gate 自然为 0。选择《英雄传奇》已首次
实际进入 `25:0000 → 25:DF62`，读入 section 16 起点 1 KB，逐字节与原文件一致。
严格运行首先发现缺失 `02:ACD8`，随后所需的 `01:B6DE/B7AA/B816/B84E` 被旧安装代码
占位；已清退该安装代码，并修复 CPU 对未实现 TRAP 静默放行的错误。
详细输入、调用契约、构建与验证见 [原厂流后端](np560_resident_stream_backend.md)。

随后确认原厂声音启停使用 `08:47A4` 的 Timer2 等待；已修复 CPU 将 `BIT[53]` 错读为
`REG[D3]`、导致等待提前结束的错误。原厂等待现在暴露真实 Timer2/IRQ 缺口，冷启动仍通过。
见 [Timer2 与位寻址](np560_timer2_and_bit_sfr_contract.md)。这不是声音已输出，也没有证明
`02:ACD8` 就是延时或某种滤波功能。

最新开发构建又统一了 Timer2/ICR 等低 SFR 内存视图，并修正 `REG[01]/F102` 的 PSR 地址。
原厂跨 32 KiB 搬运的进位检查、整份 NPE 原厂文件冷读与零输入冷启动均通过；Timer2 的
计数和通用 IRQ 仍缺，以上寄存器修正不构成可听声音的验收。

继续修复了硬件中断帧和 RETI 使用内部标志位编码、丢失 PSR 高位的错误；真实压栈/返回
检查和原厂冷启动通过。共享窗口构建选择真实 NPE 已停在 `08:47FA` 的原厂等待，
因此 Timer2/向量派发是实际游戏路径的前置依赖，而非仅合成测试中的缺口。
最新构建还统一 SOCR/F100，并让直接 IE 清零真正屏蔽中断；针对性反例和原厂冷启动
验证通过。声音计数/中断源与输出设备仍未实现，不能把正确屏蔽误称为 Timer2 已完成。

下面 2026-09-02 的未触发、gate=1 和重定位尚未进入等结论保留为旧镜像历史证据，不能
继续作为新设备的当前阻塞。真实输出仍未实现，具体 codec 不能只凭 21-byte 记录猜测。

## 2026-09-02 的阶段结论（历史）

QEMU 目前还没有可验收的蜂鸣器、PCM 或其他音频输出设备，Web 也没有播放 guest
产生的声音。现阶段不能声称 NPE 游戏音频已经实现，也不能仅凭 `.npe` 中没有明文
RIFF/MIDI/OGG 标志便断定游戏没有声音。

2026-09-02 新增的只读 SFR 观察器和真实游戏输入探针已经排除一条误判路径：输入期间
反复出现的物理 `F14C=8000`、`F11E=2000` 成对写入来自键盘扫描/中断控制链，不是已
发现的音频数据流。

同日完成的通用 NPE 流位置观察器又排除了“物件拾取时的大块读取就是音频”这一解释：
首次拾取“布鞋”新增 7 次、118954 bytes 读取，全部落在 NPE section 0/1，并流向共享
`51:A20E` 场景资源缓冲；延迟说明阶段的尾环则闭合到 `22:C7FC` 的 NUL 字符串循环。
详见 `doc/np560_npe_stream_resource_boundary.md`。

## 动态证据

`tmp/v880-npe-both-sfr-input-diff/manifest.json` 从真实游戏前台依次执行：

- 下键保持 5 秒；
- 右、上、左各一次；
- 动作键一次；
- 最后空闲 5 秒。

全部输入都经过 Web `/api/key`、QEMU 8×8 矩阵和原厂 scanner/consumer。结果为：

- unbanked unknown SFR 输入增量：0；
- unbanked unknown SFR 空闲增量：0；
- banked Fxxx 候选输入增量：42；
- banked Fxxx 候选空闲增量：0。

42 次候选写全部由固定 pair 构成：

```text
32:245A  logical 714C -> physical F14C = 8000
32:2482  logical 711E -> physical F11E = 2000
```

短按方向和动作各产生一对；下键长按因原厂连发产生 17 对。它们与键盘活动同步，空闲
期不出现。

## 静态闭合

运行期 `32:241A` 对应升级包 source `4F:241A`。两个静态调用点都传入完全相同的三个
参数 `0003,2000,8000`：

```text
3F:F72E -> 32:241A
44:E5E8 -> 32:241A
```

其中 `44:E528` 函数入口先设置 `DS0=1`，读取逻辑 `7160`，即物理 `F160`。`F160`
已经由矩阵模型和既有回归确认是 8×8 键盘矩阵端口。该函数随后执行无键计数/状态更新，
在 `44:E5D8..E5E8` 压入 `3,2000,8000` 并调用 `32:241A`。目标函数写入 F14C/F11E，
再修改 CPU 控制寄存器 27/39/41 并调用 `33:50F4`。

因此这对写入至少属于键盘扫描器使用的控制/中断恢复事务。寄存器的精确硬件名称仍未
确定，所以观察器暂不把它们静默列为“已建模”；但它们不能再作为音频寄存器候选证据。

## 直接 CPU SFR 复核

`tmp/v882-npe-direct-sfr-input-diff/manifest.json` 还记录了不经过外部数据总线的
`REG[00..EF]` 写入。方向/动作输入相对空闲只新增 `27/39/41/A7/B9`；源码与动态返回链
证明它们是 `32:241A` 键盘扫描/IRQ 恢复及 `08:4380` 的计数结束清位。其余高频写入与
周期 IRQ 保存/恢复同步，未形成 NPE 数据到硬件的 producer 链。

冷启动仅出现一次的两个 unbanked unknown 是：

```text
31:B70A -> F018 = 0000
32:DC28 -> F01E = 0000
```

二者所在函数随后初始化 guest 全局/控制表，在游戏走路、物件动作和空闲阶段都不重复。
它们的精确硬件名称尚未确定，但当前没有把它们认定为音频初始化的动态依据。

## NPE 资源反证

- 18 个 NPE 样本的 section 16..37 都满足 `4 + count*21 (+1)` 固定记录结构；
- section 18/19/30..37 在全部样本中逐字节相同，其余也只有少数聚类；
- Hero section 16 的载荷按 bit 统计熵为 `7.944892 bit/byte`；把 21-byte 记录直接按
  `12×14` 点阵字形展开只得到噪声，已排除“这些记录就是未压缩字模”的简单解释；
- `tmp/v887-hero-section16-speex-probe.json` 对 NB/WB/UWB、20/21-byte 多种切片的
  libspeex 反证测试产生大量 invalid/corrupt，raw Speex 假设不成立；
- 冷启动到首地图以及“布鞋”事件只访问 section 0..12，未消费 section 16..37。

因此不能再按“21-byte 约等于某种常见音频帧”给这些 section 命名。下一步必须等待真实
场景首次读取，再追踪其消费者。

## 条件后端的精确边界

2026-09-02 已把运行期调用链
`03:438C → 32:5F86 → 32:B974 → 25:0000` 闭合。`25:0000..0410` 不是随机数据，
而是 source `42:0000` 的逐字节精确重定位函数；它使用 `0x8800/0x8C00` 一带工作缓冲，
并按格式/状态条件选择两个后端：低格式分支目标为运行期 `10:FC0E`，高格式分支目标为
`25:DF62`。这两个运行期目标当前尚未完成安装，但其原始完整函数已经分别在 source
`2D:FC0E..FFFE` 和 `42:DF62..E322` 找到。因而这里是可继续恢复的 relocation closure，
不是需要新增 CPU 指令或伪造 ROM 服务的空洞。

QEMU 新增只读 `NPE_TRANSITION_LEAF` 环，记录每次进入 `25:0000` 时的 caller、SP、
状态/格式全局量、六个参数、分支和返回值。`tmp/v911-transition-leaf-input-probe/manifest.json`
在真实《英雄传奇》前台依次执行下键保持、右、上、左、动作和空闲；游戏 stream read 分别
新增 31、20、30、9、18、27 次，方向/动作均进入原厂控制器，全程无 fault，但该 leaf 的
call/return 始终为 `0/0`，section 13+ 读取也只保留启动时的 4 次 section 13/14 访问。

这项阴性证据证明 `25:0000` 不是开局、普通移动、常规动作或空闲循环必经的解码器。
固定 21-byte 高熵资源仍可能与音频有关，但目前没有触发条件、producer 或硬件输出链，
所以不能把上述后端直接命名为音频解码器。

2026-09-02 的 `NPE_TRANSITION_GATE` 生命周期监控又把未触发原因闭合。冷启动时
`22:9A1A`（source `3F:9A1A`）把 `A1:387A` 从 `0000` 写为 `0001`，稍后
`29:C246`（source `46:C246`）重复写入 `0001`；切换服务的 `32:5F8E` 也精确读到
`0001`，故原厂 `32:5F86` 在调用 child 前返回。旧的 `0401` 结论来自把相邻 word
`A1:387E` 当成 `A1:387A`，现已纠正。证据保存在
`tmp/v913-transition-gate-lifetime-route/08-game-ready.json`，该运行无 ROM、指令或控制流
故障。

两条写路径都通过 exact `25:206E ← 42:206E` 请求 `10:D016`。此前将小端表项
`0x2240` 错读为 `0x0040`，现已由 live code-bus/source 哈希和机械反汇编纠正：`D016`
在同一 reader 内部分派到 `25:2240`。该 continuation 把传输后的首字节限制到布尔范围：
`0/1` 原样保留，`2..255` 写回 `1`，再从 `25:2476` 返回成功。

`tmp/v915-resource-special-lifecycle-route/08-game-ready.json` 的两次真实 `D016` 调用都记录
了 `transfer=FF → output=01`，随后两个调用者分别把 `01` 写进 `A1:387A`。这证明原始
checkpoint 的 `FF` 没有被错误读取；转换完全由原厂 guest code 完成。它目前只能称为
transition/resource gate，不能称作“音频开关”。强制清零仍只会制造宿主假路径。
