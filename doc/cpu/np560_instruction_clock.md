# CPU 系统时钟基线与 QEMU 时间预算

日期：2026-09-08。M2 音频主线的一项时钟域实现；仍不是完整机器周期模型或实时播放交付。

后续实现已推进到 [首批 A/B 指令周期和外部数据等待](np560_instruction_costs.md)。
下文一周期实现及 `833f36ed` 数据是保留的历史基线，不代表当前实验模型仍对所有指令计一拍。

## 现在实际实现了什么

`target/dmcu/clock.c` 提供共享的 `dmcu_system_clock_hz()`，Timer0/1/2 与显式启用的
CPU 指令时钟使用同一份 PLL/CLKCON 选择逻辑。没有改变原有 Timer 频率公式：

- 非 PLL 路径来自已核对的 CN1916884A 图 22；CLKSEL 的 32.768 kHz 分支优先。
- PLL 路径沿用原厂频率换算代码约束下的 `4 MHz × N / D` 再分频推断。
  仍按现有整数 Hz 计算；没有由此证明 PLL 锁定、瞬态、所有模式或分数频率准确性。
- CLKCON 的受保护写入仍由既有 SFR 实现处理，所有总线视图共用；忽略的锁定写入
  不会改变 CPU 时钟。此次未扩大哪些寄存器需要 UP 解锁。

新 QOM `instruction-clock` **默认关闭**，仅能在第一次执行前、暂停状态下开启；
要求单 CPU、fixed icount shift=0、无录制/回放，不允许旧 ROM/UI HLE。
登记的 01/02 MP3 HLE v4 不属于旧 UI 模拟，仍可以使用。
这是初始化后注册的实例属性，不是可随意在 `-M` 上追加的通用启动参数。
实验播放器探针使用 `--instruction-clock --icount-shift 0` 在首次 cont 前设置它；
没有将它接成用户 Web 的默认配置。

目前每条指令只计一个系统周期，状态明确写出 `MODEL:one-cycle-baseline`。
**这只是时钟域基线，不能当成所有指令均为一周期的结论。** 已知多周期指令、内外存
A/B 条件、访存等待、流水线冲突、IRQ 进入、DTU 总线占用和 HLE 服务耗时尚未接入。
不能因为短片段声音正确而停止在这个基线上。

## 时间推进与设备期限

QEMU 单指令块入口先计一条指令、1 ns。DMCU 在指令执行前以进入该指令时的
系统频率累计实际基线时间，再通过 `icount_account_extra_ns()` 加上剩余时间。
频率变化只影响后续指令，不重新乘算已经发生的时间。

时间使用 32 位小数纳秒累计；小数余量跨频率切换保留。单次周期换算截断误差小于
`2^-32 ns`，避免每条指令都直接丢掉小于 1 ns 的余量。复位重置本地统计与小数相位；
它不是对真实晶振复位相位的测量。

`accel/tcg/icount-common.c` 新接口只由此显式实验路径调用：

1. 在 QEMU 时钟锁内结算已执行指令，再增加时间偏移，保持原始指令数不变。
2. 同时缩减当前执行预算及剩余计数器。只改时钟会沿用过长的旧预算、越过设备期限；
   只减剩余计数器则会把经过的时间伪造为执行过的指令。
3. 保留异步退出使用的 decrementer 高半部；预算耗尽后仍由 QEMU 常规路径处理定时器。
   没有直接调用 guest ISR、提前清空 DTU、伪造 RQ/EN 或改动 DAC 频率。

当前事件粒度仍是指令边界，不含指令内部的总线相位。单指令块也避免普通 MMIO 重编译
和 C helper 中途退出时重复计入尾部；自修改代码另有计数一致性检查。

功耗模式 OPMODE 非零或所选推断频率高于 1 GHz 时，实验模式显式停在未实现的
时钟边界，分别记录 `FAULT:1/2`，不把它误报为坏指令或钳成任意频率。
此时原始 icount 包含一次未能计时的尝试，本地已计时指令统计少一次，测试明确区分。
不支持此模式的 CPU-only 状态保存/恢复；整机快照原本也未完成，不能静默丢掉时钟相位。

## 定向验证

本轮 QEMU SHA256：`833f36ed9aa522e4013c3b34dffaf4a6e11e198727b4b6cf2ed675a97d945fd0`。
所有下述实验均无宿主 guest-memory 写入，进程正常退出 0。

`scripts/tests/test_np560_instruction_clock.py`：

- 3113 条指令穿过非 PLL、32.768 kHz 别名、PLL 切换及锁定写入后，累计 19355779 ns，
  与独立有理数和定点计算相符；原始 icount 仍为 3113，不含虚构的等待指令。
- 24.576 MHz 与 32.768 kHz 两种频率下，同一测量区间 Timer0 都走 4098 拍。
- 独立 32.768 kHz 时基在 24.576 MHz CPU 基线中按 750 周期关系触发；guest 两指令
  轮询循环在允许的指令边界内看到一次 RQ，并自行关闭时基。不是只比较自报 NS 计数。
- 暂停冻结、小数余量、复位统计及拒绝运行后切换模式通过；两类未实现时钟边界和
  无 icount / fixed shift=5 / auto 三种不兼容配置得到显式拒绝或停机。

记录：`tmp/np560-instruction-clock-20260908-v1/report.json`，共 6 个运行场景与 3 个配置拒绝。
关闭新模式的精确计数 12 项仍通过：`tmp/np560-instruction-clock-off-count-20260908-v1`。

启用新模式的 8 个自修改/别名用例同时检查 CPU 结果及本地计时指令数等于 raw icount：
`tmp/np560-instruction-clock-coherence-20260908-v1`。其中包括跨页扩展字、内部 SRAM、
字节别名及同块写入；没有以 host flush 掩盖计数或代码一致性问题。

共享频率函数的原有路径 24 项通过，包括普通/fixed 模式的 CLKCON 字/字节/BIT/POP/
banked/IGNDS 写保护及原厂 `24:FF92` 保存、切换、恢复：
`tmp/np560-instruction-clock-shared-frequency-20260908-v1/report.json`。

串行有限 DAC 验证：`tmp/np560-instruction-clock-dac-20260908-v1/report.json`。
577263 条指令累计 23488891 ns，两路各 1023 次请求和搬运，零空请求、零重复、
零请求外写入，左右不同帧数 0，短音调约 439.919 Hz。没有改变音频独立 PLL。

随后串行关闭新模式的普通/fixed shift=5 DAC 回归也通过：
`tmp/np560-instruction-clock-default-dac-20260908-v1/report.json`。两路各 1023 次搬运、
左右不同帧数 0；普通模式缓冲耗尽后至 guest 关闭前多 6 次请求，fixed 模式无额外请求。
两者短波形分别约 440.367 / 439.919 Hz，均在既有 1.5 Hz 检查容差内，不当作提速数据。

## 原厂 MP3 播放器

`tmp/np560-mp3-instruction-clock-20260908-v1/{report,delivery-analysis}.json`：

- 同一原厂 PRG/UPD、只读 tone NAND 和 HLE v4 ROM，精简历史观察，物理矩阵选曲；
  12 次观察与 60 秒墙钟录音上限。输入身份记录在 report，未保存 NAND，用户 Web 未替换。
- 完成原厂启动、启动卡物理 Enter、播放器文件选择；观察 2 起 mode=5/state=1。
  最终 200 帧 / 399 granule / 399 次复制，查询 791，三类失败计数均为 0；
  一次释放，当前仍一个会话。没有重现 auto 的第 19 帧停顿。
- 最后时钟快照选择 24 MHz，544786342 条已计时指令、22696457537 ns，`FAULT:0`。
  所有采集到的时钟快照均无故障；Timer0/1/2 的所选频率也为 24 MHz。
- 680 个续填事件，两路各 340 个，其中各 339 个进入既定的短 576 样本筛选。
  总延迟中位数 1.792 / 1.834 µs，仍基于一周期假设，不能称作真实 ISR 延迟。
- 实际设备录音 156904 帧 / 3.268833 秒，初始零输出 1.533333 秒，余下约 1.7355 秒
  为音调；整段仅 1 帧左右不同。PCM SHA256：
  `b22aeec06900ec7c0a56fbbdb1f8be8fa4a8bfb1991265155fc74133074016f1`。
- 第 2.000438–3.000542 秒稳态窗口，两路各 44090 次真实请求均恰好有一次写入；
  零空请求、零重复、零请求外写入，FFT bin 约 439.954 Hz，分辨率约 1 Hz。
  1–2 秒窗口混入初始化静音，不能把其中的空请求当作稳态音频缺样。

这证明新时钟基线能运行原厂播放器并保持该短稳态输出。录音窗口不覆盖全曲尾部或交接，
虽然解码观察跨过一次释放；两者不能混为一项全曲证明。大量状态抓取会显式暂停 CPU，
也不能直接拿 60/3.269 推断无暂停 Web 的吞吐率。`playback_verified` 仍是 false。

## 下一步，不收缩目标

1. 在这个时间推进接口上接入有依据的指令、内外存及访存成本，不继续停留一周期基线，
   也不再调固定 shift 或宿主自适应比例来追目标音高。未核实的管线重叠等保持明确未知。
2. 确认时序后优化真实 CPU 执行成本，让独立 Web 连续产生足够的设备 PCM；不能靠
   前端补样、变速或替代原厂播放器发声。
3. 在同一完成度足够的构建重新核对整曲、尾部/交接、暂停/续播/停止、退出释放及 NPE 声音。

M2 和 NP560+ 整机均未完成，HLE 授权也不等于允许忽略 CPU/设备行为。
