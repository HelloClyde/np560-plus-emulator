# CPU 历史诊断开销与音频续读

日期：2026-09-08。主线仍为原厂 MP3 连续播放，完整 NP560+ / NPE 范围不变。

## 先区分硬件请求语义与执行不足

本地原始架构说明 `tmp/cnpatent/CN1916884A-description.txt` 的 d134–d137、
d150–d158 描述 EN/RQ/ED、计数非零时交 DTU、归零转 CPU 最高优先级服务。
它没有给出 NP560 专用 DAC 请求线的完整保持/重触发规格，不能据此任意屏蔽空计数请求。
前轮完整播放器文件循环仍推进，但非常慢，同时 CPU 累计约 285 万次中断进入。
先找不改变指令、时钟、优先级、原厂缓冲或 ROM 契约的执行开销。

## 实际热点与修改

`scripts/probe_np560_cpu_cost.py` 分开执行固定工作量计时与只读宿主采样：

- 计时 guest 关闭 CPU IE，只执行确定的寄存器加减/分支循环，共 3146501 条指令，
  检查最终寄存器、SP、PC 和缺失/不支持/非法控制诊断。无 NAND、ROM 或 HLE。
- GDB 仅附加脚本另起的自有 QEMU，取得 24 个栈后脱离；它不参与三次速度计时，
  也不附加用户实例。采样文件保留完整线程栈，不将粗采样比例称作精密 CPU 百分比。

24 个 vCPU 样本有 14 个落在 `trace_control_transfer` 或其子调用，5 个包含
诊断 `address_space_lduw`。即使 guest 只有寄存器运算，每条指令也在读取
`51:29C4/29C6`，而那个值实际只在三个存储解析器检查点用到。
另一个热点是逐指令线性扫描 78 项设置页地址。

已修改 `target/dmcu/helper.c`：

1. 存储记录读取延迟到 `07:405A`、`07:40D6` / `07:414E` 的对应 RET 边界；
   三处实际使用位置和得到的值不变，其余指令不再进行两次无用诊断总线访问。
2. 78 项设置检查点改为编译器可优化的精确 switch 查找。全部 PC、事件编号、
   采样字段和时点保留，未知地址仍不记录；未关闭诊断、未改变 guest 内存或控制流。

旧表另存为前测目录 `sound-trace-map.json`，与新查找的 78 个键值及缺省分支逐项核对。

## 应用地址索引与诊断扫描条件（2026-09-08 后续）

后续普通时钟基线已推进到 HLE v4，数据 TLB 修正仍未明显改善续填延迟。
本轮保留整条 `trace_control_transfer`，只改变以下查找成本：

- 191 槽应用地址表改为 `observer-sites.h` 中的精确 switch；其中 190 个唯一地址，
  重复地址 `20:2E9E` 保留原先“取第一个槽”的行为。没有更改命中后的记录或停止条件。
- NPE node-transfer 观察器仅在 from 或 target 属于 5F 段时扫描；该块所有匹配地址
  原本都在 5F 段。跨段进入/退出仍可命中，没有新增 opcode 限制。
- file-write/open/commit 的 SCALL/RETS 子调用扫描提前检查原有 watch/op 条件；
  registry-builder 整块仅在 SCALL/RETS 时进入，其所有原有事件本来都要求这两种操作。
  没有取消有效日志、总线读取、故障检查或原厂指令。

## 后续：显式精简控制观察模式

上述扫描优化没有解决主要成本。已另外审计并分离历史控制观察路径，增加默认 false 的
`control-observers-minimal`；严格坏地址检查与前台按键 ACK 保留，缺失/不支持检查未关闭。
同构建 `7b485585…`、相同 3146501 指令的三次中位数为完整 1.2823 秒、精简 0.5899 秒，
吞吐约 2.17 倍。这是微基准，不能推广为全部应用的速度或全部诊断等价。

同构建原厂播放器 A/B 已结束：短交接左路中位数 82.3 → 66.3 µs，曲目交接静音
约 0.55–0.61 → 0.34–0.40 秒；但精简模式实际音高仍约 437–438 Hz、左右未对齐。
必要故障/ACK 八例、HLE 门控八个运行例和四个配置拒绝通过；原厂完整选曲/播放通过，
尚未覆盖精简模式的暂停/继续/停止、退出和其它应用，不修改用户 Web 默认配置。
审计限制、保持/不保持的日志、失败夹具及完整 A/B 见
[精简控制观察实验](np560_control_observers_minimal.md)。下一工作仍为音频实际时序，
不将不断增加诊断工具或逐个小表优化作为实现目标。

随后已将 CPU 分派接入标准顺序块连接和安全动态目标查找，严格保留 IRQ/CRIT/IGNDS
重新仲裁退出。寄存器基准约快 9.8%，内存读取未证明明显改善；完整播放器仍约 438 Hz，
总续填中位数约 70 µs，并未修好音频。自适应指令时钟的同构建对照连续播放失败，
因此下一项是建立 CPU/设备相对时间模型，不继续依赖小幅宿主提速。
实现边界、全部回归和两种时钟的实际录音见 [CPU 块连接与调度](np560_cpu_tb_dispatch.md)。
