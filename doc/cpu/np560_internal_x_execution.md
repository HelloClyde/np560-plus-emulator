# 内部 X RAM 取指范围：原厂临时中断代码被错误 ROM 覆盖

日期：2026-09-06。修复对象为 QEMU 的程序总线映射，不是新增 resident ROM 服务。

## 实际故障与原因

在《英雄传奇》后院得到 25 块钱后，用原厂菜单把进度存入第二槽并正常关闭 writer。
旧核心从保存后的 NAND 冷启动，进入游戏标题初始化时空屏，停在：

`ROM_MISSING=00:688e PREV=00:1cf6/ac00 IRQ=1`

此时尚未选择“再续前缘”，不能将它报告为第二槽读档完成或存档内容损坏。
继续检查现场发现：

- RAM 中断向量 `00:0040` 是 `SJMP 00:1202`。
- 数据 RAM `00:1202..12D7` 有 214 字节的完整中断处理程序：保存寄存器、推进时钟、恢复并 RETI。
  这 214 字节与原始 PRG 文件 `0x054288..0x05435D` 完全相同，工具 source 映射为 `25:4288..435D`。
- 同地址的程序总线却读到另一段内容。`00:1C00..1D0F` 的 272 字节与 ROM 镜像中的内容一致，
  又与原始 PRG 文件 `0x0F610A..0x0F6219` 完全相同；其中 `1CF6` 的 AJMP 指向 `688E`。
- 旧板级只把 `00:0000..102D` 映射为可执行 X RAM。它够运行旧的 `00:1002` 电源等待程序，
  但没有覆盖这次原厂装载到 `1202` 的中断代码，取指落到了旧重建 ROM 的无关载荷。

因此最初“向量被破坏”的怀疑已被更直接证据纠正：向量与实际 RAM 中的处理程序相配，
错误在取指视图。不能在 `00:688E` 补成功桩，也不能强迫向量一直指向 `08:40D0`。

故障现场：`tmp/np560-native-map2-save-20260906-v1/reader/04-title/00.json` 和实际 LCD PNG；
完整内部 RAM、向量及程序总线片段在同目录根下的 `fault/`。

## 硬件依据与修改

已目视核对本地 `tmp/cnpatent/CN1916884A.pdf`：

- PDF 第 7–8 页说明指令可从内部 X RAM 取得，不能从内部 Y RAM 执行；代码地址为 CS:PC。
- 第 128 页图 2 将内部 X RAM 定为 `00:0000..7FFF`（32 KiB），Y RAM 为 `00:8000..BFFF`。
- 第 129 页图 3–4 分别给出程序与数据编址，不能把数据银行规则套到取指。

`qemu-dmcu/hw/dmcu/np560.c` 将旧的短前缀别名改为完整 32 KiB X RAM 别名：
程序与数据视图使用相同 RAMBlock，沿用已有的写后失效通知。没有增加 `1202` 专用覆盖，
没有复制原厂代码到宿主实现，没有改 PRG、ROM、NAND 或游戏状态。
该修改不把 Y RAM 纳入可执行 X RAM，也不声称其它外部片选或整个总线模型已完成。

旧重建 ROM 在 X RAM 地址范围里的载荷不能继续遮住真实 RAM；如果发现某条旧路径依赖这些载荷，
应核对正确地址与原厂装载过程，而不是恢复错误优先级。

## 能区分修复前后的定向结果

复用 `scripts/tests/test_np560_code_coherence.py`：guest 自己通过 FP 在 `00:1202` 安装
`MOV R0,#1234; RETS`，调用后改立即数为 BEEF，再次调用。没有 NAND 或宿主 RAM 注入。

- 修复前 `ecff5a4b…` 在第一次调用停于 `00:1202`，根本没有执行已写入的函数。
  反例及正常退出记录：`tmp/np560-xram-before-20260906-v1/`。
- 修复后 `fd83eb62…` 第一次返回 1234、改写后返回 BEEF，SP 恢复。
  `00:7FFA..7FFF` 的 X RAM 上界用例同样通过，普通与 icount 模式结果一致。
- 原有同页、跨页立即数、内部字/字节和同执行块自修改用例仍通过。
  结果：`tmp/np560-xram-coherence-20260906-v1/report.json`，隔离进程均正常退出。

修复后核心 SHA-256：`fd83eb62b7390533d2c6b3b9edea827407c9c76e17a5f4d5f7791a34886d69d1`。
修复前二进制保留在 `E:/qemu-dmcu-build/qemu-system-dmcu-pre-xram-exec-20260906`。

这些结果只关闭确定的取指映射缺口。实际第二槽冷读回另行核对，不能用小程序通过代替；
声音 ROM、完整游戏及整机其它未实现能力仍在 [计划](../plan.md) 中。

## 原厂处理程序与实际使用结果

同一脚本的 `--case original-relocated-irq --original-prg <原始 PRG>` 使用上述未改动的
214 字节处理程序。guest 将其安装到 X RAM、将向量指向 `1202`、建立时钟初值，再置一次 ICR
软件请求。原厂程序必须自己推进时钟并恢复寄存器；不使用宿主函数代替中断。

- 旧 `ecff5a4b…` 实际进入中断后停在 `00:1202`，没有返回。
- 新 `fd83eb62…` 实际由 `00:12D2` RETI 返回：tick `3→4`，秒 `10→11`，分仍为 20；
  R0/R1/R2、DS0 和 SP 恢复，普通及 icount 均通过。
- 前后证据分别是 `tmp/np560-xram-original-irq-before-20260906-v1/`、
  `tmp/np560-xram-original-irq-after-20260906-v1/`。这是映射修复的确定性因果验证；
  软件请求不冒充原厂临时更换向量的完整操作时序。

新核心使用同一 PRG、ROM 和未修改的保存 NAND 冷启动，经原厂标题的“再续前缘”读取第二槽，
实际恢复后院、位置/方向及金钱 125，见 [原生存读档记录](../games/np560_npe_native_save.md)。
这次游戏启动没有触发同样的临时向量时机：标题处 `1202` 尚为空 RAM，不能仅凭标题成功
证明原来的异步故障已按同一时序重演。因此把上面的确定性原厂 ISR 验证和此次实际冷读回分别记录。

本轮 reader 已正常关闭且未启用 NAND 落盘，保存镜像哈希不变；用户 8807/8808/8809 未操作。
