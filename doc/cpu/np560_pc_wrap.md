# CPU 段末 PC 回绕与跨边界长指令

日期：2026-09-06。实现范围：普通顺序取指、调用返回地址、REP 后继地址，以及段末长指令的扩展字读取。
这是 CPU 共用语义修复，不是某个菜单或游戏的补丁，也不表示声音 ROM 已恢复。

## 依据与错误

本地原件 `tmp/cnpatent/CN1916884A.pdf` 的说明书附图第 3/18 页、图 3
明确把代码地址画为 **8-bit CS 与 16-bit PC 拼接为 24-bit 地址**；同页图 4 则是不同的 DS 数据寻址。
已直接核对扫描页，不仅依赖提取文字。按这一地址结构，顺序推进的是 16 位 PC，
段末回绕不能把 PC 的进位当作修改 CS 的指令。这里是资料支持的架构实现，不是真机段末执行测量。

旧 helper 使用 `(start + instruction_size) & 0xFFFFFF`，会出现：

| 执行位置 | 应有行为 | 旧实现错误 |
| --- | --- | --- |
| `22:FFFE` 的 16 位 NOP | 接着执行 `22:0000` | 执行 `23:0000` |
| `22:FFFC` 的 32 位 MOV | 扩展字在 `22:FFFE`，后继为 `22:0000` | 后继为 `23:0000` |
| `22:FFFE` 的 32 位 MOV | 扩展字在 `22:0000`，后继为 `22:0002` | 扩展字读自下一段，后继也进入下一段 |
| 段末 SCALL | 栈中保存原段和回绕后的 PC | 返回段可能变成下一段 |
| 段末 REP / 被重复指令 | 重复体及完成后的后继都遵守段内 PC | 后继或重复体进入下一段 |

TRAP 原先已有保存原 CS 的特殊处理，因此过去 TRAP 回绕检查通过，
并不能证明普通指令的后继和取指也正确。

## 实现

- `target/dmcu/cpu.h` 增加 `dmcu_code_advance()`，保留 CS，只回绕低 16 位 PC。
- `target/dmcu/helper.c` 的统一 `next` 使用该函数，调用返回和重复执行沿用同一规则。
- `target/dmcu/translate.c` 保留正常指令的原有页跟踪；仅在长指令操作码位于 `CS:FFFE` 时，
  通过运行时 `fetch_extension` 从代码总线读取 `CS:0000`，每次执行都重新读取，不依赖 DS0/DS1。
- 此时 TCG 跟踪的连续 TB 范围只包含末尾操作码，块在页末结束。
  翻译器的 `pc_next` 是线性的 TB 范围端点，与 guest 的段内 PC 分开，避免块大小回绕。
- `target/dmcu/disas.c` 的扩展字读取同样段内回绕；取指日志打印完整指令长度，
  不把“连续跟踪范围只有操作码”误报成反汇编与翻译器长度冲突。

不能简单把 `translator_lduw()` 的第二次调用改成回绕地址：本版 QEMU 的通用 translator
按连续第一/第二页跟踪代码，回到同段第一页不满足其连续地址约束。
也不能在翻译阶段直接 `cpu_lduw_code()` 后把扩展字缓存为常量，那样 guest 修改扩展字时会留下过期代码。

本次没有修改通用 QEMU translator，也没有为特定原厂地址增设执行补丁。
QEMU 插件对这种非连续长指令的完整字节记录尚未核对；CPU 执行与 `in_asm` 日志已有下述证据，
不据此宣称所有插件的指令长度/原始字节接口均已验证。

## 修复前后的可区分证据

使用无 NAND 的小型 guest：原段正确路径把 R2 设为 `BEEF`；邻段错误路径把 R2 设为 `DEAD`。
两条路径均返回同一个终点循环。因此错误表现为明确的寄存器差异，不是超时或未知指令。

- 旧核心：`E:/qemu-dmcu-build/qemu-system-dmcu-pre-pc-wrap-20260906`，
  SHA-256 `1f42a1e3d8979628810f66775c2f5219605332f1e7e580ab99af242a157545db`。
- 修复核心：`E:/qemu-dmcu-build/qemu-system-dmcu`，
  SHA-256 `e078605f59f6c425004a8e9f1ef4bea36222c00aecbbc0dadb7057c87af40276`。
- `tmp/np560-pc-wrap-before-20260906-v3/`：旧核心实际 R2=`DEAD`，到达 `20:0018`，
  无 ROM_MISSING、UNSUPPORTED 或 INVALID_CONTROL；检查脚本退出 1，所拥有 QEMU PID 83366 正常退出 0。
  失败时总报告的 `cases` 为空，具体失败寄存器与退出记录在 `word-icountNone.json`，不能误读为空测试通过。
- `tmp/np560-pc-wrap-20260906-v2/`：修复核心在普通运行和 `icount=5` 下通过对应路径，所有 QEMU 正常退出 0。
  检查涵盖 16/32 位顺序指令、未采用的条件跳转、SCALL/RETS 实际栈、REP 及跨段边界扩展字。
- `wide-straddling-icountNone.asm.log` 和 `wide-straddling-icount5.asm.log` 实际显示
  `0x0022fffe: mov reg[0xf0], #0x2468`，而不是邻段放置的 `1357`，也没有长度冲突提示。

自修改扩展字场景不是宿主写 RAM：guest 先从 `03:FFFE` 读取立即数 `AD03`，
经正常数据总线将 `03:0000` 改为 `BEEF`，再执行相同的末页操作码。
第一次结果 R2=`AD03`，写入读回 R3=`BEEF`，第二次结果 R4=`BEEF`；普通与 icount 均成立。
这直接覆盖了“操作码页不变、扩展字页变化”导致的旧常量风险。

历史记录保留：最早 `before-20260906-v1` 测试夹具误用 `BC22` 作为 SJMP，
实际上 SJMP 应为 `AD22`。那次停机不是 CPU 回绕证据，也没有为错误夹具补指令。
纠正夹具后的 `before-v2` 已得到 `DEAD`；此次 `before-v3` 又绑定旧核心身份重现同一结果。
修复后初版核心 `215058e8…` 的通过记录在 `np560-pc-wrap-20260906-v1/`，
最终证据使用上面的 `e078605f…`，不将两次构建混称。
