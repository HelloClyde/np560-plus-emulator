## 2026-10-01：纠正原始音量字节序，播放器最小化不等于目标档持久化

`/api/state?source=data` 返回底层**小端原始字节**，而 DMCU
逻辑字节 `4A64`（当前档）处于该 word 的高 lane，`4A65`
（目标档）处于低 lane。因此原始十六进制字节 `0007` 是
**当前 7 / 目标 0**，`0700` 是 **当前 0 / 目标 7**，
`0707` 才是两者均 7。前节及曾向用户给出的“`0007` = 当前 0、
目标 7”解释错误；以下记录据此更正，不能继续用错误解释
判断设置持久化。

从上节战后冷读的独立 8894 实例出发：游戏“音乐开”仅在 RAM
生效，`PROGRAMS=48` 未随选项改变；结束游戏确认框**默认
高亮“否”**，第一次确认只是取消。第二次目视左移高亮“是”
才真正回到 `.npe` 文件列表。进入原厂 MP3 页时 `4A64`
原始字节 `0000`、NAND `PROGRAMS=192`。七次实体上键后
变为 `0700`（目标 7、当前 0），`PROGRAMS` 仍 192，
journal sequence 未变；播放器当时未选择歌曲。按 F4 最小化
后 `PROGRAMS=464`，journal sequence 增 277，但 RAM 仍为
`0700`。这证明退出时有 NAND 写入，**不证明写的是音量**。

`474823a5e2b0760b7636a907485be17d36bd178c5f70ffc903634c89d391bb6a`）
