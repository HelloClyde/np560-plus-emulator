# 游戏世界入口：代码写入现场与复现边界

日期：2026-09-05。此问题尚未修复；不能把一次导航成功解释为已消除间歇性代码损坏。

## 原故障事实

CPU 构建 SHA `503cc5ac63ecbd7bd9b4f8dccf45c11967272a1498f7ba8e4383769c4b00f0e0`，
ROM `np560-system-v380-vma03-resident-codec-holes-v1.bin`，NAND
`np560-vendor-file-import-v3.nand`。未修改用户设备或导入镜像；HLE 关闭，显式报告 ROM 缺口。

正常菜单路线 `tmp/np560-sfr-psr-native-route-v1/` 的前三步 Start/Entertainment/GameWorld
各消费一个事件。确认进入游戏世界后，停于 `22:1840 / BCD3`，没有进入 NPE 文件列表。
`22:183C` 是合法的 `MOV R1,[5194]`；原 PRG 对应 source `3F:1840` 为 `58F1`（PUSH R1）。
合法分派进入了已改变的代码，不是缺少一条应当实现的 BCD3 指令。

原暂停实例的代码总线和数据总线在 `22:1840` 均返回 BCD3。保存的
`tmp/np560-sfr-psr-corrupt-code-221834.bin` 从该位置起包含原包的英语谚语资源内容，
而非原函数。按 guest word lane 转回逻辑字节，匹配原 `.upd` offset `0258D364`，
即 slot 3 offset `021627B8`；附近是 “Every cloud has a silver lining” 及其中文翻译。
这证明异常内容来自原包资源；**尚未证明是谁、何时、经哪条总线把它写到代码区**。

## 对照没有证明 PSR 地址修正是根因

- 旧的共享窗口、未修 PSR 地址构建 `81263143...`，同 ROM/NAND 冷启动后进入了 NPE
  文件列表。记录 `tmp/np560-pre-psr-route-compare-v1/`，最后一步映射计数 3→5，存在重复消费，
  不能把它说成和失败现场完全相同的时序。
- `503cc5ac...` 新实例启动后，宿主 GDB 对实际 data RAM 的 `22:1840` 设置硬件写断点，
  没有修改 guest 内容。该实例的首次 Start 被消费两次，后续进入课件缺失提示，偏离预期路线。
- 关闭提示后，120 ms 真实矩阵电平操作进入了原厂 NPE 文件列表，随后选择《英雄传奇》
  停在 `08:47FA`，即原厂声音启停的 Timer2 等待，CPU 没有 ROM/非法指令故障。
  记录为 `tmp/np560-psr-code-write-watch-route-v2/` 和 `tmp/np560-psr-watch-hero-v1/`。
- 此次写断点没有触发，且运行前史不同；既不能认定原问题已修，也不能认定是 PSR
  地址修正引入的确定回退。120 ms 输入是定位条件，不是用限速替代真实键盘时序实现。

新增最小工具 `scripts/probe_np560_code_write.py`：只创建自己的隔离、不保存 NAND 的 QEMU，
启动前由宿主 GDB 对实际 data RAM 字设置硬件观察点，可重用普通矩阵路线。
命中后记录 guest 当前/完成 PC、寄存器、DS、IGNDS/CRIT、中断状态、邻接数据和宿主调用栈。

## 另一个已证实的错银行机制：IGNDS

代码核对与原始指令文档确认 IGNDS 序列必须屏蔽硬件 IRQ；旧 CPU 只检查 CRIT，
会在 IGNDS 保护的 MOV 前进入向量，消耗前台前缀并在返回后写到错误 DS 银行。
独立 guest 反例直接读回错误目的地，新核心加入 IGNDS 准入屏蔽后写入恢复正确。
详见 [IGNDS 中断保护](../cpu/np560_ignds_interrupt_mask.md)，含原文页码、前后数据和同版验证。

这是一个实际修复，不是新的临时 ROM 桩；但尚无第一写入现场把它和本文件的谚语资源覆盖
关联起来。保留 `22:1840` 根因缺口；不继续无限重跑相同导航，转回可证实的共同机制和
真实 NPE 所需 ROM 服务，有新现场时复用上述监控追第一写入。
