## 已核实的记录与消费路径

以下代码地址为运行时地址；`dump_np560_range.py` 的 PRG 源地址要加 `0x1D0000`。
data 52 快照中的 16 位数按小端读取，逻辑字节通过 `address ^ 1` 访问。

1. 快照中队伍人数 `52:7AFA=1`、敌人数 `52:7AF0=1`，敌人类型表首项
   `52:792E=1`。角色记录基址 `52:6450`，步长 `0x94`；敌人首记录为 `52:64E4`。
2. 原厂 `15:8A72` 从敌人区 `0x09899D` 的索引读取相对偏移，类型 1 的偏移为
   `0x1F4`，所以文件记录地址为 `0x098B91`。
3. `15:8BD4` 开始读取 12 字节名称；`15:8C22..8C6A` 随后读取 2 字节到
   `52:647E + record_index*0x94`。该字段被敌人绘图调用用作资源编号。
4. 当前敌人名称为“大头犬”，编号字段 `52:6512=CCCC`，当前体力字段为 35。
   原始 NPE 对应的两个字节**本身就是 `CC CC`**，不是只有模拟器中的记录如此。
5. 原厂 `1A:8FCE..901C` 将该字段与 `52:7AF2` 相加并调用 `31:C498`；
   包装函数在 `31:C4E2` 调用图像装载/绘制入口 `2B:0000`。
   快照中的 `7AF2=0570`，16 位和为 `D23C`。
6. `2B:0020..0026` 对第一个参数作有符号负数检查；为负则在 `2B:0060`
   设置 `R0=FFFF` 并返回，不进入后续资源读取和绘制。

## 结论边界与下一步

这是“原始样本中的异常资源编号 → 当前 guest 记录 → 原厂绘图入口拒绝负编号”的
具体线索，比直接归因于 LCD、mask ROM 或前端更有依据。
其中函数执行结果目前是**结合快照和静态代码推导**，尚未记录本次调用的完整动态参数和返回值。

不能据此宣称样本一定损坏、真机也一定不显示，或所有敌人图像都存在问题；仍需排除
遗漏的编号修正、进入了不应进入的路径，以及同版本原厂行为的未知部分。
下一步核对该调用的实际参数/返回，并通过原生玩法观察另一种有效编号的敌人。
若证实是样本自身缺陷，应记录兼容性边界，不把 `CCCC` 强改为猜测的编号，
也不按游戏名在 QEMU 或 Web 中补图。

`play/12-bat-battle/00.png` 中左侧敌人正常出现，右侧角色和战斗控件同时显示。

这否定了“整个敌人绘制路径都因 ROM 缺失而不可用”的宽泛归因。
它不等于已经动态记录了大头犬的负编号返回路径，也不证明样本中的 `CCCC` 应改成哪个值。

## 取证失败记录与剩余边界

前一尝试 `tmp/np560-battle-native-20260906-v1/` 中，直接调用 `cpu_breakpoint_insert`
却没有先初始化 GDB 服务，隔离 QEMU PID 75959 以 `-11` 退出。
QEMU 的 `cpu_handle_guest_debug → gdb_set_stop_cpu` 依赖已创建的 GDB process 状态；
这是本次取证方式的错误，不能据此声称游戏引发了 CPU 指令故障，也没有为此修改整机语义。
在 v2 中先初始化只使用本机 Unix socket 的调试服务，两个断点均正常命中并继续。
v1 的桥接进程也已关闭。另一次 Start 超时发生在开机初始化未完成时，原样保留失败记录。

本轮不增加测试平台、诊断专用 CPU 字段或 guest 特判。它新增了真实使用链路的证据，
不是源码修复，更不是 M2 或整机完成。声音、全部技能/装备/敌人规则、其它游戏、
存档覆盖/取消/异常路径仍未完成；大头犬原样本异常编号仍按前述范围保留。
