## 2. AudioCtl 目前证明了什么

展开后出现 `Active Audio Record Component` 版本资源，以及 `IAudioRecord/IAudioPlay`
类型库、录音/播放/文件格式方法；同时有 FLAC、GSM、ADPCM 等代码相关字符串和 LAME 接口。
PDB 路径为 `e:\rentacoder\tts\AudioCtl\Release\AudioCtl.pdb`。

这些证据指向通用 PC 录音播放组件，并非已经定位到 NP560 专用 codec。
`WAVE_FORMAT_LRC` 只是可见的格式名称，不能据此宣布存在 CYBIT LRC 解码器。
本轮没有在该组件中定位或执行 ESAC 帧处理函数。

## 3. 编译器中 NP560+ 的实际分组

以下全是 **Compile 的 x86 VA**，不是 DMCU 段地址。

- `1000EFE5..1000EFF5` 将字符串 `101C5CBC = "NP560+"` 与数值 `2` 注册。
  NP560T、NP580 等也注册该数值；不把它当成独一机型硬件标识。
- 分派表 `1003026F[2] = 1002FE6A`。
- `1002FE6A..1002FE9C` 设置高度 `120`、宽度 `240`，并令全局分组
  `[102323D8] = 2`。尺寸和实际型号一致，是对字符串证据的进一步交叉核对。
- 声音资源分派表 `10060673[2] = 1005FE87`。

## 4. 已核对的声音写入阶段没有调用 Sonix/Sitronix 编码器

`1005FE87` 首先比较 `.mp3`。MP3 走另一条资源路径；非 MP3 在 `1005FF58`
调用跳板 `1000104B -> 1005CB40`，第三参数为 `1`。

`1005CB40` 的相关行为：

- `1005CBBB` 和 `1005CC68` 读取 `[102323D8]`。
- 只有分组 `0` 改成 `mrc` 文件名并可调 `100011EA -> 100478F0`（Sonix 路径）。
- 只有分组 `4` 可调 `100011E5 -> 10047520`，后者装载
  `SitronixSoundLib.dll` 并解析 `SitronixBRC*` 接口。
- 分组 `2` 不进入以上两个编码调用，保留输入文件名返回。

之后 `1005FFB0` 经跳板 `10001924 -> 1005D310` 写入 `voice.tmp`。
该函数对正常非空输入求文件长度、分配缓冲、读入，再将 **同一缓冲、同一长度**
写到目标末尾：读调用在 `1005D3F2`，写调用在 `1005D408`；两者之间没有声音编码调用。
这说明 **已追到的这一阶段** 是原文件数据拼接，不能把旁边的 Sonix/Sitronix 库
当作 NP560+ 的 ESAC 实现。没有据此证明整个编译器、所有后续处理或其他版本绝无 ESAC。

作为有边界的补充扫描：在展开 Compile 中，对 ESAC-4 十档、LRC 五档、固件 ESAC-5
六档数值做连续 LE uint16/uint32/float32/float64 精确查找，均无匹配。
它只排除这些表的这些表示，不排除计算生成、非连续、缩放表或无名算法代码。

## 5. 下一步边界

本包保留作为机型和资源格式参考。不要继续展开 Sonix/Sitronix 来充当 NP560 的声音进展；
若再深入本包，必须先有它与原始 NPE 压缩帧契约相符的具体证据。
下一来源重点是 NP560/NPE 的声音制作或 codec SDK，而非通用录音组件、NWF 媒体封装器。

原始 NPE 的 `B6DE/B7AA/B816/B84E` 等契约及实际音轨仍是验收依据；
本轮没有改变模拟器 CPU、resident ROM、NAND、Web 或用户测试进程。

## 6. MRC2PCM 导出更正及原始音轨比较

同日补充。此前把 `MRC2PCM.DLL` 中的 `SonixCodec.dll`、`SonixDecFrame`
当成对另一库的引用，这个判断不正确：PE 导出目录 RVA `212A0`、长度 `4F`，
内部 DLL 名为 `SonixCodec.dll`，唯一导出 `SonixDecFrame` 的 RVA 是 `C3A0`。
因此有必要核对它自身的解码入口；不能用另一文件的导出表推测版本缺失。

### 静态展开与安全边界

原始文件及哈希见来源记录。ASPack 2.12 的四个块为 `1000/1C000`、
`22000/8000`、`2E460/1BA0`、`30000/3000`（RVA/展开长度，十六进制）；
原始入口 RVA `D7BE`。输出位于
`tmp/np560-noahmedia-static-20260907-v1/MRC2PCM.rva.bin`，221,184 bytes，SHA-256：
`1325c42e391886a07294b8b7189978187264a90d0404626ba2cef5b8c4661b5d`。

仍是 **文件偏移等于 RVA、ImageBase 为 `10000000`、未重建 IAT 的数据镜像**。
没有安装、加载、注册或执行原软件，也没有向模拟器接入宿主解码库。

原有带 sanitizer 的解包工具本次启动异常，停止后未产生目标镜像。
同一源码以 `-fno-pie -no-pie -fsanitize=address,undefined` 重新编译为
`tmp/np560-unaspack-fixed-base`，限时运行后四块全部展开、退出码 0，成功运行中
没有 sanitizer 报告。尚未证明旧构建崩溃的具体原因；不把它归因于原音轨或 QEMU。

### 已读到的入口与格式分派

以下地址全是 **MRC2PCM 的 x86 VA**，不是 DMCU 固件地址。

- `1000C3A0` 是单参数导出包装器，调用 `100021B0`，最终固定返回 `1`；
  不能将这个返回值直接解释为解码成功。
- `100021B0` 的初始化路径打开输入并读前两个字节。
  `10002380..10002388` 将其作为 LE 16 位数与 `0FFF` 相与后分派：

| 标记（十六进制） | 内部模式（十进制） |
| --- | ---: |
| 0FFF | 1 |
| 0FDF | 4 |
| 0FBF | 5 |
| 0F9F | 6 |
| 0F7F | 7 |
| 0F5F | 8 |
| 0F3F | 10 |
| 0F1F | 12 |
| 0EFF | 14 |
| 0EDF | 16 |

- 未匹配时进入 `100025F8`，设置模式 `3`，经 `10003130` 将文件位置退回开头。
- 模式分派表 `10002C09` 中，模式 `3` 到 `100026C5`，构造函数 `10003160`
  使用虚表 `1001D5D0`；解码虚函数为 `10004E20`，继续调用 `10005240`。
- 默认模式初始化 `10004E70` 在 `10004E91` 令输出计数字段 `context+8 = 0x80`。
  `100052CD..100052F0` 的正常输出循环将 **128 个 16 位样本**复制到 `context+10`。
  这是静态代码结论，本次没有实际运行解码。
- 默认模式的 `10004FF0` 有码率相关赋值：按输入代码分别出现
  `5000/6000/10000/12000/14000/16000/20000/24000/29000`，不是原 NPE
  格式 `9..18` 的 ESAC-4 十档分派。`context+214` 的“码率”含义仍是据数值和
  赋值位置推断，不把这段局部代码当作整个 DLL 所有算法的完整清单。

### 与现有 NPE 原始数据的实际比较

只读复核 `D:/Downloads/NP560plus游戏全集/英雄传奇.npe`：2,053,994 bytes，SHA-256：
`adea7c7442cefaea1c21ab7442cdd10d7796e7fc1dd3a5b98fd3c1c61dfa8c19`。
文件偏移 `0x1BFAD8` 起的 27,976-byte 音轨，SHA-256：
`300392f0771e5a88ed627466eb3f078380199fcf287ea405a0015612e0559a06`，
前 16 bytes 为 `20 0D 05 34 F1 6B CA 68 08 0F 0D DC 9C E8 D2 8B`。

将这段原始数据不作修改地交给上述文件入口，头两字节形成 `0D20`，
与 `0FFF` 相与仍为 `0D20`，**不会匹配任何显式格式标记，而会落入默认模式 3**。
这与原固件解析出的 NPE 格式 `13` 不能直接对应。

另外，对展开后的 MRC2PCM 数据镜像做 ESAC-4 十档数值连续表扫描，
LE/BE uint16、uint32、float32、float64 均未命中；这只排除这些完整表的这些表示。

结论边界：已经找到可读解码入口，但没有取得“该解码器兼容 NPE”的证据。
默认输出 128 样本不能单独证明不兼容，因为 NPE 的 160 样本推断仍有条件；
文件头不匹配也不能排除另一封装中的载荷使用相近算法。没有修改头部、强制模式、
跳过不明字节或进行试听，更不能宣称已恢复原厂解码。

本次进展是纠正导入/导出误判并收窄候选，不是音频功能交付。
**MP3/NPE 实际播放仍未恢复；CPU、ROM、NAND、Web 和用户实例均未修改。**
