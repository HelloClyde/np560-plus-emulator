# 整机快照：CPU 状态组件与不完整快照保护

更新：2026-09-06。**CPU 序列化组件已实现；完整整机快照仍未实现，不能用来保存游戏进度。**
这项工作不改变声音 ROM 的缺失状态，也不代替原厂存档和 NAND 持久化。

## 1. 已确认的实际缺陷

旧版没有 DMCU 目标 CPU 的 VMState，也没有 NP560 外设/NAND 的完整状态保存。
QEMU 通用 RAM/CPU-common 状态仍能生成一个报告 `completed` 的迁移文件，
所以“命令成功”并不表示它是一台可恢复的 NP560+。

用同一旧构建保存、冷恢复一个只设置 R0 后原地循环的诊断程序：

| 观察 | 保存前 | 同一旧构建冷恢复后（暂停） |
| --- | --- | --- |
| PC | `20:0004` | `20:0000` |
| R0 | `BEEF` | `0000` |
| 迁移报告 | `completed` | 进程正常加载，但目标 CPU 寄存器未恢复 |

旧对照构建是 `qemu-system-dmcu-pre-repeat-split-20260906`，SHA-256：
`e078605f59f6c425004a8e9f1ef4bea36222c00aecbbc0dadb7057c87af40276`。
它不是紧邻本次修改前的最新版；这里只用来复现同样缺少目标 VMState 的行为。

未加载用户 NAND 或日志，没有修改游戏。诊断迁移文件 2,201,104 bytes，位于
`E:/qemu-dmcu-build/np560-snapshot-boundary-20260906-v5/old-incomplete.vmstate`，
它是已证明不完整的反例，不是可用存档。

## 2. 实现内容与责任边界

`qemu-dmcu/target/dmcu/machine.c` 注册版本 1 的 `cpu/dmcu`：

- 显式序列化 PC、16 个 GPR、256 个 SFR、PSW、DSP SB/SE。
- 保留 IGNDS、CRIT、独立的 REP/REPB 当前状态，以及 DTU 错误请求抑制状态。
- 保留当前中断帧身份和暂停的循环状态；动态父中断栈逐项编码，不保存 GArray 指针或宿主结构体裸字节。
- 保留当前仍存放在 CPU env 中的物理输入电平；前端输入租约需在整机恢复接入时另行处理。
- 核对复位地址、代码/ROM 范围、启动上下文和 ROM 模式配置。宿主内存指针、总线和设备回调不从快照覆盖。
- 恢复时清除目的进程旧时间线的诊断环。除与当前/父中断上下文一起保留的观察字段外，
  历史诊断记录不是该版本的恢复契约，不能将加载前后诊断计数当连续运行记录。
- 拒绝未覆盖的旧 HLE 模式、错误版本、不匹配配置、截断流、非法帧身份和过大父栈计数。
  父栈的 `1 << 20` 限制是迁移输入的资源保护，不是声称硬件只能嵌套这些层。

QEMU 已有的 `cpu_common` 负责 halted/中断请求、异常索引及 TLB/TB 失效；
目标组件不在恢复时执行 DTU、确认中断、复位机器或改写 guest RAM。
目前组件级检查还没有证明“中断执行中整机存下，再冷恢复继续执行”的流程。

## 3. 整机保护及恢复失败清理

`hw/dmcu/np560.c` 在完整设备状态接齐之前：

- 通过 migration blocker 拒绝 `migrate` 和 `savevm`，不生成貌似有效的新整机快照。
- 单独设备状态导出也由设备保存回调拒绝，不能绕过上述保护；调用者可能留下失败文件，
  但请求明确返回错误，它不能作为可恢复的设备快照。
- 拒绝 `-incoming`；`-only-migratable` 也会明确失败。
- 注册全局加载准备检查，拒绝旧的不完整流。仅靠 CPU 的 `pre_load` 不够：
  旧流根本没有 `cpu/dmcu` 或 NP560 外设段，因而不会调用这些逐段检查。
- 原厂应用存档、NAND checkpoint/journal、备份恢复和正常开机保持原有路径。

定向检查还发现 QEMU `xen-load-devices-state` 路径在恢复失败后调用
`migration_incoming_state_destroy()`，却没有与其配对的 yank 注册，触发断言退出。
`migration/savevm.c` 已补齐注册及注册失败时的通道释放，无 NP560 地址/应用特判。
修改后同一旧流被拒绝时返回 QMP IO 错误，进程继续存活，诊断 CPU 寄存器不变。
同文件的设备状态保存错误路径还用短路 `||` 跳过了 `qemu_fclose()`，现已改为无论保存结果
都关闭通道；实际两次失败请求前后文件句柄均为 14，没有新增泄漏。

这不等于所有失败的 HMP 磁盘快照加载都保证原状态不变；通用 `load_snapshot`
在设备加载之前还会切换 block snapshot、执行机器复位。当前不向用户开放这一能力。

## 5. 下一步：真正接齐整机状态

保持上述保护，直到下面的状态能够一起保存、加载并继续执行：

1. LCD GRAM、命令参数进度、地址游标、扫描/显示模式；键盘驱动行、ECC/ADC 当前状态。
2. Timer/时基剩余计数和期限、虚拟时钟、待处理 IRQ/DTU，与 CPU 状态在同一时间点恢复。
3. DAC 当前输出、音频时钟/缓冲，以及 Web 恢复后的音频流和输入租约重新同步。
4. NAND data/OOB、控制器状态和增量日志时间线。必须明确回滚/分支策略，
   不能把旧 RAM 状态与更新后的 NAND 日志混用，也不能静默覆盖用户后来的存档。
5. 固件、ROM、设备参数、内存映射与快照格式的身份兼容检查；不只比较代码范围。
6. 同一构建下从原厂界面保存、结束进程、冷恢复，继续游戏/系统用途；
   特别覆盖有活动设备和嵌套中断的保存点。满足后再解除保护并接入日常入口。

组件实现是完整整机快照的前置工作，不把这个边界缩减为最终目标。
