# 原厂文件命令与 NPE 内容导入

日期：2026-09-05。目标是由原厂 guest 文件系统创建目录和写入真实内容，替代旧的离线
FAT/目录拼装诊断输入。本记录不把 RAM 传输工具称为完整 USB 控制器模拟。

## 代码来源与命令契约

原包 `NP560+.upd` slot 0，97,416 字节，SHA-256
`9cea0c9a5be8ab2d72e382cdc69d6314807a56d61517b2210807afbe597982e7`。
地址对应 [完整原厂反汇编](../disassembly/NP560_UPD_block0_full_reachable.asm)，不是独立 burner 的旧版本。
`50:7566` dispatcher 按 `50:0008` 命令号分派；反汇编的 `entry_N` 标签不是命令号。

| 命令 | handler / 实际函数 | 参数与行为 |
| --- | --- | --- |
| 1 | `50:76AA` | 初始化/挂载 storage 与文件服务；导入工具只接受成功，不自动格式化 |
| 3 | `51:CD88 → 50:E6DE` | 建目录；near `00:0FF0` 文件名，`50:0010/0012` 为字节长度；函数设置目录属性 `0x10` |
| 4 | `51:CAD6 → 50:C3F8(mode=0)` | 创建文件，已有文件时也可能截断；handle 写到 `50:0852/0854` |
| 5 | `51:BEC2 → 50:C3F8(mode=1)` | 只打开已存在文件；返回 handle，缺失叶文件为类别 `-10`、细节 `-7` |
| 6 | `51:BEC2 → 50:C3F8(mode=2)` | 已存在文件的写入模式；本轮不需要用它 |
| 7 | `51:D0D2 → 50:8DA6` | 从当前 handle 读取，目标固定 `00:0FF0`，请求固定 `0x2000` 字节；实际返回长度写回 `50:0010/0012` |
| 8 | `51:CF7A → 50:6008` | 当前 handle 写入；`50:0014/0016` 源 far pointer，`50:0010/0012` 请求/实际字节数 |
| 10 | `51:D618 → 51:0CD0` | 关闭并清零 handle，再映射内部状态为命令结果 |

原厂函数负责目录解析、文件分配、FAT/FTL 与 NAND 写入，不是宿主实现这些操作。
创建函数 mode 0 的依据为 `50:C646..C71A`：已有项进入原厂处理，缺失项进入创建分支；
mode 1 的缺失错误在 `50:C694..C69E`。不能因命令 4 名叫“创建”就认为它不会覆写文件。

结果类别取自原厂 `R0:R1` 与 `50:001A`，二者须一致；独立错误细节取自 `50:001C`。
不要将内层 `50:0860` 的数值直接当作完整宿主错误。

## 传输实现及边界

工具：[import_np560_vendor_file.py](../../scripts/import_np560_vendor_file.py)。
它启动自己的 QEMU 实例，只读加载输入 NAND，成功后才保存到一个全新的输出路径。
失败保留小型状态/命令记录并回收自身子进程，不保存大型失败 NAND，也不操作用户 Web 端口。

- guest harness 使用独立 `0xC104` 协议。只自主执行命令 23，之后等待文件操作请求，
  不自主执行整包写入或格式化/提交命令。
- 宿主仅传送文件名、文件内容及命令字段。字节按原厂 USB loader MOVB lane 规则编码；
  文件名先进入 `52:6000`，由普通 guest MOV/REP 复制到原厂 handler 读取的 `00:0FF0`。
- 复制时源逻辑指针是 `E000`、`DS1=00A4`，目标是 `0FF0`、`DS0=0`。
  DMCU 的 DS0/DS1 由地址 bit 15 选择，不能将 DS1 想成所有 MOV 源操作数的专属段。
- `debug-data-save` 读取 near data RAM 以核对文件名/读回数据；不能拿低地址 code-bus
  别名的物理内存视图替代这个缓冲区。没有扩大宿主对受保护低 SRAM 的写入窗口。
- 导入前以命令 5 检查文件，已存在即关闭并拒绝覆写；只有已经确认的 `(-10,-7)`
  缺失结果才执行命令 4。其他错误保持失败，不把错误统一解释为不存在。
- 以最多 8,192 字节分块调用命令 8；最后一块传输偶数填充，但 guest 写入长度保持真实
  文件长度。逐次核对实际写入数，关闭后重新打开，读取到 EOF 并逐字节比较全部源文件。
- `--verify-only` 在新 QEMU 实例上按同一路径冷读回源文件，不创建目录/文件，不输出 NAND。
  用于区分同一次运行的缓存回读与真正保存后还能读取的文件。

目录/文件写入走原厂 API 是一个实际能力进展，但 USB 枚举、端点 FIFO、原机文件交换
线协议、Web 内容导入入口尚未完成。harness 是显式传输程序，不是产品启动 PRG。

## 正常菜单进入 NPE：发现实际 resident 入口冲突

`tmp/np560-vendor-file-game-route-v2/` 从已显示的主菜单按真实矩阵执行
`Start → 娱乐 → 游戏世界 → NPE 列表`，前四步逐次 map 和 foreground acknowledgement 均为 1。
原厂浏览器正确显示 `英雄传奇.npe`，不是宿主画出的文件名。

第五步选择文件后没有进入游戏，发生首个控制流故障：

```text
25:DFD0  BD01 B6DE  SCALL 01:B6DE
01:B6DE  58F0       MOV [--R15], R0
...                 实际是旧安装代码中的指令/操作数流
01:C518  C620       RETS
INVALID_CONTROL=01:c518/c620>00:0025 SP=0d3a FP=0d5e IRQ=0
```

`INVALID_CONTROL_CONTEXT` 保存的栈顶是 `0000,0025,dfd4,...`，与额外压入一个 word 后
RETS 将原本 `0025:DFD4` 拆错一致。后续 `00:1039 WORD=2F58` 是错误控制流的后果，
不能当成要补的新 CPU 指令。

代码快照 `rom01-b6de.bin`、`rom01-c4e0.bin`、`caller25-df80.bin` 已保留。
builder 中 `APPLICATION_OPERATION_MODAL_SOURCE_REPAIR_INSTALLER_ADDRESS=0x01B000`，
生成物为 5,402 字节，范围 `[01:B000,01:C51A)`、末指令在 `01:C518`；
原包 source `42:DFD0` 独立读取为 `BD01 B6DE 50F6 74F0 6000`，证明调用不是错误反汇编或
宿主改写出来的。因此将这里当作“空闲 ROM 区”放入安装程序的旧假设不成立。
真实调用要使用 `01:B6DE`，当前镜像并没有给它提供正确的函数契约。

这次自然触发了之前仅静态确认的条件分支：

- `NPE_TRANSITION_GATE` 在源配置读取/写入后为 0，没有宿主清零；
- `03:438C → 32:5F86 → 32:B974 → 25:0000`；
- `NPE_TRANSITION_LEAF CALLS=1 RETURNS=0 HIGH=1`，进入 `25:DF62`；
- 该原厂高分支在 `25:DFD0` 调用上述 resident 入口。

旧诊断 NPE 镜像 gate 为 1，绕过这条分支，因此旧镜像的游戏操作成功不能证明这里已经实现。
仍不能仅凭这个分支就断定它一定是音频；需继续追真实输入、返回值和消费者。

当前结论是：**原厂文件 API 导入、跨实例读回及原厂列表显示通过，选择文件后的游戏启动未通过**。
下一项实现是恢复 `01:B6DE` 契约并清退占位旧安装代码，而不是回到离线 FAT、强制 gate=1
或添加成功返回桩。故障实例只用于诊断，未替换用户 8807/8808/8809。

## 后续接入

2026-09-05 后续严格运行更新：`01:B000..C519` 旧安装代码已签名核对后清退，CPU 对
未实现 TRAP 的静默放行也已修复。首个真实缺失入口提前定位到 `02:ACD8`，随后才是
`01:B6DE`；现场 `00:8800` 的全部 1 KB 与原 NPE section 16 起点逐字节相同。
新构建冷启动通过，但 NPE 选择仍未通过。后续以
[流后端与 ROM 缺口记录](../audio/np560_resident_stream_backend.md) 的顺序继续，不把上节旧返回栈
故障误认成第一分歧。

1. 原厂 API 完整写入、保存和新实例读回已通过；最小出厂生成输出与导入初始输入 hash 相同，闭合两条流程。
2. 从上述真实选择故障恢复 resident 入口，继续原厂 loader/runtime；不能将文件 API 或列表通过当作游戏已可玩。
3. 将相同设备侧文件功能接到真正的内容传输/USB 和 Web 设备操作；应用和游戏仍读取 guest 文件系统。
