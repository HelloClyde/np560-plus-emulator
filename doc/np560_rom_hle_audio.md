# ROM 01/02 音频 HLE：决策与当前实现

更新：2026-09-08。用户明确允许 01/02 缺失 ROM 服务采用 HLE。

## 当前架构

有原厂代码的系统/应用继续执行。对 01/02 已登记的缺失服务，可以由宿主实现其调用语义，
不再要求把成熟标准算法重新编成 DMCU 指令。HLE 不冒充原厂 mask-ROM 转储或逐周期实现。

MP3 目标链路是：原厂文件读取/压缩输入环 → 缺失 ROM 服务（HLE 解码）→ 原厂 PCM 缓冲 →
DTU/DAC → Web PCM。后端不能访问文件、NAND、Web 或设备时钟，不能直接播放宿主文件。
原有 CPU、PLL/音频请求修复仍有必要，HLE 不掩盖通用硬件错误。

旧 `rom-hle` 开关包含广泛服务拦截及旧诊断 UI/事件兼容路径，并与 `soc-rom-skeleton` 互斥。
**本路线不直接开启旧开关**。新服务必须独立启用、范围明确；未登记入口继续报告缺失。
即使调用地址在 01/02，也不能把未知入口全部返回成功或将原厂已有字节静默替换。

## 已实现：帧级后端与 QEMU 服务桥

- `qemu-dmcu/hw/dmcu/np560_mp3_codec.c/.h`：每实例独立解码历史，初始化、复位、释放与帧处理。
- 成熟库采用 [minimp3 官方实现](https://github.com/lieff/minimp3)，固定提交
  `ea99364f61c14656440e8d77e9c233ccf3124633`；原文件、CC0 许可证和 SHA256
  存于 `qemu-dmcu/hw/dmcu/minimp3/`。初期采用标量输出，不启用宿主 SIMD 分派。
- 接受调用者已送达的 MPEG Layer III 字节，只处理首个完整帧，返回消费字节数、采样率、
  声道数、每声道样本数及交错 PCM16。没有自动裁剪、增益调整或重采样。
- 短输入、坏头、不支持层/自由格式、CRC 错误均不提交历史或 PCM。层 III CRC 在调用库前检查。
- 完整帧被库消费但未产出 PCM 时单独返回 `NO_PCM`；不伪造静音/ready。
  库未公开每种无输出原因，不能把所有 `NO_PCM` 宣称为已经证明的位储备不足。
- 当前支持边界不是完整 MP3 标准符合性证明：自由格式明确未支持，所有畸形码流的检测、
  完整变格式/seek/错误恢复与性能仍须在服务接入后核验。

验证脚本：`scripts/tests/test_np560_mp3_hle_codec.py`。仅编译并调用上述同一后端，不运行 QEMU，
不向用户设备写内存。证据：`tmp/np560-mp3-hle-codec-20260907-v1/report.json`。

### 明确的服务边界与生命周期

`np560_mp3_hle.c/.h` 负责 guest 适配，`rom-mp3-hle-base` 默认 0（关闭）。
启用时要求 strict skeleton，拒绝旧 ROM/UI HLE 同时开启，并验证 01/02 内四个连续的
16-byte 服务门及版本标记。CPU 只在这些确切位置分派；调用后继续执行普通 RETS，
不会由宿主伪造返回地址。禁用入口及未登记的相邻 ROM 空洞仍触发缺失诊断。

| 服务 | 当前实验入口 | 状态与数据契约 |
| --- | --- | --- |
| reset | 02:A880 | 按已校验的 guest 工作区创建/复位实例，清 PCM/待取块状态 |
| decode_frame | 02:A890 | 只读取 guest 输入环已暂存的帧，发布每声道 576 个样本 |
| next_granule | 02:A8A0 | MPEG1 的后 576 样本，不再次消费压缩输入 |
| release | 02:A8B0 | 清除实例及工作区标记，重复释放不生成残留状态 |

工作区须为完整可写 RAM，不允许跨边界、未对齐或 MMIO；传回 R0/R2 状态，保留其它
调用现场。现有 guest 环管理和七入口封装仍负责原厂文件消费、回调、双缓冲与堆分配。
重建 session 的释放/初始化失败分支会清理宿主 codec；CPU/设备复位也清理全部实例。
尚未序列化宿主历史，整机快照继续明确拒绝。完整播放器暂停/跳转/结束/退出的生命周期
尚未验证，不能拿独立服务释放通过代替应用级控制通过。

`scripts/build_np560_mp3_hle.py` 记录所有更改和来源：只使用审查过的 ROM 空洞，
把旧重建 decoder 的三个入口改为服务门跳转，增加 release 并重连 session/factory。
原生算法保留作对照，不修改 NP560.PRG；manifest 清楚区分旧代码、HLE 门与新封装。
当前实验输出 `tmp/np560-mp3-hle-factory-20260907-v1/`：

- ROM SHA256：`5194ab5b2e25a65184bd1b54abc4f8fcf65a5b009dd519ab3deaba4f731a77da`。
- QEMU SHA256：`b2623e471acde1996a5a14fe00ee6e4ddad287dfc08e785ca059bc91105fd513`。
- 服务开关值 `174208`（`0x02A880`）。用户现有 Web 实例与 ROM 未替换；测试未保存 NAND。

## 下一实现项

1. 优先定位修复 ICR 竞争后仍存在的第 19 帧停顿：追 `16:EB0A/EC34` 文件续读、
   `08:3B48` ISR 与待输出 granule 的交接；区分请求语义、调度及调用契约，
   不重复将原厂已执行的重新开启当作缺失，也不以无依据的中断屏蔽替代修复。
2. 扩展已接入七入口的 MPEG2/2.5、错误和边界案例；保持禁用路径、原生封装回归。
3. 沿原厂 PCM 供给/回调进入 DTU、DAC；在正确 PLL/音频请求组合观察连续输出，随后完成
   暂停、继续、停止、曲目切换、EOF 与退出释放。不得靠修改时钟或固定 ready 宣称正常播放。
4. 核验真实应用下 codec 生命周期，未序列化历史前保持快照拒绝；确认后才向用户实例交付。
5. NPE 专用编码保持独立：允许 HLE，但 MP3 库不等于 ESAC-4/NPE 解码器。

## Version 2：缺失输入空间查询也使用 HLE（2026-09-08）

第 19 帧现场并非前台已证实死锁：十二次快照的被中断 PC、SP 和矩阵读取次数仍在变化，
只是进展很慢；音频 ISR 反复调用 01:49BE，而重建查询经过 factory、session、ring 三层封装。
因此进一步 HLE 化这个缺失的软件服务，不改变未经核实的 DAC 请求频率或中断仲裁。

`scripts/build_np560_mp3_hle.py --hle-free-words` 生成 version-2 的五个服务门。
新增 `02:A8C0`，重建的 `01:49BE` 跳到它；原厂 PRG 不变。默认不传参数仍生成原来
5194ab5b 的 version-1 镜像，已经重新逐字节确认。V2 镜像 SHA256：
`802eccc1e63e0f08887a600d446e8370a213fac702472caab41164ffaeded659`。
实际受测 QEMU SHA256：`14bbb22ec38220e5716c44b05205a9855b07a38192b42f304fc6c05c79c9c85f`。

HLE 查询尊重已有单例/session 忙状态，检查同一 NEW owner 签名、几何与 ring 状态，
返回 `766-ceil(available_bytes/2)`，保留半个已消费 word，拒绝异常游标和侵入两 word 保留区。
保留原重建封装的 R0/R2、3346 和 session STATUS 行为；不消费压缩输入，不修改读写游标、
PCM、ready、文件源或硬件请求。服务在 vCPU 上原子执行，不模拟 transient claim/release 写入；
这属于已授权 HLE 行为兼容，不声称恢复原厂内部布局或周期。
`input_space_calls/failures` 与解码失败计数分开，合法的 closed/busy 查询不混同解码失败。
