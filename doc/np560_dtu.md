# NP560 DTU：逐请求传输和原厂缓冲续填

日期：2026-09-05。地址使用 VMA03 运行地址；原始 PRG 文件偏移为运行地址减 030000。

后续三路周期定时器和 DPRAM 位寻址修正，已使原厂双路 DAC 寄存器传输通过；
最新构建与边界见 [三路 Timer 与 DPRAM](np560_periodic_timers_and_dpram.md)。
下文构建指纹属于本篇初次实现，DAC 可听输出仍未完成。

## 实际新增的能力

DMCU 的数据传输单元现已处理 ICR.ED 请求：每个请求移动一个 word/byte，按配置更新
指针、递减计数。计数非零时不进入 CPU ISR；归零请求以最高优先级交给原厂安装的向量。
这是 CPU/SoC 数据总线机制，不是宿主 SCALL、音频解码或 ROM 返回桩。

未经修改的原厂 `24:98FC..99CC` 已经由真实 Timer2 请求驱动，先设置 `83FF`、再设置
`8001`，完成 1023+1 次传输和两次数据块完成。新构建正常冷启动仍显示原厂桌面。
NPE 所需 `02:ACD8/AD92`、格式后端、DAC 与可听声音仍未完成。

## 规格依据及 NP560 与旧示意图的差异

已目视核对 `tmp/cnpatent/CN1916884A.pdf` 的完整相关图页：图 12/13 是 ICR，
图 16/17 是 DTUC/INC，图 18 是指针表；文字“数据传输单元”章节说明逐次传输、
计数归零和最高优先级完成中断。它是 DMCU 架构资料，不是完整 NP560 芯片手册。

| 项目 | 实现与证据 |
| --- | --- |
| 4 个通道 | ICR.PRI 在 ED=1 时作为通道号；非 ED 时仍是 CPU 优先级 |
| 控制寄存器 | `REG[21..24]`，与内存 `F142..F148` 共用状态；原厂播放使用 21/22 |
| 指针表 | `F0F0/F0F2` 是 source/destination 0，之后每通道递增 4 bytes；表本身不使用前台 DS |
| COUNT | NP560 使用低 10 位 `03FF`；原厂 `24:990E..9930/9966..9984` 明确按 1023 分块。旧专利图 16 只画低 8 位，不能原样套用 |
| WBT | bit 13：0=word，1=byte |
| SDS / DDS | bit 12 / 11：对应指针是否结合 DS0/DS1；按指针 bit 15 选择银行 |
| INC | bits 15:14：0 保持、1 递增目标、2 递增来源，按 WBT 加 1/2；3 为保留配置 |
| 请求 | EN/RQ/ED 同时设置、COUNT 非零时进行一次传输；非末次传输清 RQ |
| 完成 | COUNT 归零后保留完成请求，CPU 接受时清 RQ，live CPRI=3，与通道号无关 |
| 初始空通道 | COUNT=0 的 ED 请求不读写数据，进入 CPU 服务以便原厂首次填入计数 |

字节 lane 与 CPU 一致：逻辑偶地址选择 word 高字节。未使用 SDS/DDS 的数据访问走
现有 unbanked RAM/SFR 视图；使用它们时走数据银行。不能读取主机数组来避开设备副作用。
每次传输通过 QEMU AddressSpace，包含设备 MMIO 和可写代码区的正常写入失效机制。

CPU 的 IE/CPRI/CIRQ 和 ISR 屏蔽限制 CPU 进入服务，不阻挡已致能的 DTU 搬运；这是
按独立传输单元/CPU 仲裁关系采用的行为，尚无 NP560 真机时序观测。来源 EN 仍控制请求。
初版 DTU 统一在完成当前 CPU 指令的边界运行。2026-09-08 已修正外设请求路径：
已启用的传输在外设事件中持有 BQL 搬运，软件 RQ/配置仍在指令边界处理。
这样不再因宿主 vCPU 调度延迟而合并连续采样请求；空计数和完成仍由 CPU 服务。
没有整段缓冲伪造完成，仍受虚拟时间和真实请求约束。反例及当前边界见
[专用音频请求](np560_audio_requests.md#2026-09-08dtu-外设事件受理与双声道记时)。

## 原厂路径对应关系

- `24:97AC` 保存源缓冲，设置 `DSTP0=F1E0`、`DSTP1=F1E2`，清 DTUC0/1。
- `24:9A1E` 选择 Timer0/1/2 或其它来源，将 ICR 设为 `0041/0051`，启动相应计时器。
- `24:98FC` 是实际分块/续填逻辑，写 `83FF` 或 `8000 | 剩余长度`，切换双缓冲。
- 接收路径 `08:450C/469C` 将 SPI 数据口 `F204` 配为 source，使用 DTUC1 的递增目标
  配置 `4000 | 长度`；接收控制器本身尚未实现，不能把 DTU 可搬运称为已能录音。

这些原厂通路说明 DTU 是声音与其它数据流的实际共同依赖。算法缺口的进一步静态约束
记录在 [ROM 流后端](np560_resident_stream_backend.md)，不因传输硬件实现而关闭。

## 验证结果与边界

`scripts/test_np560_dtu.py` 在下面同一二进制上检查：

- 四个通道 × 保持/递增源/递增目标 × word/byte；SDS/DDS 各组合、非零 DS 下的
  unbanked 指针表、逐请求计数以及 EN 屏蔽后再致能。每一步读取实际 guest 寄存器和数据。
- 真实共享 SFR 总线读写，不只普通 RAM；跨 `7FFE → 8000` 切换不连续 DS 银行，
  byte 指针 `FFFF → 0000` 回绕；普通执行和软件请求 icount=5。
- 原厂 `24:98FC` 完整原字节，真实 Timer2 每次发请求：初始空计数触发首次续填，
  1023 次传输后第二次续填，最后 1 次完成。最终 `SRCP0=3800`、目标 word=`CAFE`、
  DTUC0=`8000`、DTUC1=`8001`、ICR=`0000`、SP=`4000`；DTU0 transfer=1024/completion=2。
  同一原厂函数在普通执行及 icount=5 均完成。测试 ISR 只计数、调用该函数，并于第三次
  IRQ 停止计时器；另一条旧 fixed tick 使用独立 RETI fixture，不冒充 Timer2。
- 初次 icount 原厂检查的 12 秒宿主期限不足，超时时硬件仍在推进：transfer=563、
  Timer2 expiry=564、无 DTU fault。改为 45 秒观察期限后完成；没有改变 guest period、
  搬运次数或原厂驱动来制造通过。
- 前一 `pre-dtu-20260905` 二进制在同一首个检查实际失败：计数保持 3 而非 2，
  目标保留 `A5A5`；证明检测到了原来的“请求没有搬运数据”，不是只新增日志字段。
- `test_np560_icr_vectors.py` 重新通过，新增空 ED 通道 0/3 的最高优先级请求检查。
  旧测试中“ED 永远不派给 CPU”的预期已改为正确的 COUNT=0 续填行为。
- `test_np560_timer2.py` 和 `test_np560_interrupt_psr.py` 重新通过；构建和定向
  whitespace/Python 语法检查通过。

冷启动记录 `tmp/np560-dtu-cold-boot-v1/report.json`：95.33 秒，零按键、零宿主 guest
内存写入、不保存 NAND；末三帧顶栏均为 0/5280 像素差异，CPU/ROM/NAND 故障检查通过。
已目视 `final.png`：学习桌面、左下开始和右下时间正常。这不是 NPE 或间歇性花屏验收。
新 DTU 构建本轮没有再次执行完整游戏路线；当前最早游戏 ROM 缺口仍由前版实际记录及
未变的 ROM 内容确定，不将旧运行记录改称为新构建游戏通过。

## 仍未实现或未证明

CPU 中断嵌套、精确总线周期占用、同时请求仲裁的真机顺序、休眠/掉电传输状态、完整
整机快照和相关外设仍有缺口。当前 DTU 与 CPU 仲裁均临时按来源向量升序选择同级请求。
保留 INC=3、奇地址 word 与总线失败不会伪造搬运/成功中断，而保留请求并记录
`FAULT_SOURCES`，重配 DTUC/ICR 后允许再试；精确硬件错误/异常机制仍须恢复。
指针回绕、屏蔽及同时事件的真机细节没有观测，合成检查不能提升其证据等级。

没有实现音频算法、DAC 波形或 Web 播放。不能以 DTU 功能关闭“音乐播放器不能播放”
和“NPE 完整游玩”的待办，更不能用它绕过 `02:ACD8/AD92`。
