# 原厂日历计算与 RTC 边界

2026-09-18。此项核对月份天数，不是完整 RTC、断电走时或跨午夜整机验收。

原厂 `31:7B9E` 对应 PRG source `4E:7B9E`，文件偏移
`0x2E7B9E..0x2E7C4F`，长度 178 字节。它读取参数 year/month，
通过 `52:52EE + month` 取基础天数；二月使用整除 400、4、100 的分支
增加闰日，月份 0 或大于 12 返回 0。

`scripts/tests/test_np560_original_calendar.py` 使用原厂字节，保持跳转 PC 偏移，
在 CS21 的无冲突区运行；每项执行前从真实指令总线逐字节核对。
基础月份表由诊断 guest 指令初始化为公历常量，不宣称本测试恢复了原厂表来源。
所有参数/初始化是 guest 指令，无 NAND、无用户实例或宿主 RAM 写入。

九项通过：1900/2000/2100 年二月分别 28/29/28；2024/2025 年二月分别
29/28；2025 年四月 30、十二月 31；月份 0/13 返回 0。返回栈一致，
CPU/ROM 异常为 none。1900 是计算边界，不意味着原厂日期界面允许设为 1900。
核心为 `af89a942…`，PRG 为已锁定的 `d555609e…`。

失败边界保留：首次采用 CS20:7B9E，落入现有 `20:76CA..7C55` 文件记录
代码覆盖区，出现跑飞而非正常返回；更换栈地址也未解决。确认覆盖区后，
改用 CS21:7B9E 才通过，并加执行前指令总线校验。不能将该失败归因于
闰年算法、UDIV 或栈硬件，也没有为此更改核心。

剩余工作：真实月份表初始化、原厂日期设置/提交/冷读回、午夜跨日/跨年、
RTC 的硬件寄存器与断电/休眠计时。桌面分钟递增和本项函数检查不能证明这些完成。
`seed_np560_factory_clock.py` 修改的是启动 NAND 日期记录，不是 RTC 硬件实现，
不应用它替代正常的原厂设置和持续计时路径。

## 启动记录与保存链静态核对

2026-09-18，直接反汇编当前 PRG，尚未做本节的整机设置/冷启动验收。
runtime `2F:4D94` 对应 source `4C:4D94..4EDA`，文件
`0x2C4D94..0x2C4EDB`。调用 `25:206E` 读取逻辑 `10:D01F` 的
12 字节到栈上，年使用前两字节小端值，其余字段取偏移 2/4/6/8/10。

校验范围为年 1901..2100、月 1..12、日 1..31、时小于 24、分秒小于 60。
月日时分秒先零扩展，因此没有负数输入问题。**这里没有按月份检查天数**，
不能拿这个启动记录校验器证明 2 月 31 日等日期会被拒绝。

通过时写入 DS=A1 的普通数据位置：

| 字段 | DS=A1 下的地址 | 宽度 |
| --- | --- | --- |
| 年 | 3846 | word |
| 月 | 3844 | byte |
| 日 | 3843 | byte |
| 时 | 3842 | byte |
| 分 | 3841 | byte |
| 秒 | 3840 | byte |

这些是数据寻址操作，不能仅凭地址称为硬件 RTC 寄存器；也不能与
LCD 前缓冲的 `50:3840` 混为一谈。

失败分支 `4C:4ECC` 调用 runtime `32:B2F4`，然后调用 `31:3FC0`：

- source `4F:B2F4..B346`（文件 `0x2FB2F4..0x2FB347`）逐字段写入
  `2006-07-01 08:00:00`；这是原厂默认值，不是宿主选定的日期。
- source `4E:3FC0..407E`（文件 `0x2E3FC0..0x2E407F`）从上述位置
  取值，组装相同的 12 字节布局，间隔字节置零；在 `4E:4072` 调用
  runtime `32:EBAE`，目标逻辑地址仍为 `10:D01F`、长度 12。
- source `4F:EBAE..EBEC` 继续调用 `33:0D7E`。当前 ROM 构建器和
  QEMU 已有该通用资源保存链 `32:EBAE -> 33:0D7E -> 28:0F92`
  的代码覆盖支持；这不等于此次已经动态证明日期记录成功落盘。

由此可定位正常保存入口，不必修改 NAND 日期代替原厂保存。下一步应在
隔离实例用原厂日期设置确认这些字段、保存调用和冷读回，再追踪秒/跨日更新者。
上述失败分支本身没有日期模态调用；首次启动完整流程是否另行打开设置页，
需要沿调用者继续确认，不能从这一个函数直接断言。
