# 原厂 MP3 播放状态和物理控制

更新：2026-09-08。属于 M2 音频接入核对，不是播放完成或独立测试平台。
现行方案允许 ROM 01/02 缺失服务 HLE；前面的原生实验为历史记录，最新统一构建结果见文末。

## 原始程序中的契约

以下均为原始 PRG 在实际 VMA03 映射下的地址。旧工具
`scripts/dump_np560_range.py` 打印的段号比实际段号大 `1D`；例如工具参数
`2A:4FFC+0x110` 对应实际 `0D:4FFC`，不能混用两套地址。

`0D:500C` 从 `50:7E06/7E08` 读取播放器 far pointer。
其字节字段 `+087A` 的值 5 是 MP3 控制模式；`+087C` 是播放状态。
原厂 D/F/G 快捷键分支均先检查 MP3 模式，再按状态转送事件：

| 物理键 | 矩阵位置 / 映射结果 | 原始分支及行为 |
| --- | --- | --- |
| D | 1 / 0064 | `0D:4FFC` 同时接受大写 0044；状态不为 1 才转送 0092 |
| F | 9 / 0066 | `0D:5060` 同时接受大写 0046；状态为 1 才转送 0092 |
| G | 17 / 0067 | `0D:50C4` 同时接受大写 0047；转送 0091 |

`0D:54BA` 调用实际 `24:8274`。后者对 0092 的处理为：

- 状态 1：`24:8516..853A` 写为 2，调用相应暂停服务。
- 状态 2：`24:85BA..85DE` 写为 1，调用相应继续服务。
- 其它状态：存在有效文件名时调用 `16:9516` 重新进入播放准备。
- 0091 且状态 1：`24:82AE..82D2` 写为 0，调用停止服务。

所以 1/2/0 可分别与播放、暂停、停止路径对应。但“状态为播放”不等于 DAC
已在连续产生正确声音。也不能将已在状态 1 时按 D 没有变化判为按键错误。

### 实际结果：未通过播放控制验证

- 原厂 MP3 对象指针一直为 `51:4A46`。文件选择期间模式为 0，最后返回 5；
  载入期间状态已为 1，未先按 D，也不是处于已证明的“暂停待播放”状态。
- `05-codec-10` 压缩消费位置为 2089 words，DAC 启用；下一样本消费位置回到
  208 words，DAC 关闭，但应用仍为模式 5、状态 1。重建 session/ring/core 的
  采样错误字段为 0。确切触发调用仍未捕获，不能说已经查明正常初始化或错误重试。
- D 的映射计数 34→35，原厂 modal 消费计数 31→32，实际事件 0064；状态仍为 1。
  这与原厂“正在播放时 D 不再次启动”的状态门限相容；不能把随后 DAC 再启用归功于 D。
- F 的 150 ms 物理脉冲后，等待 45 秒仍没有新的候选/映射事件 0066，验证失败。
  失败时矩阵已释放，固件的 `28D6=0009`、`2A8A=0009` 记录了该矩阵位置，
  `2A5C=1`，候选/映射仍保留 D，播放器状态仍为 1。
  因此不能用这次结果判定暂停服务本身失效；输入尚未完成事件交付。
- CPU 仍在原生解码（失败样本 `01:B0A6`），没有 ROM_MISSING、UNSUPPORTED
  或 INVALID_CONTROL。矩阵读取计数 8486→9249，不能称为整机或键盘硬件彻底停止。
- 后续“继续”和“停止”没有执行，不能列为通过；没有以 ACK 代替状态变化验收。

设备 PCM 仍不连续：`06-play-2` 的整个 0.2 秒 ring 切片为 `(-160,-160)`，
`06-play-6` 为 `(-239,-239)`。失败切片也捕获到 533 种样本对，说明设备并非
始终静音，但这不能抵消其它窗口的长时间保持值，更不等于正常听歌。

实验身份沿用 [性能记录](np560_mp3_performance.md)：QEMU `f46789be...`、
实验 ROM `5d2b27fb...`、只读 tone NAND `639e4707...`；完整 SHA 在报告中。
诊断脚本退出 1（按键观察失败），拥有的 QEMU 正常关闭、退出 0，
`unexpected_qemu_exit=false`。没有重启来掩盖超时，没有替换用户实例或保存 NAND。

## 快速 DCT32 后的完整原厂观察

记录：`tmp/np560-mp3-player-fast-dct-20260907-v1/report.json`。
QEMU 仍为 f46789…，ROM 为 89da6fc7…，完整身份见报告及
[性能记录](np560_mp3_performance.md)。同一原始 PRG、同一只读 NAND，
从桌面冷启动选歌，12 次观察后按 D/F/D/G；没有宿主写 guest RAM、逻辑按键注入，
没有超时重启、替换用户实例或保存 NAND。

与上一版不同，本次四个物理键均完成普通映射和原厂 modal 消费，每个恰好一次：
maps 34→35→36→37→38，modal ACK 31→32→33→34→35，事件依次
0064、0066、0064、0067。F 不再停在“矩阵已采到但未产生逻辑事件”的旧失败点。
这是该次场景的送达证据，不证明全部负载和键盘行为已经修好。

| 动作 | 实际采样结果 | 能得出的结论 |
| --- | --- | --- |
| 初始载入 | 模式 0→5，状态始终采到 1；DAC 开启后曾关闭、又开启 | 解码与真实设备连接保留；载入后状态/复位原因未结案 |
| D | 事件送达，状态仍 1；READY 曾回到 0、DAC 关闭后再开启 | 不能把重新开启归因于正确的 Play 行为；需要实际调用链 |
| F | 事件送达，之后三个间隔采样仍为状态 1；DAC 先关后开 | 未观察到稳定状态 2，暂停没有通过；不再只归因于输入未送达 |
| 第二次 D | 事件送达，状态仍 1，READY 0→1、DAC 关→开 | 因此前未建立暂停状态，不能算 Resume 通过 |
| G | 状态 1→0，DAC 关闭；后续三次五秒间隔观察均维持状态 0、PCM 全零 | 该次原厂停止动作和设备关闭有效；不是退出释放或全部控制完成 |

停止后 session BUSY=0、READY=1，handle6 的 96-byte 控制对象仍锁定，
lease handle7 仍保留；不能声称释放流程完成。所有已采样 session status/detail 为 0，
没有观察到 ROM_MISSING、UNSUPPORTED 或 INVALID_CONTROL，但这不能排除瞬态问题。

### 设备输出仍不连续

每份设备切片是 48 kHz 双声道出口的 9600 对样本，即 0.2 秒。

- `05-codec-12` 全部保持 `(-239,-239)`。
- `06-play-6` 全部保持 `(-277,-277)`。
- `06-pause-2` 有 516 种样本对，但最长连续保持 4648 对。
- `06-pause-3` 全部保持 `(-200,-541)`。
- `06-stop-3` 全零，与真实停止状态一致。

因此即使存在实际解码音频片段，也不能宣布正常听歌或双声道同步。
脚本的 `passed=true` 只代表该观察流程、原生 owner/PCM 和四键送达完成，
`playback_verified=false` 明确保留；脚本及拥有的 QEMU 退出均为 0。

## 状态写入者：原厂结束回调后重新打开曲目

记录：`tmp/np560-mp3-player-state-writes-20260907-v1/report.json` 和同目录
`player-state-writes.log`。仍为上述同一 QEMU、fast-DCT ROM、原始 PRG 和只读 NAND。
在原厂选歌并完成 12 次观察后，对拥有的 QEMU 附加宿主 GDB 硬件写观察点：
实际对象 `51:4A46 + 087C`，以及实际 96-byte owner 的 session READY。
不下 guest 软件断点、不写 RAM、不调用 QEMU 内部函数。断点暂停会影响时间，
本次只用于确认写入者和栈，不作为吞吐或实时性能测量。

观察窗口共有 36 次 word 变化，未达到 128 次上限；其中包括与状态相邻的低字节
文件名字节变化，不能把整 word 的每次变化都记作状态转换。剔除这些低字节变化后：

1. 原厂 `31:CEEC` 回调的 `31:CF1C` 在中断上下文将状态从 1 写为 3。
   连续捕获到五次；栈返回点是原厂 `08:3AB2`，对应从 `00:4AA8/4AAA`
   注册指针进入的回调跳板。没有在本窗口观察到状态 2 的写入。
2. 原厂主循环 `0D:48D4 → 22:7E6A`，后者在 `22:82D0` 调用
   `16:9516` 重新准备播放；`16:9DBC` 再把状态写成 1。
3. `1D:375C → 01:4804` 重新进入实验 codec 初始化。其释放旧 session
   的 `01:C288` 将 READY 清零，然后新的实际解码在 `01:C074` 发布 READY=1。
   栈及本次 ROM manifest 与这两个 writer 对上；不是未知写入者破坏 READY，
   也不应把这条路径误记为单纯调用 `01:485A` reset。
4. 最后的 G 由原厂 `24:82D2` 写状态 0，之后 DAC 保持关闭，观察流程退出 0。
   G 的停止仍不等于 owner 和核心释放；`playback_verified=false` 保留。

这确认了“结束回调 → 主循环重新开曲 → codec 重新初始化”的调用链，
**还没有证明为何提前走结束，也没有证明 F 已执行过暂停分支。**
原厂 `16:E8B8` 将 `01:49F8` 的 R0 bit0 反值写入 `BIT[8C].8`；
这个标志参与后续 drain/fade 路径。新实现的 short/busy 会返回 R0=0，
因此它们是否被误当结束是待验证假设，不能据此先改成固定 R0=1。
下一次沿此依赖观察 internal SRAM `F012` 的 89.11/89.15 和 `F018` 的 8C.8，
捕获实际返回寄存器和写入栈；不能错用同编号 SFR 槽位。

## 结束标志：本次实际是坏帧头，而非 short/busy

后续记录：`tmp/np560-mp3-player-end-writes-20260907-v1/`。
在上述两个观察点外，增加 internal SRAM F012/F018 的硬件写观察，
只打印选定位变化，栈从偶数地址打印，避免字节压栈导致的 word 错读。
本版 QEMU 的 `internal_data` 与板级 data RAM 共享 backing，日志也验证了同址；
选择 CPU 指针是明确 BIT 地址空间，不意味着本机另有一份不同的 F012 RAM。

捕获到两个关键事件：

- `16:E8B8` 将 8C.8 置位时，**R0=0、R2=3、3346=1**。本次实验 ROM 中
  3 是新 ring 适配器的帧头拒绝结果；不是 R2=1 短输入或 R2=7 busy。
  当时 `3352` 从 0829 推到 082A，符合拒绝头时实际跳过一个字节的路径。
- `16:E9A8` 随后设置 89.11，R1=4；结合原始 `E95A..E980` 错误计数
  分支，说明该事件经四次错误达到结束阈值。原厂结束请求不应被当作无依据的
  外设误报而直接屏蔽。89.15 原本已置位，是回调启用门限，不是本次首次 EOF。

失败时已保存的实际 heap 显示核心 `READ=1458`、消费 byte 数 `1058`（4184），
最近读取的 `HDR0/HDR1=AAAA/AAAA`、ring STATUS=3，原厂 writer 游标为 144E。
前一个 `05-codec-12` 样本还是 `FFFB/9264` 有效头，消费 09CB bytes。
原始 MP3 在 4179 附近确实存在 `FF FB 92 64`，不是文件在这里自然结束。
因此下一定位对象是输入环内容/续填/游标，而不是重新实现 MP3 标准算法。
**尚未确定 AAAA 是怎样进入读取结果的，也不能据此断言 NAND 坏了或游标算错。**
原始输入的完整原厂导入读回已有同 SHA 记录，可排除“源测试文件只有几帧”这类猜测；
仍需核对当前播放器的实际读取路径，不能用旧导入检查证明本次运行读取全部正确。

这次四硬件观察点显著干扰执行时间：D 未在 45 秒内送达，脚本如实退出 1，
F/D/G 未继续执行；拥有的 GDB 和 QEMU 正常退出 0，没有超时重启或保存 NAND。
本次没有再次捕获后续状态 3，不能把上一轮状态写日志与本轮拼成同一次完整时序。
失败报告与快照保留，不能将此流程列为控制通过。下一次快照同时保留 1536-byte
原始输入环；不增加与此故障无关的监控平台。

## 输入写入者与实际文件块：首帧重复初始化

记录：`tmp/np560-mp3-input-writes-20260907-v1/`，同一旧 fast-DCT factory ROM。
观察前移至选歌之前，只跟踪输入环 word 1000/1452，避免高频 IRQ 标志写观察的开销。
`16:EDFA` 的原始错误处理只调整音频阈值，不向输入环填 AAAA。

抓到 `16:E87C` 将 AAAA 写入 1452，源位于 `50:E99A` 附近的第二暂存区。
此时有原始搬运器和参数栈，不能再把它说成解码算法内部随意产生的帧头。
按 guest word 内字节顺序还原后，两个独立时点的**完整 4096-byte 内容**比较显示：

- `04-mp3-init`：D948 与文件 `[0,4096)` 全部一致，E948 与 `[4096,8192)` 全部一致。
- `05-codec-1`：D948 仍是首块；E948 已与 `[8192,12288)` 全部一致，
  而解码仅消费 835 bytes，输入环当前未读内容也仍在首块范围。
- 随后的环快照在消费 1253、1671、2089 bytes 时，所有当时可用未读字节都与
  源文件对应区间一致；问题收窄到下一文件块的交接，不是此前每个输入字都乱了。

注意 `AA` 本身也是本 MP3 的合法压缩/填充字节，不能称为已证明的 RAM 毒化标记。
在应读帧头的位置读到它才是错误。旧 GDB 在准备执行首份二进制 dump 后退出 -6，
没有取得该瞬间的二进制文件，具体 GDB 内部原因未明；首次写入日志和之前的 QMP
快照已保存，不能冒称取得了完整原子转储。脚本退出 1，拥有的 QEMU 退出 0。
后续诊断改用已有的只读 `x/hx` 路径，调试器失败时也保留独立 QMP 故障快照。

原厂在创建 codec 前已完成格式初始化，新封装却在首帧 FORMAT_CHANGE 再调用一次，
重置了压缩暂存区标志。针对性原厂代码检查已复现旧版第二缓冲请求 0→1；
修正封装后保持 0，PCM 不变。实现、镜像与未配置设备分支的回归见
[首帧回调修正](np560_mp3_factory_abi.md)。完整播放器中的块交接和控制仍须验证。

## 首帧策略实验的完整应用结果：控制改善，但传输未启动

记录：`tmp/np560-mp3-player-first-format-20260907-v1/report.json`。
ROM 为 `08ae5a8f…`，其它输入同上；从桌面冷启动选择原始 tone 文件，再按 D/F/D/G。
此次没有 GDB，不用调试器时间开销解释失败。四键各完成一次映射和 modal 消费，
maps 34→38、modal ACK 31→35，事件 0064/0066/0064/0067。

- F：模式 5，状态 1→2，DAC 关闭；三个五秒间隔样本均保持状态 2。
- D：状态 2→1，DAC 开启；六个五秒间隔样本保持状态 1。
- G：状态 1→0，DAC 关闭；三个五秒间隔样本保持状态 0。
- 预填后第二缓冲仍保存文件 `[4096,8192)`，没有出现旧构建的提前覆盖现场。

**不能把这写成真实音乐的暂停/续播全部通过。** 同一构建仅消费 835 bytes，
即前两帧；从 `05-codec-2` 至停止前一直没有继续推进，没有越过旧 4179-byte 故障边界。
owner BUSY=0、READY=1、status/detail=0，不是采样到 native 锁一直占用。
4AAC/4AAE/4AB0 均为 0240；F01C=3BF0，原厂解码分支所等的 8E.14/.15 未置位。

设备证据进一步限制原因判断：四个 DTU 通道计数全为 0；不是已观察到传输完成但
漏通知。`05-codec-12` T1 CONTROL/PRELOAD/EXPIRED 均为 0，T2 CONTROL/PRELOAD
为 0、EXPIRED=1200；恢复样本 T2 EXPIRED=1450，但 DTU 仍无传输。
DAC 虽启用且已有 108/108 次采样寄存器写入，`05-codec-12` 与 `06-resume-3`
的 9600 对设备样本全保持 `(106,106)`；暂停样本全零。故仍不能正常听歌。

下一步应检查初次原厂设备配置和 codec 初始化期间的 Timer/DTU 寄存器写入，
确定为什么本实验策略保留了软件状态却没建立实际传输；不能直接跳到补完成中断，
也不能凭 buffer 标志正确宣布首帧契约已完整实现。此实验 ROM 未替换用户版本。
观察脚本和自有 QEMU 均退出 0；`passed=true` 是观察流程结束，
`playback_verified=false` 明确保留，未保存 NAND或新增大型 NAND 副本。
