## 为什么前两帧后没有传输

原厂 `1D:3708 → 2F:A6BA → 08:2F22` 的首次配置传入采样率**编号**。
44.1 kHz 传入 6；之前的独立 codec 测试传入 44100，遗漏了这一区别。
`08:2FE4` 按编号读取 `32:BD96` 的八字节记录；大于 10 的参数走 raw-Hz 分支，
使用固定路由 01B8，选择 Timer1/2。编号 6 的原始记录是：

```text
AC44 03F8 0AE3 09C6
Hz   路由       音频 PLL 参数
```

`24:97AC` 的路由字段 03C0 选择两个非 Timer 请求源，设置 8E.12/.13；
`24:9A1E` 分别写 REG61=0041、REG60=0051。
REG61 对应 ICR 来源 17 → DTU0 → F1E0；REG60 是来源 16 → DTU1 → F1E2。
旧模型只有 Timer 请求发生器，DAC 只保持采样并供 Web 读取，没有这两路请求。
所以首次配置被保留后，T1/T2 不运行是正确的路径选择，不是已经证明 codec 清坏定时器。

旧二进制的独立原厂驱动反例保存在
`tmp/np560-audio-requests-before-20260907-v1/report.json`：已由原厂设置
DTUC0/1=8020、ICR61/60=0041/0051、DACC=0009，但双路实际搬运次数均为 0。
这是有界超时失败，不是音乐解码测试。

## 当前功能模型及证据边界

`08:38D0` 设置 REG[EA]，从 F2D4 比较/保存同一音频 PLL；在参数上设置 bit15、
清 bit14。现将 F2D4、banked 别名和直接 REG[EA] 接到同一状态；与相邻 CPU PLL
F2D2 共用既有 MMIO 窗口，避免添加大量银行映射。

专用时钟由 guest 硬件配置驱动，采用以下**推导模型**：

```text
N = AUDIO_PLL[12:5] + 1
D = AUDIO_PLL[4:0] + 1
frequency = 4 MHz × N / D / decimation
decimation = DACC.bit1 ? 1536 : 1024
```

CPU PLL 的同族比值有原厂频率计算依据；将其用于音频 PLL，以及 1024/1536
分频关系，由下列五条独立原厂表项共同约束，并非已取得完整时钟规格。

| 原厂编号 | 标称 Hz | 路由 | PLL 参数 | 模型整数 Hz |
| --- | ---: | --- | --- | ---: |
| 3 | 32000 | 03FA | 0AA6 | 31994 |
| 5 | 22050 | 03FA | 0FCE | 22048 |
| 6 | 44100 | 03F8 | 09C6 | 44084 |
| 8 | 24000 | 03FA | 100D | 23995 |
| 9 | 48000 | 03F8 | 0AA6 | 47991 |

误差小于 0.04%，但相近不等于已证明精确硬件公式。模型不读取软件 4A60/Hz，
不按 MP3 文件名强定频率，也不使用 Web 的 48 kHz 作为设备请求时钟。
目前仅支持 PLL[15:14]=10、DACC[3:1]=100/101，且既有 DAC 使能条件成立。
其它模式不会冒充正常请求；PLL 锁定、重配置相位、模拟滤波与精确时钟仍未知。

`np560_audio.c` 使用虚拟时钟 ptimer，每期锁存两路 ICR.RQ。
EN/IE、计数和完成服务仍由已有 CPU/DTU 仲裁；不直接搬整个缓冲，不调用 guest
函数，不修改软件 ready/完成位。暂停虚拟机不推进该时钟，设备复位清除旧计数。
`audio-pcm.request_clock` 仅提供只读状态；PCM 呈现仍走原来的寄存器采样链。

## 首次整机试验与新发现的 CPU 写回错误

`tmp/np560-mp3-player-audio-requests-20260907-v1/report.json` 使用上述 8680196c
硬件与 `08ae5a8f…` 首帧策略 ROM。实际消费 835→4597→6269 bytes，越过旧坏头
位置；D 后到 7941 停顿，F 后状态 2/DAC 关闭，D 恢复后到 10866，帧头仍有效。
`05-codec-12` 双路 DTU 各搬运 14976/完成 26；恢复第六样本各 28224/完成 49。
但设备采样仍长时间保持单值，G 未在有界期限内映射到 0067，流程退出 1，
自有 QEMU 正常退出 0，无保存 NAND。不能列为播放或停止控制通过。

更重要的是，同一整机读到 AUDIO_PLL=BDC6、模型请求频率 133370 Hz，而不是
预期 89C6/44084 Hz。原厂 `08:2FF4` 的 `MOV R7,[R7++]` 从 BDC4 读取 09C6，
旧 CPU 却在写入目标 R7 后再写回指针 BDC6，覆盖了刚加载的数据。
这说明直接在测试中设置正确 PLL 不足以验证原厂表加载路径。

该缺陷有通用反例：`tmp/np560-postincrement-load-before-20260907-v1/` 中，
R3 指向 3000、该位置存 09C6，执行 `MOV R3,[R3++]` 得到 3002 而不是 09C6。
修正在通用 MOV word/byte 后增量装载实现：读取旧指针内容，提交 AGU 增量，最后
写回加载目标；不是只在音频地址特判。依据包括原厂上述用法与架构资料 d176..178
中“操作数阶段计算间接地址/增量，最后阶段写回结果”的顺序。
字节目的与指针另一字节的合并、普通目标、FP/SP 同名情况都需要单独检查。
原厂 codec 预配置检查现也验证实际 F2D4 值，不能再次只测软件 Hz/完成标志。

CPU 修正后 QEMU SHA-256：
`426d48e2457dc2aa62f881a4352c845da7b068c8f7041113081ea82429c5a2a3`。
`tmp/np560-postincrement-load-after-20260907-v1/` 的 14 项通用字/字节/普通目标/
FP/SP 检查通过；`tmp/np560-agu-audio-regression-20260907-v1/` 的 16 项既有
AGU 修改器回归通过；同一版本的专用音频 16 项检查再次通过，位于
`tmp/np560-audio-requests-cpu-fixed-20260907-v1/`。
