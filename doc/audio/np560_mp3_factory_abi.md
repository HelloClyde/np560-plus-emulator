# 原厂 MP3 公共入口的原生重建与实际播放器接入

日期：2026-09-07。以下代码为明确标注的新 ROM 软件实现，不是原厂 mask-ROM 转储。

本轮已消除“只有显式 DS0:R3 测试对象才能调用解码器”的限制：原厂 `01:4804`
自行申请、锁定控制对象及核心工作区，其它原厂入口自行找到该对象，实际执行解码、
复位、缓冲查询和回调。完整原厂系统经物理键选入 NAND 中的 MP3 后也已执行这条路径，
并从实际输入产生 PCM。**仍不是完整播放器已可用：停止/退出自动释放、其余共享状态、
设备时序与实时性能尚未全部接通；低码率和 NPE 的独立缺口仍在。**

## 实现与所有权

生成器为 `scripts/build_np560_mp3_factory.py`。只改 resident 镜像中的明确空洞及
以下七个缺失入口的四字节跳转，不改原始 PRG、CPU、SoC、Web 或 NAND。
原厂调用栈参数保持原形式，不由 CPU 按 PC 拦截执行，不在宿主提供对象/PCM。

| 原厂入口 | 新实现 |
| --- | --- |
| 01:4804 | 释放原有实例（若有），通过原厂 allocator 申请并锁定 96-byte 对象，复制原厂 26-byte 参数，实际初始化 session |
| 01:485A | 复位输入环、位储备、滤波历史及四块 PCM，保留实例 |
| 01:4954 | 向两个原厂 far 输出参数返回当前实际 X0 缓冲指针 |
| 01:49BE | 返回实际输入环空余 word 数 |
| 01:49F8 | 调用 native 解码，返回原厂 bit0/3346 状态，完成后调度注册回调 |
| 01:46F2 | 注册格式回调，格式变化时传实际 Hz；原厂 2F:A6BA 本身支持此形式 |
| 01:46D4 | 注册完成回调；当前实际原厂调用者传 16:EDB2（原始函数体为 RETS） |

新增内部 `close` 实际 free/unlock 核心和控制对象。重复 close 不重复释放，
重新初始化会先归还旧实例；这些路径已运行验证。**没有把 EQ 的 46CC/46D0 冒充 close，
也尚未把原厂停止/退出动作自动连到 close。** 因而这一版仍须作为隔离实验镜像使用，
不能以“有关闭函数”声称应用退出已无泄漏。

控制对象前 80 bytes 保持 session 布局，80/82 为自身 handle/签名，84/88 是两个 far
回调，余字节保留。核心仍通过既有 lease 适配器申请，不占第五块初始化缓冲 2984。
回调以 guest 的 far 返回栈正常调用；两种返回续点分别处理带 Hz 参数和不带参数的情况，
不依赖回调保留临时寄存器。

### 私有根：新软件布局与证据边界

`00:3342/3344` 在本重建实现中定义为控制对象的 far 指针。这是紧邻已知 writer3340、
error3346 的 **新 codec 私有布局，归属是有静态核对的推断，不是已恢复的原厂字段**。
入口以四指令 CRIT test/set 将 segment 临时设为 FFFF，串行化查找、解码、复位、关闭；
返回时先发布 offset，再恢复 segment。对象保持原厂 heap 的锁定状态，指针不会随压缩移动。
非空根须通过 arena、对齐、近 bank 边界、对象签名与自身 handle 范围检查。
不同步的调用返回 BUSY，不把一个损坏指针当成功对象。

构建器拒绝新增的无法解释的直接引用，并核对已有命中：

- PRG `0A:D9FC`、`0A:EA64` 是 Unicode → GB2312 去高位映射数据行。
  `886C→3344`、`9648→3342` 可由字符编码独立算出，不是实际访存指令。
- resident `09:89B0/89B8` 是已有原生安装器的写入；`09:8930` 明确设 DS0=10，
  且后续逐条核对为直线常量写入，实际目标是 `08:3342/3344`，不是这两个 X0 字段。
- 新解码器的 requantize 常量页另有两个相同 word 模式，位于已验证 hash 的数据片段，
  不是代码。最初只考虑安装器的守卫因此拒绝构建；分类依据补齐后才通过，未删掉守卫。

扫描包括 word/byte 直接读写与算术、DS1 形式和两个字段的奇地址，但**没有排除所有
间接访问或未知 ROM 入口的占用**。清单明确 `original_private_layout_recovered=false`
和 `all_indirect_accesses_excluded=false`。构建必须显式启用
`--experimental-private-layout`；不借此新建硬件 RAM、假寄存器或隐蔽宿主状态。

## 原厂预填条件与新的状态发布

原始 `1D:390C..3938` 要求 F006 bit15 为 1，且已成功处理的数量达到 `51:2B10`，
才离开预填循环。该地址是双端口 SRAM，不是可随意做成恒定 ready 的硬件状态寄存器。

初版封装已产生 PCM，却没发布这个条件。完整原厂观察记录
`tmp/np560-mp3-player-priming-before-20260907-v1/` 在持续的解码过程中 F006 仍为 0000，
因此不能把它判为原厂初始化完成。

v3 在实际 PCM 和回调完成后以 `BSET BIT83.15` 发布这一位，初始化/成功复位与关闭
实际实例时撤销它；缺输入/BUSY 保留上一期已完成 PCM 的有效性，实际处理失败撤销。
其余 F006 位不改。**这是按已知消费条件重建的输出有效性发布；没有找回原厂生产者，
不宣称已解释 F006 的全部位或其它声音格式的相同语义。** 没有跳过原厂成功计数和检查，
更没有在初始化入口无条件设置 ready。

## 预填后的 QEMU 定时器并发缺陷

`tmp/np560-mp3-player-priming-after-20260907-v1/report.json` 是必须保留的失败：
v3 ROM 已在实际解码后发布 F006=8000，接着旧 QEMU 的
`ptimer_transaction_begin` 触发 `!s->in_transaction` 断言，进程退出 -6；
QMP 断线只是后果，不是把播放成功误判成通信问题。不能将该次的非零 PCM 判为可播放。

逐层核查没有发现 `dmcu_irq_raise()` 同步调用 DTU 再写回定时器；它只设置请求并唤醒 CPU，
因此没有采用“允许嵌套 ptimer 事务”的修补。真正发现的是直接 SFR 指令从 CPU helper
调用板级 timer/DAC 时绕过 MMIO 的 BQL 设备锁，可与主循环虚拟时钟回调并发。

只读 GDB 记录 `tmp/np560-sfr-device-lock-before-20260907-v2/` 的前五次实际访问：
T2C 读/写、DAC0 读/写、T2 读均 `locked=0`；随后数据总线别名访问 `locked=1`。
这证明了无锁路径，虽未取得此前 SIGABRT 当刻的完整栈，不能称为逐帧还原了那次竞争。
第一版诊断脚本未正确挂接多个 GDB breakpoint commands，未取得观测；v2 已修正。

修复位于 CPU `sfr_read` 和 `sfr_write_internal`：时钟、timer、DAC 的直接访问条件式
取得 BQL，写路径覆盖旧值读取、SFR backing 和设备副作用；MMIO/DTU 已持锁时不重复加锁。
CPU-only 寄存器保持原路径，板级设备入口新增持锁断言。**未改变 ptimer 事务规则或
移除原断言，未跳过计数器更新，未更改 guest 代码以绕过设备故障。**

修复后 `tmp/np560-sfr-device-lock-after-20260907-v1/report.json` 通过，直接和 MMIO
读写均持锁，包含 T2 counter 和 DAC。`scripts/tests/test_np560_timers.py` 也退出 0：三个
定时器正常/`icount=5`/暂停恢复及原厂全部六种双定时器路由通过；两个 DTU 声道均实际
传输 32 个样本并完成一次，T1/T2 的 icount 运行也通过。它们不代替完整应用播放验证。

`scripts/tests/test_np560_dtu.py` 完整退出 0，包括四通道/字节与 word/增址/别名/边界及
原厂 24:98FC 正常与 icount 的实际 1024 次传输、两次完成。声音回归
`tmp/np560-audio-lockfix-20260907-v1/` 的普通、icount、活动复位也通过：真实 DAC
PCM 正负样本、静音、原厂 08:33FA 渐变、暂停不推进音频、复位清除状态仍正确。

## 修复后完整应用：已送达 DAC，但不是正常听歌

`tmp/np560-mp3-player-priming-lockfix-20260907-v1/report.json` 使用同一 v3 ROM 和
未保存的 tone NAND，完整选择文件后观察 12 次，每次间隔 5 秒，最后正常退出 0。
无 ROM_MISSING、UNSUPPORTED 或 INVALID_CONTROL；先前崩溃在第 2 次采样后，
这次通过了该窗口。不能据一次观察声称所有并发错误已排除。

- `05-codec-3` DAC 实际启用；后续真实 DTU 搬运解码后的 X0 缓冲。
- `05-codec-12` DAC 写计数为 9325/9308，DTU 为 9216/9199（完成 16/14 次），
  `FAULT_SOURCES=0`；对应音频寄存器为 FE2A/FE2A/0009。
- 末次设备 ring 的 9600 个立体声帧（48 kHz，即 0.2 秒）**全部为 `(-470,-470)`**。
  两个定时器在该采样时均已停止，CPU 尚在 synthesis。其它采样 PC 也主要落在
  hybrid、synthesis 或它们调用的共享算术代码；这是粗观察，不是精确性能占比。

因此现在打通的是“完整原厂选歌 → 新 guest codec → 原厂缓冲 → DTU → DAC”，
不是连续音乐播放：初版直接矩阵/通用多 word 算术吞吐严重不足，持有的最后样本
不能冒充音乐；左右通道传输数差异还须核对，不能全归于性能。所有设备音频快照都
是只读且不连续的 0.2 秒 ring 切片，不拼成完整播放文件，不将其作为听感达标证据。

## 首帧重复格式初始化：2026-09-07 后续修正

沿坏帧头的追踪见 [播放控制记录](np560_mp3_play_controls.md)。原始播放器在
`1D:3708` 已调用 `2F:A6BA`，之后才创建 codec、在 `1D:37A6` 注册该回调，
预填压缩缓冲，再调用 `01:49F8`。新 ring 的第一帧 FORMAT_CHANGE=1 仅表示
**解码器自己尚无历史格式**，不能直接推成原厂设备还需要初始化。

旧重建封装无条件将这次变化通知 `2F:A6BA → 08:2F22 → 08:3262 → 08:3292`。
`08:32C6` 写 F014，将两块压缩暂存区的请求标志重新设为 1。实际第二块数据尚未消费，
于是续填又读取下一块，丢掉原先的 4096-byte 区间。这是重建软件回调契约的错误，
不是需要屏蔽原厂结束回调，也不是 MP3 标准算法缺失。

`build_np560_mp3_factory.py` 现在在已有 96-byte owner 的空闲偏移 92 保存新的
FIRST_FORMAT_SEEN，创建清零、成功 reset 清零。不扩大堆。只有第一次通知，同时
原厂完成位 8A.10 为 1 且实际 `4A60` Hz 等于新帧解析出的 Hz，才省去重复初始化。
没有配置过设备或 Hz 不一致仍调用原厂函数；后续格式变化仍通知，不按相同 Hz
永久禁用回调。实际 PCM、每段完成回调、错误和 ready 发布保持原路径。
这是新软件布局与有依据的调用策略，不称为取得原厂 mask-ROM 字节。

实验 ROM：`tmp/np560-mp3-first-format-factory-20260907-v1/resident.bin`，SHA256
`08ae5a8f0403e3eec4d3cd40deeb90514ca967680b24a97c6e9d42c8122211cc`。
仅封装/公共入口改变，完整解码核心仍为 fast-DCT core v2；封装 2200→2270 bytes，
由已检查空洞分配到 `01:2A40`，未改 QEMU、原 PRG、Web 或输入 NAND。

针对性 guest 检查从真实压缩头调用原厂 parser 和格式初始化，再设置明确标注的
隔离双缓冲控制向量，最后经七入口实际解码三帧；不是向用户实例注入标志。

- `tmp/np560-mp3-preconfigured-before-20260907-v1`：旧 ROM 的 173 项中一项
  失败，第二缓冲请求期望 0、实为 1。失败原件保留。
- `tmp/np560-mp3-preconfigured-after-20260907-v1`：新 ROM 的同一 173 项通过。

  167 项仍通过，首帧确实调用原厂函数完成设备配置，没有简单禁用初始回调。

值的 SHA 仍为 `2c932993c6c1f4ff954674e7ece045942693e60f451c6dfe29a29a67d96b387d`，
与独立 FFmpeg 最大差异 1。它们证明本处契约修正和有限 PCM 回归，不代表整曲、
