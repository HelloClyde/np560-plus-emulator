## 已确认的调用关系

原厂 `31:F312..F3A0` 接收一个 word 模式参数，保留 R0..R3：

- 有符号 `1 <= mode <= 13`：取 `30:5966 + (mode - 1) * 20`。
- 其它模式：取同一张表的首项 `30:5966`。
- 两条路径都压入 `count=10` 和 far pointer，调用 `01:4674`，然后清六字节参数栈。
- 合法模式调用无显式参数的 `01:46CC`，设置 `BIT[8C].10`；
  默认模式调用 `01:46D0`，清该位。两者随后都调用原厂 `30:6C9E`。
- `31:B774` 的系统初始化传入模式 0；`33:4D82` 是另一层参数转发包装。
  后者有 `0D:329A/59BE/5CCA`、`0E:B610`、`18:2236` 五个对齐 SCALL 调用候选，
  所检查上下文为连贯代码；其中一些值从 `33:5A2E` 字节表取得。

因此这组服务不是只在选择 NPE 后才需要：系统初始化已经存在调用。
这不证明初始化时可以安全跳过它们，也不证明它们就是 NPE 解码器。

`30:5966..5A69` 是 13 组、每组十个 word，共 260 字节。
第一组为 `8000 8000 8000 8000 8000 8000 6101 6101 6101 5943`。
这些数值的分布可以提示处理系数，但不足以确定频段、量化格式、目标 SRAM 或实际算法。

## 已在 PRG 内的后续处理

`30:6C9E..6D9C` 是完整原厂函数，不需要补一个新 ROM 桩。
它读取 `51:285C`、内部 `4A66/4A72`，做除法、范围限制和表查询；
`BIT[8C].10` 会使查询前的索引额外减 2，最终更新内部 `33D8/4A70`。
这闭合了模式位的一个消费者，但没有揭示 `01:4674` 的数据目标或处理过程。

全 PRG 短操作码扫描另有 `08:13C2/14E6/2A34`、`09:4290` 的位写入匹配；
检查周围字节是数据形态，不能作为已发现的原厂执行路径。扫描匹配不等于函数引用。

## 当前实现边界与下一步

`build_np560_vma03_soc_rom.py` 仍为三个入口生成 `RETS` 临时桩，本轮没有替换算法，
只把旧的推测性命名改成实际调用契约。既有用户镜像未改，也没有因移除桩而制造启动回退。
“严格 codec 空洞镜像”仍含这些桩，不能把其 `ROM_MISSING=none` 当成所有服务已实现。
`02:ACD8` 是最近游戏记录遇到的显式空洞，不是此前所有服务都正确的证明。

恢复这组服务还需要真实目标状态、启停副作用及运算消费者的证据；
不能只复制十个 word 到任意空闲地址，再把其余入口实现为无操作。
若继续恢复，应优先查这组表模式的调用者/消费者及原始模块合成关系；
没有依据时不要把它与 `ACD8`、`AD92` 或 `B6DE` 后端强行别名。

本轮另外修复了有独立架构证据的 [普通 Y 指针内存视图](../cpu/np560_y_pointer_memory.md)。
这是 CPU 修正，不作为本篇三个 ROM 服务已经实现的证据。
