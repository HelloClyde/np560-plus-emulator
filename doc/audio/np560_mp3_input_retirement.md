# MP3 HLE v3：PCM 交付与输入回收

记录：2026-09-08。属于用户已授权的 ROM 01/02 HLE 路线。
这是**新的兼容性实现，不是找回的原厂 mask-ROM 算法或私有布局**。

## 已复现的冲突

原始 PRG SHA256 为 `d555609e03ece17f42c1881beeb88361572f18621161de67bc9dc765857089f5`。

- `16:EA42` 调用 `01:49BE`，把返回值作为可以追加的 word 数。
  当前和备用来源都不足、`BIT89.14` 清除时，由原厂 `16:EA94` 设置 `BIT89.7`。
- `16:E89C` 在调用 `01:49F8` 前保存 `3352`，随后读取更新后的消费位置。
  `16:E906..E924` 再调用 `01:49BE`，比较本次消费增量与 `766 - 返回值`；
  增量不小于该余量且 EOF 标志已设置时，置 `BIT89.11`。
- `08:3B60` 检查 `BIT89.11`，转入原厂结束处理，不能当无关状态位忽略。
- 旧适配器在 MPEG-1 第一 granule 就回收整帧输入并增加消费量，而第二 granule
  仍留在解码器。原厂可能在这 576 个采样交付之前发出结束请求。

`test_np560_mp3_factory.py --eof-tail --preconfigured-format --preconfigured-selector`
使用原厂采样率配置、原厂续填器和原厂消费函数。有限前缀由 guest 自己提供，
EOF 由原厂续填器设置；没有宿主 RAM 注入、NAND 或替代结束回调。
MPEG-1 两帧/普通时钟、三帧/icount=5 均复现最后一帧前半部后的提前结束标志。
旧解码 PCM 本身与 FFmpeg 差异至多 1，故不能将此错误归因于标准 MP3 算法。

早期夹具遗漏原厂预配置，首帧格式回调清除了 EOF，造成假阴性。
现已要求真实预配置并逐 granule 检查 EOF 保持。另有一项夹具预期已修正：
备用输入不可用应保持 BIT8A.1=1，不沿用非 EOF 夹具的“备用已填充”预期。
失败文件全部保留，不能以早期的 passed 推论 EOF 正确。

## v3 的明确软件契约

新字段仅在已分配的 codec 工作区内：`+60` 回收目标、`+62` 待回收、`+64` 已暂存。

1. 复制完整压缩帧到已有 scratch，但该帧仍占有输入环；第一 granule 不增加公开消费量。
2. MPEG-1 第二 granule 交付时才发布整帧消费量；LSF 一次完成。32-bit word 文件位置
   仍保留 seek 基数和跨奇数字节帧的进位，不将其重置成宿主局部偏移。
3. `01:49BE` 先按仍占有的输入窗口计算安全可写量，再回收已完成帧。
   第一次返回保守的空间额度，第二次查询可见释放后的空间，不会重复回收。
   这使原厂消费判断比较的是包含本次完成帧的窗口，而非已扣除它的窗口。
4. 若调用者不查询空间而直接继续解码，在下一帧开始前完成回收；不会重解同一帧。
5. 初始化/复位清空新状态；坏头重同步、CRC 拒绝、短输入保持原有错误语义。
   HLE 查询校验回收标志、长度、目标、环余量与 pending 状态，错误时不回收。

**v3 的空间查询有明确的回收副作用，不再沿用 v2“只读输入游标”的定义。**
返回值始终不超过实际可安全写入的空间；不根据调用 PC 改返回值，不修改原厂 EOF、
ready、EN 或文件占用位，不读宿主整首 MP3，不改 DTU/DAC 时钟。
同一私有 ring 也实现此规则，便于独立核对 HLE 与 guest 路径。

默认构建仍为原 v1；`--hle-free-words` 单独使用仍为 v2。
同时加 `--deferred-input-retirement` 才生成 v3，旧 ring 字节保留且标为 retired。
不自动推广到用户 Web 实例。
