## 关闭区间内的第二次停止（2026-09-18）

复核原有不暂停录音的完整控制事件，而非只看 enabled 翻转：同一 `08:478E/4792`
在 DAC 已关闭时还会再次执行。六次交接的事件边界一致：

| 虚拟时间区段 | 实测 |
| --- | --- |
| 首次 `08:478E` → 第二次 `08:478E` | 50.032458–50.032459 ms |
| 第二次关闭写 → `08:38F4` 配置音频 PLL | 37.891916–38.050917 ms |
| PLL 写 → `08:4718` 真正重开 DAC | 4.986166–4.987209 ms |

所以约 93 ms 并非一整段解码耗时；其中约 50 ms 是两次停止写之间的时间。
新增可选 `--profile-audio-reopen` 在测速窗口外、有界 12 秒内只读采样最多三次
关闭区间：音频包前后夹住 CPU 状态，跨重开采样单独标记；不改 guest、不使用
断点、不连接用户 journal。QMP 采样改变宿主负载，不能作新的速度对照。

沿重开配置/文件与对象路径拆分，不能用强制跳过停止来制造“无缝播放”。

## 第二次停止的动态调用栈已确认

`--profile-audio-reopen-stack` 仅在关闭区间采到等待位置后暂停一次，再读取一致的
CPU、96 字节内部栈与 F010..F017，最后恢复。不会改 guest 栈/状态；该模式不再
声称整个区段无暂停。要求三段完整且均有栈，缺失则失败。

`np560-audio-reopen-stack-20260918-v1` 三段都没有栈：运行中 PC 为 47FE，暂停后
实际为 47FA，旧筛选条件把快照排除。该版本仅导航 passed=true，不算栈证据。
v2 保留 trigger_cpu 与暂停 PC，DAC 仍关闭才采集；三个栈齐全，passed=true，
QEMU exit=0。SP 分别为 0EB2、0EF6、0EE4，暂停 PC 均为 `08:47FA`。

按未修改函数的 push/pop 顺序和 SCALL 的 CS/PC 两 word 布局核对，而非在栈里
任意搜索相似数值；三组对应偏移完全相同：

| 相对 SP 字节偏移 | 返回内容 | 对应调用 |
| --- | --- | --- |
| +18 | 478A（near） | `08:4786 → 08:47A4` |
| +26/+28 | 0008:3284 | `08:3280 → 08:475E` |
| +34/+36 | 0032:3052 | `32:304E → 08:3262` |
| +44/+46 | 0033:6652 | `33:664E → 32:3032` |
| +50/+52 | 0031:CF22 | `31:CF1E → 33:664C` |

因此实际第二次停止调用者是原厂播放器结束处理 `31:CF1E`，不是上一节候选的
`08:2F3C` 配置入口，也不是 HLE codec 自行调用停止。PRG 静态核对地址用
`dump_np560_range.py 4F:3020+0x60 50:6620+0x40 4E:CF00+0x40`（source 地址，
不是 runtime）。`31:CF06..CF1C` 先写播放器 state=3，然后调用该关闭链。

三个快照 F010 均为 8011：`32:303A..3046` 的 `F010 & FFF0 == 8010` 条件成立，
`08:3266` 的 bit2 未置、`326E` 的 bit11 未置，故确实进入专用 DAC 停止分支。
这证明本次重复停止由原厂当前状态驱动，不支持直接删除调用；尚不等于证明所有
状态生成、缺失 ROM 服务和真实硬件时序均正确。余下约 38 ms 仍需沿第二次停止
返回之后的释放/重开处理定位。
