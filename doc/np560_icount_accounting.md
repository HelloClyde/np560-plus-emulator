# DMCU 指令计数：中途退出翻译块的多计时修复

日期：2026-09-08。属于 M2 音频的 CPU/设备相对时间前置修复；不是完成硬件周期模型。

## 发现及修复

QEMU `accel/tcg/translator.c::gen_tb_start/gen_tb_end` 在翻译块入口一次扣除整个块的
指令数。DMCU C helper 则可能在块内任一指令后退出：REP/REPB 回跳、CRIT/IGNDS
窗口结束、SFR 状态改变，以及缺失 ROM/不支持指令的直接 longjmp。
旧实现没有撤销未执行尾部的计数；后继块会再次计数。正确的寄存器和中断返回地址
不能证明指令时间正确，旧行为回归没有覆盖这个断言。

`target/dmcu/translate.c::dmcu_tr_init_disas_context` 现对 `CF_USE_ICOUNT` 使用
单指令块，精确覆盖动态退出和 helper longjmp；普通非 icount 路径保留现有
16 指令块与标准块连接。没有改动通用 QEMU 时钟、PLL、采样率、原厂 ready、
DTU 计数器或 PCM，也没有扩大 HLE 到其它应用地址。

这是一项正确性优先的实现选择，**不是提速**。后续如恢复 icount 多指令块，必须同时
正确处理正常早退、异常早退、MMIO 重启以及计数预算，不能只给返回路径补一个退款。

## 周期资料核对及尚未实现部分

本次用 PDF 技能渲染并目视原始 `tmp/cnpatent/CN1916884A.pdf`，没有只信任网页 OCR：

- PDF 第 18 页区分 A（内部 ROM/FLASH 取指、内部操作数）与 B（外部取指、内部
  操作数），明确表中周期不包含流水线冲突/暂停。第 20–22 页宽 ADD 等确实写有
  “1 或 2”；不能把表里的不确定值统一解释为一个周期。
- 第 15 页定义外存片选边界、WS 最多插入三个系统时钟等待；第一外存区的 WS 来自
  SOCR，后续区来自 EMCR。应结合已记录的原厂 EMCR 初始化与真实总线路径计算，
  不能只按 guest 文件的存放位置猜内外存。
- 第 16 页及第 140 页图 21/22 定义 CLKSEL、写保护及非 PLL 频率表。已有 Timer
  模型并不意味着 CPU 执行速度已随 CLKCON/PLL 正确变化。

渲染文件保留在 `tmp/pdfs/cpu-timing-20260908/`；相关既有契约见
[CLKCON 写保护](np560_clock_write_protection.md)和
[常驻 ROM 启动契约](NP560_resident_boot_contract.md)。

当前修复的是 **QEMU 指令计数**。`shift=5` 仍是一条指令 32 ns，`auto` 仍随宿主
调节比例，二者都不等于 DMCU 实际机器周期。PLL 锁定、内外存访问/流水线重叠、
时钟切换相位和 HLE 服务耗时仍需分别建模。不能因此宣布音频或 M2 完成，
也不能把先前 auto 停顿直接全部归因于本次错误，需重新跑完整播放器。

## 完整播放器：auto 仍失败

`tmp/np560-mp3-icount-precise-auto-20260908-v1/{report,delivery-analysis}.json`
使用同一 `da55c492…`、HLE v4、原厂 PRG/UPD/tone NAND、精简观察、物理选曲，
12 次观察及 60 秒墙钟录音上限。进程退出 0，无 NAND 保存，用户 Web 未修改。

- 观察 1–12 仍固定在 19 帧 / 38 granule / 38 次 PCM 复制；输入空间查询继续到
  109887，三类失败计数均为 0，未释放会话。这不是正常连续播放。
- 记录了 934995 帧 / 19.4790625 秒设备 PCM，SHA256
  `faa937eb4b5c671b48e6efe3072f4bb1adcf1c102ac18d0f547c32d06d5af2e0`。
  开始零输出 1.670292 秒；第 2.152875 秒起 `(448,448)` 保持至末尾，共
  17.326188 秒。第 10 秒窗口双路零新写入，各 42144 次空请求、交流 RMS=0。
- 只捕获到开始阶段的 64 个续填事件；左路 32/32、右路 22/32 入选，短事件总延迟
  中位数 44.544 / 46.080 µs。不是稳定播放区间，不能以较低中位数宣称声音改善。
- 原厂播放器从第一次观察起仍 mode=0/state=1；Timer2 已停止在 1200 次到期，
  两路 DTU 都停在 20736 次搬运 / 36 次完成，ICR60/61=0052/0042（EN=0）。
  解码器有 ready=1/phase=1。这些是后续定位线索，**不是授权强制 EN/ready**。

`passed=true` 仅代表探针完成，`playback_verified=false`。精确计数修复成立，但
不能解释全部 auto 播放停顿；auto 仍不采用为默认。需与同构建固定指令时间对照，
再实现有依据的 CLKCON/PLL 与机器周期推进，而不是继续调 host 自适应比例。

## 同构建固定 shift=5 对照：连续推进，但不是实时交付

`tmp/np560-mp3-icount-precise-fixed5-20260908-v1/report.json`、
`delivery-analysis-v2.json` 使用与 auto 完全相同的输入身份、物理路径、观察及录音配置，
只将 icount 改为固定 5；与 auto 串行执行，没有其它自建 QEMU 并行争用。

- 观察 3 已到 24 帧，最终 178 帧 / 355 granule / 355 次复制，查询 703；所有解码、
  查询及复制错误为 0，有一次释放、当前仍一个会话。不能将累计帧数除以 WAV 时长
  当成吞吐率，两者观察范围不同。
- 原厂播放器观察 2 起为 mode=5/state=1，持续产生新 PCM，未重现 auto 的第 19 帧
  停顿。没有主动改模式、EN、ready 或强制结束原厂等待。
- 644 个续填事件，两路各 322 个，各 321 个进入既定的短 576 样本筛选；总延迟
  中位数 1.376 / 1.408 µs。该单位取决于实验性的每指令 32 ns，**不是实测硬件周期**。
- 60 秒墙钟上限内捕获 149111 帧 / 3.106479 秒设备音频，PCM SHA256
  `55358d90a443bd3ce50465632d65e0331dd23a40322fc4c2333fcdf161a37c13`。
  初始零输出 1.533958 秒，余下约 1.572521 秒为音调；整段只有 1 帧左右不同。
- 第 2.000313–3.001917 秒窗口双路各 44157 次真实请求写入，零空请求、零重复写入、
  零请求外写入；FFT 原始 bin 为 440.294 Hz，分辨率约 0.998 Hz。这支持该短窗口
  音调接近 440 Hz，不应把 bin 小数位当成测量精度。
- 录音含显式暂停以抓取大块只读状态，因此不能拿 60/3.106 推断无诊断 Web 的速度。
  当前仍没有无暂停实时播放、整首尾部、曲目交接及暂停/续播的同版本完整证明。
  录音在首次曲目结束前停止，虽然后续解码观察跨过一次释放，不能借此宣称交接无缝。

分析器原先多减了一个窗口，漏掉最后完整一秒；短录音因此只剩混入启动静音的
1–2 秒窗口。现修正循环上界，原分析保留为 `delivery-analysis.json`，另存 v2。
没有改 WAV 或既有窗口结果，也没有把录音时长扩大为全曲。

本轮结论：精确计数是一项确定修复；固定相对推进下的短稳态输出来到了每请求一次
真实写入，但 auto 仍失败、固定 32 ns 也不是硬件模型。下一项应将 CPU 的实际
时钟选择与有依据的指令/访存周期接到设备时间，再评估和优化真实 CPU 执行成本。
不得据短音调成功默认切换用户 Web，或把 M2 标为完成。
