## 历史修正：先移除静默跳过 TRAP 的 CPU 错误

旧 `target/dmcu/helper.c` 对所有 `0Fxx` 只打印 `TRAP ... stubbed`，然后继续执行。
只有显式 skeleton 模式才把 resident 范围的 `0F00` 识别成缺失 ROM。普通 Web 默认关闭
该模式，因此大片未恢复区域会被逐字跳过，并可能撞上另一函数及其 RETS。
`ROM_HLE=off` 或 `ROM_MISSING=none` 单独都不能排除这个错误。

该次修正使未实现的 TRAP 进入现有 unsupported 停机路径，保留 PC、寄存器和先前控制流；
显式 skeleton 模式继续报告更具体的 `ROM_MISSING`。这不是实现了真实 TRAP 异常机制，
而是消除了把未知语义当作 NOP 的错误；真实 TRAP 的向量与异常约定仍待恢复。

当时的 `scripts/test_np560_trap_strict.py` 检查 PRG 的 `0F00/0F37`、普通 resident 的 `0F00`，
以及显式 skeleton 缺口。陷阱后的指令会把 R0 从 `1234` 改为 `BEEF`：

- 旧二进制实际执行到 `20:000A`，R0=`BEEF`，验证失败。
- 新二进制四种情形均停在 `xx:0004`，R0=`1234`；未执行后续 guest 指令。

## 已确认的真实输入

`input-buffer-8800.bin` 是停机现场的 near data RAM `00:8800..8BFF`。
全部 1,024 字节与原始《英雄传奇》文件 `0x1BFAD8` 起的内容逐字节相同，正是 section 16
起点；不是从随机 RAM 搜到的短串，也不是宿主注入的数据。

```text
20 0D 05 34 F1 6B CA 68 08 0F 0D DC 9C E8 D2 8B ...
```

缓冲 SHA-256：`96268fa6aacbafcb3ff0e2f49f978cf49b7dd50d5c4d7fff60430dcbe94879d9`。
section 16 大小 27,976，头部 count=`0x0534`=1,332，满足 `4 + 1332×21`。
`file-path-526eba.bin` 保存对应原厂文件名内存；原文件是
`0:\应用程序\英雄传奇.npe`。内存字节 lane 与文件名字符顺序须按 DMCU 规则转换。

原厂 parser（source `49:0C56`，运行 `2C:0C56`）已实际写出：

| 物理数据地址 | 实际值 | 已知意义 |
| --- | --- | --- |
| `51:282A` | `000D` | 后端格式分支编号 13，选择高分支 |
| `51:282C` | `0534` | 对应输入头中的 count |
| `51:282E` | `003F` | parser 解出的字段；完整语义待证 |
| `51:2830/283C` | `1F40` | 8,000；具体时间/采样单位仍需与消费者闭合 |
| `51:2836` | `0003` | parser 解出的字段；完整语义待证 |
| `51:283A` | `20D0` | 查表所得 8,400；不能仅凭此就命名一种 codec |

这推翻了旧 gate=1 镜像下“本次没有消费 section 16”的适用前提；旧阴性结果只适用于旧配置。
仍未产生可验证的解码输出，不能仅凭 21-byte 记录、8,000/8,400 数值认定为 Speex、CELP 或其它标准。

## 服务契约的现有边界

2026-09-06 本地数据补充：直接按 NPE 第 16 段描述符取得 `0x1BFAD8` 起的 27,976 字节，
段 SHA-256 为 `300392f0771e5a88ed627466eb3f078380199fcf287ea405a0015612e0559a06`。
对其头后数据按 1,332×21 排列，首列低两位 0/1/2/3 分别出现 278/245/395/414 次，
末列对应 411/393/292/236 次。21-byte 等长切分并没有直接显露统一首/尾标记；
它仍只是布局假设，不能据此认定某种标准编码器或其帧边界，未据此生成解码实现。

| 入口 | 原厂调用证据 | 尚不能伪造的部分 |
| --- | --- | --- |
| `02:ACD8` | PRG 有 26 个直接调用，均传一 word、调用后清栈，不消费返回值；当前参数 `0014`；其它为 `0032` 或全局 `51:2AE4/2AFE` | 精确副作用、计时/硬件意义尚未知；不能按常量 20/50 就实现成宿主 sleep |
| `01:B6DE` | 六个调用；传 far `0000:8800` 和零 word；初次返回 `R0 & 6000` 非零时调用者返回 `FFFD`；重定位读位置时也再次调用 | 初始化/复位整个流状态，不只一个返回状态位 |
| `01:B7AA` | `26:8D2A` 的试处理循环、`2E:7FE4` 实际处理函数调用；输入为输出缓冲 far pointer 和另一个 far pointer；返回 count 写 `51:2AFA` | 输出格式、数据生成算法、状态推进/耗尽行为 |
| `01:B816` | 返回当前 far pointer，同时经一个 far pointer 参数写出 bit 余量；调用者用 `(ptr - 8800)*8 + remainder` 计算流位置 | 指针推进与 bit 游标精确约定；必须与 B6DE/B7AA/B84E 一致 |
| `01:B84E` | 六个调用，设置 far `0000:8800` 与 bit 余量；用于 seek/重新填充后继续 | 内部游标和跨缓冲状态不能各入口独立猜测 |

`2E:7FE4` 后续把 `00:2984` 的处理结果分两部分，经 `08:3536`、`08:372A` 处理到
`00:1000`，再调用另一个缺失入口 `02:AD92` 送往 `00:1784/2084`。
`08:2F22` 保存回调并写 `F010/F012`，`08:31AC` 后续启动的精确硬件通路仍需恢复。
这些是共同流状态/输出链，不应逐个填 RETS，也不应跳过 gate 来绕开。

## ACD8 参数与 AD92 缓冲契约：进一步静态约束

以下均使用 VMA03 运行地址，来自原始 PRG 的完整函数反汇编，不是实际执行了缺失 ROM。

- `31:192C..19F6` 将一 word 参数分档，写 `51:2AE4`；`31:1AC4..1B8E` 用相同
  规则写 `51:2AFE`。按无符号比较，输入区间 `0..22 / 23..28 / 29..41 / 42..59 /
  60..72 / 73..84 / 85..65535` 分别得到 `20 / 25 / 33 / 50 / 70 / 80 / 90`。
  两个函数本身没有硬件寄存器写入。初始化分别在 `32:F3C6..F400` 与
  `33:4B44..4B5A` 写默认值 20。
- 四个薄封装 `33:4D98/4DAE/4DF0/4E06` 调用上述分档函数；尚未找到它们的直接
  PRG 调用者或明确的导出名称，因此不能将这些数值命名为 MHz、毫秒、增益或滤波系数。
- 原厂已有独立的 `08:3324`（限制 0..7，写近地址 `4A65`）与 `08:334A`（限制
  10..160，写 `4A66`，按参数/100 重算计时配置）等调节函数。`08:34C4..3728`
  则读 `4A64`、查表并对 16-bit 样本做 MAC。不能为了补缺口，将 ACD8 随意别名到
  其中一个现成的音量/速度/样本增益函数。

`02:AD92` 共 8 个直接调用，参数是来源 far、目标 far、count，共五 word；调用者清栈
10 bytes，未消费返回值。已经确定的调用布局：

| 调用位置 | AD92 之前 | 来源 → 目标 / count |
| --- | --- | --- |
| `1D:32B6/3A02` | `08:372A` 按整数倍重复 word 样本 | `[4A82/84] → [4A7E/80]` / 0240 |
| `2F:771A` | 原厂样本增益与重复处理 | `[4A82/84] → caller far` / 0240 |
| `2E:813E/82B8` | `01:B7AA` 输出到 2984，再做增益和四倍重复 | `00:1000 → caller far` / `[51:2AE6]` |
| `2B:62CC/63CC` | 原厂 `08:372A` | `00:1C04 → 00:1784/2084` / 0200 |
| `31:391E` | `08:460E` 取得 SPI/DTU 接收缓冲并原地处理采样值 | `returned far → 00:1000` / 0200；随后交 `01:7E34` |

这说明 AD92 同时位于输出准备和输入缓冲处理链，不能简化成“向 DAC 写寄存器”。
`1D:2C7C/33CE` 根据 `[51:25CC] < 32` 设置软件位 `8C.7`；该位既选择
ACD8(20) 初始化，又选择样本重复/AD92 路径。另一分支直接配置缓冲指针和初始输出样本。
本节写作时 `51:25CC` 的字段含义仍未闭合；后续已由原厂 MPEG 头解析器确认它是
码率 kbit/s，见 [2026-09-07 初始化契约](np560_mp3_init_contract.md)。AD92 的实际算法
仍未知，以上不证明它是滤波器或 memcpy。

与未知算法独立，原厂 `24:97AC/98FC/9A1E` 已明确使用 DTU 指针表
`F0F0..F0FE`、`REG[21/22]` 和定时器 ICR.ED。缺失的传输硬件是后续输出的实际依赖，
不是用新硬件机制冒充已还原 ACD8/AD92。
