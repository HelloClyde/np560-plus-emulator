# NP560+ V3.80 常驻 ROM 启动契约

这里记录的是由升级包机器码、DMCU 专利指令/寄存器说明以及严格 QEMU
探针共同约束的行为。它不是原厂 ROM 字节复原；凡是仍依赖模型推断的部分
都会单独标明。

## 复位交接不是普通函数调用

- `20:0000` 先 `SCALL 03:0030`，再直接 `SJMP 33:4F50`。
- `33:4F50` 是事件处理器 `33:4510` 的 `0x008E` 激活路径中段，不是
  函数入口；其前序状态为 `R0:R1=context+0x38`、
  `R2:R3=context+0x30`，并已有兼容的外层栈帧。
- 所以常驻层必须构造寄存器、移位缓冲和栈帧状态，不能把 `03:0030`
  简化成通用 `RETS`。

## `20:0030` 与代码/数据分离

`20:0030` 是完整、可返回的固定回调。它写入逻辑寄存器
`7100=2082`、`7108=5001`，并清零下列半开数据区间：

- `00:0100..00:0FA0`
- `00:0FF0..00:5000`
- `00:8000..00:9000`
- `50:0000..54:0000`

主程序仍在 `50` 至 `53` 段取指，因此 PRG/NOR 代码映像和外部数据 RAM
必须保持为 Harvard 两套后端。QEMU 现在只在已证实的可写代码槽上建立
代码/数据共享别名。

## 外存边界寄存器

专利图 19 给出 EMCR 的字段：`EMBLK` 位于 bit 15..8，`WS` 位于
bit 1..0。`20:026A` 依次写入：

- `EMCR1 = 5002`：边界段 `50`，等待状态 `2`；
- `EMCR2 = 6001`：边界段 `60`，等待状态 `1`；
- `EMCR3 = F002`：边界段 `F0`，等待状态 `2`。

代码先设置 `DS0=1`，所以指令中的逻辑地址 `7108/710A/710C` 在当前
物理观测模型中对应 `F108/F10A/F10C`。这些字段说明外部片选边界与等待
状态，不会把 `2C:9A7C` 自动重映射到 `49:9A7C`。

## 两条编译器初始化链

PRG 中有 270 个连续复制描述符，全部调用覆盖目标 `32:F786`：

- `24:7FE4` 开始的第一组有 9 项，末尾 `SJMP 03:026A`；
- `2E:4560` 开始的第二组有 261 项，末尾 `SJMP 07:7FE4`。

平铺的 `32:F786` 是无关函数中段；`4F:F786..4F:F7C2` 则是完整的
60 字节编译器复制器。重建 ROM 通过普通 DMCU 数据读写把它装到
`32:F786`，然后执行原始描述符代码。双初始化探针验证了全部 9+261 项；
第二组最终写入图覆盖 2955 个字节。

第一组的源位于内部 ROM 段 `04`/`07`，但其存储值并未真正丢失。三个源
窗口严格遵循本映像已验证的 `+0x1D` 链接规则：`04:FFF8 <- 21:FFF8`
（8 字节，`0000000000008002`）、`07:57C8 <- 24:57C8`（4 字节全零）、
`07:A622 <- 24:A622`（16 字节，包含 `A62C/A62E` 两条 `RETS`）。前两处
分别位于平衡尾声后的段尾和两个完整函数之间，第三处后接 `FFFF` 填充，
边界均可逐字验证。系统映像现在使用这些原厂存储字节；只有独立 ABI 探针
继续使用显眼哨兵，并明确不把哨兵冒充成原厂数据。

两个直接 `SCALL` 改指该槽，因而保留平铺 `33:5906` 的原始 PRG 字节。

## 后续精确代码恢复

升级映像后来提供了两个此前未识别出的重定位模块，因此旧的
`08:427E`/`03:4124` 探针边界已经消失：

- `25:2EDC..25:4B8E` 是按同一 PC 链接到 `08:2EDC` 的完整 `0x1CB2`
  字节 resident 模块。其内部 27 个远调用全部选择段 `08`，并包含精确的
  `08:427E` 函数以及 `08:43A6` 前向远内存复制器；
- `20:4000..20:4790` 是 484 项、每项四字节的 resident `03:4000`
  AJMP 表，精确覆盖 `03:4124` 等入口。旧的“固定返回零”探针不再替换
  任何代码，只保留为兼容的构建流程开关。
- `3C:B496..3C:BA66` 是按同一 PC 链接到 resident `1F:B496` 的完整
  `0x5D0` 字节应用事件分派器。九个调用者均使用一字清栈，源地址没有原地
  调用；事件 `0x84` 已在 QEMU 中执行该原始客体代码并切换应用界面。
- `39:7FFE..39:87C8` 是按同一 PC 链接到 resident `1C:7FFE` 的完整
  `0x7CA` 字节资源单元模块；内部 `AJMP 39:8110 -> 39:873C` 及最终
  `RETS 39:87C6` 均保留。
- `3B:7E4E..3B:84BE` 是按同一 PC 链接到 resident `1E:7E4E` 的完整
  `0x670` 字节资源扫描模块，最终由 `3B:84BC` 正常返回。

同样，原先为探索而写的 `17:9244` 返回探针已被完整的同 PC
`34:9244` 文本/字形实现取代。以上均为升级映像内可逐字验证的客体
DMCU 机器码，不是 ABI 猜测。

## 当前已验证的系统启动顺序

系统 ROM 当前执行：

1. 安装 `32:F786` 复制器并调用原始 `20:0030`；
2. 执行 `24:7FE4` 的 9 项复制，再执行 `2E:4560` 的 261 项复制；
3. 安装已恢复的运行时、LCD、存储和应用覆盖；
4. 进入原始 `20:026A`，执行精确的 `2C:9A7C`、`08:2EDC`
   resident 模块以及后续初始化；
5. 由 clean-room `01:0200` 晚期装载器完成应用覆盖安装；
6. 进入精确的 `2D:7DD2` 顶层应用、`3B:F734` resident dispatcher、
   `31:D9AA` GPIO 扫描器和 `06:B126` 的 `F160/F164` 矩阵读取路径；
7. 从完整烧录后的 NAND checkpoint 读取资源，通过原始应用绘制路径驱动
   ST7529，生成非均匀 240×120 帧；
8. 事件 `0x82/0x83/0x85` 可从模态前台返回；`0x84` 则进入精确恢复的
   resident `1F:B496`，在同一应用生命周期内完成界面转换；
9. 一个前台生命周期返回后，`03:0080` 再次 `SCALL 20:026A`；由完整
   原厂主函数建立编译器帧、调用 `01:0200`，再进入 `2D:7DD2` 续体。
   两次 Enter 生命周期的严格追踪可见 `20:0326 -> 03:0084` 的真实
   `SCHEDRET`。该边界保存的寄存器为
   `R0=0000, R1=0080, R2=0085`：原厂 `20:0320` 尾声清除了 R0，但把
   应用退出事件留在 R2。对调度器拥有的生命周期分别注入 `0x82`、`0x83`
   后，同一精确边界又稳定得到 `R2=0082`、`R2=0083`。因此已经反推出
   原厂 selector 的输入寄存器 ABI，但尚未反推出它把事件映射到哪个后续
   应用的完整策略。`FIRST_LOW_SP/FIRST_LOW_FP` 始终为 `none`。精确
   `33:529E` 编译器尾声在 `33:52A4` 的最后一次 POP 会合法地令
   `SP=FFFE -> 0000` 持续一个指令，随后 `UNLINK` 从 `FP=FFF8` 恢复
   高地址栈；QEMU 将它单独记为 `BENIGN_SP_WRAP`，不会与异常低栈
   混淆；冷启动所用的
   `20:0004 -> 33:4F50` 激活路径不再被错误地重复执行。

严格系统测试的结果为 `ROM_HLE=off`、`ROM_MISSING=none`、
`UNSUPPORTED=none`、`INVALID_CONTROL=none`。按键只改变 `F010` 和
`F160/F164` 可见的物理状态；`F340_READS=0`、`KEY_CODE=0`，证明没有
回落到早期的主机 make-code latch。8×8 矩阵的 64 个物理位置已在同一
QEMU 系统会话中全部验证，均通过精确的 `2E:5F28` 扫描和 `28:F4A4`
映射。四个重点事件 `0x82/0x83/0x84/0x85` 中，返回/调度路径保持可交互，
`0x84` 进入精确 resident `1F:B496` 并完成同生命周期界面转换。
连续 64 个生命周期已越过旧的第 50 轮资源调用故障点，累计生成 1,554 帧
并完成 66 次 NAND 读取，低栈/低帧诊断始终未触发。运行时覆盖回归目前
逐字验证 223 个模块；重建 ROM 单元测试共 122 项。

多轮回归自然触发了 `02:C588`。四个静态调用只传 `0x23/0x24/0x30/0x65`
之一，调用者自行回收一个参数且不读取返回值；其中 `0x23/0x24` 包围相邻
`02:C5DC` 的三字节输出，`0x30/0x65` 只出现在芯片 ID `0xEC` 的 NAND
自检分支。当前以客体 ROM 中单条 `RETS` 还原其 CPU 可见契约；疑似外部
诊断字节副作用必须等到 SFR 或引脚证据出现后再建模，不虚构 UART 地址。

字体配置曾暴露出另一条 Harvard 数据别名：应用从数据地址 `33:707C`
取得字体基址，而平铺的同地址是指令 `6A0B FFEE`；其数据初始化像位于
`50:707C`，内容为 `33:D000`。QEMU 现在只为这四个有直接证据的字节建立
数据别名，原生 framebuffer 因此不再保持全零。

## 菜单目录、应用注册表与启动管理器

升级程序中已经恢复出一条不依赖主机 HLE 的完整菜单数据/调度骨架：

- `3D:0B82..3D:1142` 是链接到 `20:0B82` 的菜单动作辅助函数；其后
  `3D:1142..3D:161A` 是唯一连续的 124 项应用目录，每项五个字；
- `39:9748..39:9DBA` 是链接到 `1C:9748` 的 25 页层级表，每页固定

- `35:9A58..35:A510` 是链接到 `18:9A58` 的菜单事件分派器。它用
  15 项跳转表处理 `0x80..0x8E`，其中 `0x82/0x83/0x84/0x85` 分别进入
  已确认的选择、移动、打开和继续路径；
- `47:0514..47:079C` 是链接到 `2A:0514` 的 81 项应用注册表。每项为

  `0x2000`。`4C:E4C8..4C:E5EC` 是链接到 `2F:E4C8` 的原厂二分查找函数；
- `35:21F4..35:2D22` 是链接到 resident `18:21F4` 的完整应用启动

  再执行原始应用启动/退出流程；
- `3A:668A..3A:6DBA` 和 `3A:0EEA..3A:165A` 分别是链接到 resident
  `1D:668A`、`1D:0EEA` 的完整资源打开器和应用记录装载器；其前置
  `2B:E3E6` 上下文检查器来自完整源 `48:E3E6..48:E5FE`；
- `31:AA5C` 的完整源 `4E:AA5C..4E:AB00` 已恢复。它在
  `A0:70B8 bit0` 置位时，用 `A0:70B7` 对指定记录窗口逐字节异或；
- 注册表代码 `0x1203` 精确映射到通用菜单入口 `2C:C9E8`。其
  `49:C9E8..49:CBCA` 源函数、`2A:322A` 菜单表构造器、`32:AF98` 非对齐
  16 位读取器、`32:6F7C` 解码读取器及资源指针辅助函数均已装入重建 ROM。

以上代码和表全部来自 PRG 中同 PC 的 `+0x1D` 段源像，QEMU 只提供可执行
RAM/内部 ROM 映射。当前尚缺的是 `03:0080` 出厂 manager 在一个前台生命
周期返回后，如何依据 R2 事件和 resident 状态选择下一应用；目录、页面、
应用代码解析和通用菜单执行本身已不再是猜测。

## resident `02:DEA6` DES/3DES 契约

完整 4 MiB PRG 中共有 24 个 `SCALL 02:DEA6`，每个调用点返回后都执行
`ADD SP,#0x0C`，固定了六个栈字 ABI：数据远指针、密钥远指针、64 位块数和
方向字（`1` 加密、`0` 解密）。调用分布及块数为：

- `3A:0EEA`：15 次，块数 `0x80/0x40/0x41`；
- `3A:668A`：3 次，块数 `0x3E`；
- `4B:0192`：3 次，块数 `4`；
- `4B:AA26`：3 次，块数 `2`。

四个函数都以第一半 8 字节密钥加密、第二半 8 字节密钥解密、第一半再次
加密，因而这是证据闭合的双密钥 Triple-DES E-D-E，而不是按输出画面猜出的
“解码服务”。原始 `02:DEA6` 位于更新包不包含的 resident 段，无法逐字提取；
当前在该地址放置 clean-room 标准 DES DMCU 实现。置换表、轮移位和八个
S 盒由 `06:C000` 的客体初始化器写入物理 `5F:E000` RAM，所有加解密循环也
由 DMCU 执行，QEMU 不拦截 `SCALL`。

独立 QEMU 已知答案测试已验证：明文 `0123456789ABCDEF`、密钥
`133457799BBCDFF1` 加密得到 `85E813540F0AB405`，并能按方向零解回原文。
这同时覆盖了 DMCU 的 RB 高/低字节配对、外部总线 A0 字节交换、正向轮密钥
和反向轮密钥。

## 推断边界与仍待恢复

下面几项仍不能称为原厂 ROM 还原：

1. `01:0200` 的原始字节、精确覆盖安装顺序和应用状态 guard；当前实现
   根据调用点、覆盖依赖和可观察 ABI 以客体 DMCU 指令重建；
2. `2D:7DD2` 经 `20:0320` 退回后，原厂 resident 如何选择/切换下一个
   应用。当前 `03:0080` 是四字 clean-room 策略：`SCALL 20:026A`，然后
   跳回 `03:0080`。`2D:7DD2` 以 `ADD SP,#8` 开头，是消费父级传输帧的
   编译器续体，不能作为普通函数直接调用；现在由完整 `20:026A` 建立帧并
   进入它。同一 QEMU 进程连续 64 个退出生命周期通过，但原厂 manager 的
   出厂 manager 的下一应用选择策略仍未恢复；但 124 项目录、25 页层级、
   81 项应用注册表、`18:21F4` 启动管理器和代码 `0x1203` 的通用菜单链均已
   逐字恢复。精确返回探针和正常连续调度证明退出事件通过
   R2 传入 manager（已验证 `0082/0083/0085`），因此未知范围已经从
   “返回 ABI”收窄为“R2 事件与持久状态如何选择下一个应用”。停止在精确
   `20:0326 -> 03:0084` 边界后，三种事件的 PC、PSW、DS0/DS1、R0/R1、
   R3..R15 全部相同，只有 R2 不同；三次重复的完整 16 MiB 数据 RAM 差分
   也只留下矩阵原始索引 `51:28D6` 和事件副本 `51:28D8/28DA`，没有第二个
   稳定选择参数；
3. 原厂 `03:026A`、`07:7FE4` 的精确 resident 字节及完整冷启动时序；
4. `F20A/F20C/F20E` 成对奇偶 ECC 及厂商单比特纠错流程已经精确建模；
   仍未知的是完整文件系统 OOB 布局、坏块/磨损策略、应用级写入恢复路径，
   以及定时器/中断、音频、USB、更多 DMA/SFR 和未走到的外设寄存器；
5. 没有真机对照时，主界面的最终视觉、时间行为和电气寄存器布局只能
   追求行为兼容，不能证明逐字节等同于 factory mask ROM。

`03:0080 -> 20:026A -> 2D:7DD2 -> 20:0320 -> 03:0080` 的循环在 guest
CPU 上执行，不是 QEMU 的 ROM HLE，也不会由主机拦截 `SCALL`。它已通过单进程连续生命周期压力
回归，但尚不能替代出厂应用 manager 的选择策略，必须一直保留“推断”标签。
完整 4 MiB `NP560.PRG` 的签名审计进一步证明：全映像只有
`20:031C` 一处字面 `SCALL 2D:7DD2`，紧接着就是 `20:0320` 启动函数尾声；
指向 `03:0080` 的字面 `SCALL/SJMP` 为零。因此原厂 manager 不隐藏在可升级
PRG 的其他位置，而属于当前缺失的 SoC resident ROM。
